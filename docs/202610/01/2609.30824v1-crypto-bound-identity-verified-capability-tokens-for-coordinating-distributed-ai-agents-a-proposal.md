## 摘要
直到高能力语言模型问世，完全自主的交易型智能体这一前景才初现端倪。借助此类模型，自适应任务编排以及独立（但受约束）决策所带来的运营收益，对企业与个人而言都极具吸引力。然而，每个此类智能体都携带一个严重的攻击面，即提示注入；它可以破坏任何可能已置于上下文中的软性“护栏”。这些攻击的后果包括凭据外泄；如果不加以缓解，信任破裂会导致这类智能体整体无法使用。此外，考虑到自主智能体的增长预期，为其构建的安全框架将需要某种形式的去中心化才能扩展。借鉴拟议的 OAuth Agent Authorization Profile 以及 W3C DID 和 VC 标准，我们提出了一个基于能力安全原则并采用去中心化智能体身份的框架；其中，智能体基于令牌访问服务，这些令牌以加密方式绑定到智能体和签发者的身份，并规定其权限范围。服务在处理任何给定令牌之前，可以验证委托链仅涉及权限范围衰减。我们表明，这样一个位于安全模块中、处于语言模型上下文窗口之外的层，能够使智能体在可强制执行的安全边界内行动。

## Abstract
The prospect of fully autonomous transactional agents did not appear on the horizon until the advent of high capability language models. With such models, the operational benefits of adaptive task orchestration and independent (but constrained) decision making are tantalizing for enterprises and individuals alike. However, each such agent carries with it a serious attack surface in the form of prompt injection which can compromise any soft "guard rails" that may have been placed in context. The consequences of these attacks include credential ex-filtration which, if left unmitigated, renders the whole category of such agents unusable due to breach of trust. Furthermore, expecting a growth of autonomous agents, a security framework for them would require a form of decentralization to scale. Drawing on the proposed OAuth Agent Authorization Profile and the W3C DID and VC standards, we propose a framework based on the principles of capability based security with decentralized agent identity whereby agents access services based on tokens that are cryptographically bound to the agent's and issuer's identities and specify their scope. Services can validate that the delegation chain only involves scope attenuation before acting on any given token. We show that such a layer that lives outside the language model's context window in a secure module can enable agents to act within enforceable security boundaries.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：高能力语言模型的出现，使"完全自主的交易型智能体（transactional agents）"首次具备现实可能性。自适应任务编排、独立但受约束的决策对企业与个人都有巨大吸引力（MIT 2025 AI Agent Index 记录了智能体能力的快速扩散已超过治理框架的跟进速度）。
- **核心问题**：每个此类智能体都带有一个严重攻击面——**提示注入（prompt injection）**。它能击穿任何仅以"软护栏"形式写在上下文中的约束，导致**凭据外泄（credential exfiltration）**。一旦信任破裂，整类智能体将不可用。
- **规模问题**：预期智能体数量会爆发式增长，中心化的智能体身份与授权管理无法扩展，安全框架必须**去中心化**。
- **问题定位的独特性**：
  - 论文将"agent"定义为**代表人类（直接或传递性地）行动**的程序，而非仅能作用于世界的程序。
  - 强调隐私目标：服务提供方不应获知用户完整意图（例如航空公司只需知道订票，无需知道旅行目的与最终目的地），以免影响交易或产生后续风险。
  - 明确讨论为何**能力令牌（capability tokens）优于访问控制列表（ACL）**：ACL 是"行视角"（按资源列出可访问主体），能力是"列视角"（按主体携带可验证授权），在开放系统、大量临时性智能体的场景下更易扩展、泛化并支持去中心化委托。
- **整体含义**：论文主张构建一个**位于 LLM 上下文窗口之外**的加密安全层，使智能体只能在"可强制执行的安全边界"内行动，从而让分布式自主智能体在信任前提下可用。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想

以**能力式安全（Capability-Based Security）**为原则，结合 **W3C DID（去中心化标识符）+ VC（可验证凭证）** 标准与 **IETF OAuth Agent Authorization Profile（AAP）草案**，构建一套"加密绑定身份、仅允许权限衰减的委托链"的令牌体系，并将所有密钥与策略封装在**凭证钱包（Credential Wallet）**中，置于模型上下文之外。

### 2.2 能力令牌的结构与机制

- **令牌形态**：签名 JSON 结构（JWT 序列化），内含：
  1. 智能体身份（加密凭据，如从 `https://agentname.somedomain.com/.well-known/did.json` 获取，并可用 `plc.directory` 等公共目录校验）；
  2. 签发者身份与其所持权限（签发者可以是用户，也可以是持有另一张链式令牌的智能体）；
  3. 目标资源；
  4. 约束参数（交易目的、预算、读写权限、是否可再委托等）与有效期。
- **身份绑定**：令牌绑定到智能体身份，服务方可要求智能体通过**挑战-应答（challenge-response）**机制证明其持有对应私钥（验证方给随机串，智能体签名，验证方用预先知晓的公钥验签）。这意味着智能体必须可通过特定的安全 URI 端点访问。
- **委托链与权限衰减**：智能体向下级委托时，签发一张绑定自身授权的令牌，形成链。服务方在受理前必须验证**每一级委托只做权限衰减（attenuation），不得放大（amplification）**。论文明确指出"衰减判定是领域相关的"（脚注 1）。
- **身份锚定方式**：
  - DID 文档（JSON 结构）+ 公共目录（如 ATProto 的 `plc.directory`），信任部分转移到目录；
  - 或**互联网域名 + HTTPS 证书**（Let's Encrypt 使证书几乎免费，实现近去中心化托管），多智能体可用独立子域 + 独立证书区分；此时中心实体退化为域名注册商。
- **能力泛化到工具与本地资源**：能力不止用于 Web 服务，也可门控工具调用与本地文件系统访问（如限制只能访问某目录及其子目录），前提是工具自身使用能力感知的系统设施，云环境可借助 **WASI（WebAssembly System Interface）** 这类通用能力接口。

### 2.3 三层安全机制（论文 Table 1）

| 层次 | 机制 | 目的 |
|---|---|---|
| 用户 → 智能体 | 主能力令牌（master capability token） | 授权协调者代表用户行动 |
| 智能体 → 智能体 | 委托能力令牌（ECDSA 签名 JWT） | 限制每个子智能体于其声明权限，防止权限提升 |
| 智能体 → 服务 | W3C 可验证呈现（did:jwk + ECDSA） | 向外部服务认证而不暴露原始凭据；钱包策略阻止提示注入导致的窃取 |

### 2.4 凭证钱包（Credential Wallet）模式

- 核心目的：**移除智能体读取原始签名凭据的能力**，使其无法自行生成可验证呈现（VP）。
- 架构要点（Figure 4 / Figure 9）：
  - 钱包作为**独立进程**运行，仅通过**类型化 IPC** 通信，位于 LLM 上下文之外；
  - 服务验证方（ServiceVerifier）下发**一次性挑战 nonce**，验签后将 nonce 加入**已消费集合**以防重放；
  - 采用 **BBS-2023 / BBS+** 做零知识证明派生，实现**选择性披露**与 **VP 去关联（unlinkability）**；
  - 每个验证域使用**成对 DID（pairwise DID）**，身份呈现与支付呈现使用**相互独立的成对密钥**（key_A ≠ key_B，key_C ≠ key_D），使不同服务间无法关联用户。
- 钱包实现建议：
  - 钱包独立进程 + 类型化 IPC；
  - 用**钱包持有的密钥做 HMAC**，而非 SHA-256 之类的哈希；
  - 所有拒绝消息必须**完全一致**，避免沦为预言机（oracle）；
  - 使用 **BBS-2023** 替代 ECDSA 类证明以获得不可关联性。

### 2.5 撤销机制的设计权衡

- 根本矛盾：若令牌完全**离线可验证**，撤销极难甚至不可能；任何中间环节又增加延迟。
- 参考 RFC 7009 的"令牌撤销端点"，但会造成网络访问开销与延迟。
- 论文给出三种替代设计：
  1. **短寿命令牌**（如 5 分钟）+ 强制刷新，刷新失败即视为已撤销；代价是延迟。
  2. **父令牌引用 + 链式回溯**：服务方沿父链走查，支持任意子树级撤销，但延迟取决于委托树深度。
  3. **密码学累加器（cryptographic accumulator）**：发布在已知端点，令牌携带见证与累加器 epoch，被撤销令牌从累加器移除后验证失败；管理复杂但性质良好。

### 2.6 威胁模型（要点）

- **假设**：人与智能体都能在不依赖中心签发服务的前提下证明对自身 DID 的控制；无撤销的签名令牌链足以授权；令牌有效期保持短以缓解时序攻击；用户信任其所访问的核心服务。
- **需保护的资产**：用于身份证明、签名与生成 VP 的各类密钥；LLM 不得通过猜测签名秘密来生成有效令牌。
- **主要威胁**：伪造 DID 控制权、篡改能力令牌与 VP、针对任一参与智能体的提示注入、恶意代码在合法服务/智能体边界内的权限篡改、令牌重放劫持、长期用户画像导致身份盗用、服务提供方内部人员越权访问"守卫"、以及**签发者事后抵赖**（对支付网关等尤为重要）。
- **本提案聚焦的攻击面**：**能进入 LLM 上下文窗口的内容**，因为秘密外泄与约束篡改都会破坏交易安全。

## 6. 主要结论与发现

- **加密绑定、身份可验证、内嵌约束且委托时仅衰减**的令牌，是管理临时性"代表用户行动"的智能体资源访问的**可扩展方案**。
- W3C DID/VC 标准与 OAuth 面向智能体的授权草案，已构成一条**成熟可采纳的标准路径**。
- **BBS

BBS-2023/BBS+ 等零知识证明技术，是实现**选择性披露与跨服务不可关联**的关键工具，使"钱包持有凭据、智能体只做呈现"这一分离架构在密码学上成立。
- **把秘密挡在 LLM 上下文窗口之外**，是本提案最具操作性的安全主张：只要智能体自身无法读取原始签名密钥与凭据，提示注入即便成功操控其推理，也无法直接完成凭据外泄或伪造呈现。
- 论文明确承认若干问题**尚未解决**：撤销机制的三种设计各有代价，无一是"免费午餐"；委托链的权限衰减判定依赖领域语义，难以通用自动化；实现差异（不同钱包、不同验证方的行为不一致）本身会引入新的攻击面。

## 7. 局限性与开放问题

- **无形式化安全证明**：论文未对令牌链、委托衰减、钱包 IPC 边界给出形式化模型或可证明安全性论证，威胁模型为定性列举。
- **撤销是最大未决难题**：短寿命令牌、父链回溯、密码学累加器三条路径分别以延迟、深度依赖、管理复杂度为代价，论文未给出定量取舍建议，也未讨论跨域撤销的协调问题。
- **衰减判定的领域依赖**：脚注承认"衰减是否成立"需按领域定义，这意味着跨组织、跨行业的委托链验证缺乏统一语义，可能成为互操作性瓶颈。
- **信任锚的转移而非消除**：无论是 DID 公共目录（如 `plc.directory`）还是域名 + CA 证书，都把信任集中到了新的中介；论文将其表述为"退化为中心实体"，但未深入分析这些中介被攻陷或审查时的后果。
- **钱包本身的攻击面**：作为独立进程，钱包需防御宿主环境（浏览器、操作系统）的恶意代码、IPC 劫持与侧信道；论文虽强调"类型化 IPC"与"拒绝消息一致化"，但未给出完整的钱包威胁模型。
- **缺乏可用性与部署成本评估**：零知识证明的生成/验证开销、用户审批交互频率、多智能体场景下的延迟累积，均无数据支撑。
- **隐私与合规的张力**：成对 DID 与 VP 去关联提升了用户隐私，但也可能与企业 KYC/AML、反欺诈审计要求冲突，论文未展开讨论。

## 8. 实践启示与后续方向

- **对工程实践的启示**：
  1. 在智能体架构中应尽早引入"上下文外安全组件"（钱包/策略引擎）这一分层，而非把授权逻辑写进系统提示；
  2. 委托链设计应默认"只衰减"，并在验证侧强制执行逐级检查；
  3. 身份呈现与支付/权限呈现应使用独立密钥与成对 DID，避免跨服务画像；
  4. 撤销策略宜按令牌敏感度分层选择（高敏感短 TTL，低敏感走链式或累加器）。
- **对标准化的启示**：论文将 W3C DID/VC 与 IETF OAuth AAP 视为可复用基座，暗示未来工作重点在于**补齐智能体特有的语义**（委托衰减规则、钱包互操作、撤销协调），而非另起炉灶。
- **对研究的启示**：该提案留下了明确的可研究空白——形式化验证、撤销方案的定量比较、衰减语义的可组合规范、钱包实现的安全基准，以及面向真实多智能体工作负载的性能评测。
- **总体评价**：作为一篇立场/提案论文，其价值在于**清晰的问题定位、标准对齐的架构蓝图与诚实的风险披露**，而非实证结论。它更像一份"设计议程"，为后续的系统实现与安全评估提供了可检验的靶子；但在被采纳前，仍需实验与形式化工作来回答其自身列出的开放问题。
