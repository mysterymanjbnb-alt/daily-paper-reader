## 摘要
大语言模型（LLM）智能体正在从聊天界面进入基础设施运维领域，在那里它们读取遥测数据、调用工具、生成并执行代码，并改变生产 Kubernetes 集群的状态。这打破了传统云原生安全所假设的一条边界：数据与控制之间的边界。智能体仅仅读取的内容（一行日志、一张工单、一段工具描述）就可能改变其行为方向。本文认为，模型不应被视为安全边界，因此 Kubernetes 上智能体的安全性本质上是一个基础设施问题：所有保障都必须在智能体已被提示注入完全攻陷的假设下仍然成立。我们贡献了：（i）面向在 Kubernetes 之上及内部运行的智能体的威胁模型与十类威胁分类法，并与新兴的 OWASP 智能体应用指南保持一致；（ii）九项设计原则，核心是在工具边界实施完全中介，并打破不可信输入、敏感访问和外部外联三者的组合；（iii）一个七层纵深防御框架，将每项原则映射到 Kubernetes 原生或广泛采用的机制：工作负载身份、RBAC 与 ValidatingAdmissionPolicy、通过 SIG Apps Agent Sandbox 项目实现的 gVisor/Kata 沙箱、FQDN 感知的出站策略、带有对工具参数执行策略即代码的智能体/MCP 网关，以及 eBPF 运行时强制执行；（iv）一个参考架构，包含具体策略工件以及针对 Amazon EKS、Azure Kubernetes Service 和 Google Kubernetes Engine 的逐层绑定；（v）一项定性评估，包括威胁-控制覆盖矩阵和四个攻击演练，并提出一种实证方法。我们不报告实测的攻击成功率或开销数据；相反，我们识别残余风险以及验证该框架所需的测量指标。

## Abstract
Large language model (LLM) agents are moving from chat interfaces into infrastructure operations, where they read telemetry, call tools, generate and execute code, and change the state of production Kubernetes clusters. This collapses a boundary that conventional cloud-native security assumes: the boundary between data and control. Content that an agent merely reads (a log line, a ticket, a tool description) can redirect what it does. This paper argues that the model must not be treated as a security boundary and that agent safety on Kubernetes is therefore an infrastructure problem: every guarantee must continue to hold under the assumption that the agent is fully compromised by prompt injection. We contribute (i) a threat model and ten-class threat taxonomy for agents operating on and within Kubernetes, aligned with emerging OWASP guidance for agentic applications; (ii) nine design principles, centered on complete mediation at the tool boundary and on breaking the combination of untrusted input, sensitive access, and external egress; (iii) a seven-layer defense-in-depth framework that maps each principle to native or widely adopted Kubernetes mechanisms: workload identity, RBAC and ValidatingAdmissionPolicy, gVisor/Kata sandboxing via the SIG Apps Agent Sandbox project, FQDN-aware egress policy, an agent/MCP gateway with policy-as-code over tool arguments, and eBPF runtime enforcement; (iv) a reference architecture with concrete policy artifacts and per-layer bindings for Amazon EKS, Azure Kubernetes Service, and Google Kubernetes Engine; and (v) a qualitative evaluation comprising a threat-control coverage matrix and four attack walkthroughs, with a proposed empirical methodology. We report no measured attack-success or overhead figures; instead we identify residual risks and the measurements needed to validate the framework.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景迁移**：LLM 智能体正从聊天界面走向基础设施运维，能够读取遥测数据、调用工具、生成并执行代码，并直接改变生产 Kubernetes 集群的状态。Kubernetes 成为其天然归宿，因为它承载被管理的工作负载、拥有适合自动推理的声明式 API，且已涌现出 MCP、A2A、kagent、agentgateway 等生态。
- **边界崩塌**：智能体是一种"新型主体（principal）"——其行为不由可审查的代码固定，而是模型、提示词与上下文窗口中所有内容的函数。它无法可靠区分"指令"与"数据"。因此，智能体仅仅读取的内容（攻击者控制的容器日志行、资源注解、工单字段、第三方 MCP 服务器提供的工具描述）就可能变成它用自身凭证执行的命令。
- **传统假设失效**：云原生安全赖以成立的"数据平面/控制平面"分离在智能体面前崩塌。间接提示注入、工具投毒（tool poisoning）、工具"拉地毯"（rug-pull）等攻击已在真实系统中被验证。
- **核心主张**：**模型不是安全边界**。模型对齐、系统提示、输入分类器只能降低误行为概率，无法提供保证，其失效模式可被对抗性地发现。因此智能体安全是一个**基础设施问题**：必须像多租户平台安全那样，假设工作负载是敌对的，约束其可触及、可执行、可外泄的一切，而不管它"意图"如何。
- **关键建模选择**：一旦注入成功，即授予攻击者对智能体后续工具选择与参数的**完全控制权**——"我们信任控制平面、内核、运行时、策略引擎、网关和身份提供方，但不信任模型、智能体进程、上下文、检索内容、外部工具元数据与生成代码。"

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体框架结构
论文提出 **"七层技术控制（L1–L7）+ 一个横切治理层（G）"** 的纵深防御框架，并用九项设计原则统摄：

- **九项设计原则（P1–P9）**：
  - P1 模型不是安全边界；P2 工具边界完全中介；P3 最小代理权（按任务而非按产品授权）；P4 委托且可归因的身份；P5 隔离不可信执行；P6 打破"致命组合"；P7 优先可逆、可审查的动作（走 GitOps PR）；P8 可观测与可归因；P9 有界自主（限速、预算、熔断）。

- **七层框架**：
  - **L1 身份**：每智能体独立 ServiceAccount，禁用默认 SA 与 token 自动挂载；使用 audience 绑定的短时投影令牌；云侧使用工作负载身份联合（EKS Pod Identity/IRSA、Entra Workload ID、GKE Workload Identity Federation）而非静态密钥；SPIFFE/SPIRE 提供跨集群身份。通过 **OAuth 2.0 Token Exchange (RFC 8693)** 实现"用户+智能体"双主体委托，或使用 K8s 用户模拟（impersonation）让 RBAC 按人类权限评估。
  - **L2 授权与准入**：命名空间级 Role（绝不使用可写 ClusterRole），默认只读，排除 `pods/exec`、`secrets`、`serviceaccounts/token`、RBAC 对象；用 **ValidatingAdmissionPolicy（CEL）** 通过 `matchConditions` 仅约束智能体身份，弥补 RBAC 无法表达"对象内容约束"的缺陷（如禁止缩容到 0、禁止改控制平面命名空间）；Pod Security 采用 restricted 标准。
  - **L3 执行隔离**：通过 RuntimeClass 使用 **gVisor**（用户态内核）或 **Kata Containers**（轻量 VM）；使用 SIG Apps **Agent Sandbox** 项目的 Sandbox CRD，配合模板、声明（claims）、预热池降低启动延迟；沙箱按会话临时创建、不挂载 token、非 root、只读根文件系统、丢弃全部 capability、镜像按 digest 固定。
  - **L4 网络**：默认拒绝出入站；出站仅允许集群 DNS、网关、模型端点；因外部服务 IP 变动，必须用 **FQDN 感知策略（如 Cilium）**；智能体 Pod 无 API Server 路由，所有集群操作经网关后的工具服务器执行，实现 P2；东西向用 mTLS。
  - **L5 工具中介（最核心控制点）**：在智能体与所有工具服务器（MCP）、对等智能体（A2A）之间放置 **agentgateway**，执行五项功能：(1) 认证与令牌交换；(2) **对工具及参数授权**（用 OPA/Rego 或 Cedar 做结构化决策，因为危害在于参数而非工具名，如 `scale(deployment, 0)`）；(3) 工具供应链控制（签名镜像、固定工具元数据哈希以检测 rug-pull、拒绝名称混淆/shadowing）；(4) 响应处理（剥离可疑标记、限长、标注来源，属"卫生措施"而非边界）；(5) 日志与限速。并将工具分为 **observe / propose / act** 三档风险等级。
  - **L6 数据与密钥**：密钥永不进入上下文，由工具服务器服务端从密钥管理器获取；日志/事件工具在源头脱敏；**记忆溯源**（记录来源与信任级别、分区、可回滚）；**信息流分离**——采用 CaMeL 思路，将"读取不可信数据的隔离读取器"与"从不摄入原始不可信内容、经 L5 行动的规划器"分为独立 Pod 与身份。
  - **L7 运行时检测与响应**：eBPF（Tetragon 可执行强制，如击杀尝试打开 token 路径的进程；Falco 提供规则集）；API Server 审计日志按智能体身份建立基线；网关决策日志中的拒绝峰值是注入进行中的强信号；**预设的 kill switch**（吊销身份、缩容、隔离网络策略、失效网关会话）。
  - **G 治理**：人工审批（按工具+参数哈希绑定且过期，防重放）；**按环境分级的自主权层级表**（dev/staging/prod × observe/propose/act/destructive）；预算与熔断（针对无需对手即可发生的失控循环 T8）。

### 2.2 威胁模型与分类法
- **系统模型**：运维智能体作为集群工作负载，接受人类或自动化任务，调用 MCP 工具，可请求代码执行沙箱，可存记忆，可经 A2A 委派子任务。
- **五类对手能力**：A1 内容注入；A2 恶意/被攻陷的工具服务器；A3 恶意生成代码；A4 低权限内鬼；A5 良性故障。
- **十类威胁（T1–T10）**：T1 目标劫持（间接注入）；T2 工具误用/过度代理；T3 权限提升/混淆代理；T4 工具与 MCP 供应链；T5 不可信代码执行与逃逸；T6 数据与凭证外泄；T7 记忆与上下文投毒；T8 级联/失控动作；T9 智能体间欺骗；T10 抵赖与不可追溯。与 OWASP 智能体指南对齐并特化到 Kubernetes。
- **"致命组合"（Lethal Combination）**：严重危害需同时具备三要素——暴露于不可信输入、访问敏感数据/特权动作、能对外通信或改变状态。任缺其一即可大幅限定损害。K8s 特别适合结构性执行：三要素分别映射到工具授权、RBAC/密钥放置、出站策略。

## 6. 主要结论与发现

- **核心结论**：AI 智能体把"内容"变成"命令"。在 Kubernetes 上，一条错误命令的代价以停机衡量，因此安全响应应是**把智能体当作不可信租户**，并在基础设施中**重建数据/控制边界**。
- 提出的威胁模型、九项原则、七层框架与参考架构，使得**每个动作都被中介、每项保证在智能体被完全攻陷时仍然成立、自主权按动作类别逐级获得**。
- **覆盖矩阵的两个关键性质**：(1) 每类威胁都有至少两层缓解，且至少有一个主控强制点位于智能体进程之外，无任何威胁仅依赖模型行为；(2) 注入驱动的威胁（T1/T2/T6）各由工具边界（L5）的预防控制与不同执行点的独立控制（L2 于 API Server、L4 于 CNI）双重覆盖，单一配置错误不导致危害。
- **残余风险**（明确承认）：
  - 有害但合规的动作（策略无法判断"是否明智"）；
  - 范围内的完整性攻击（误导性摘要、微妙的坏 PR，靠审查质量而非基础设施控制）；
  - 经模型通道的外泄（模型端点是必要的允许出站目的地，只能靠合同与数据驻留控制 + L6 最小化上下文）；
  - 隔离运行时与策略引擎自身的漏洞（它们进入可信计算基础）；
  - 策略漂移（多层策略之间的一致性本身需要被测试）。
- **标准化缺口**：缺少工具调用授权请求的通用 schema、MCP 中签名且版本化的工具元数据标准、多智能体链中委托用户身份的传播标准、跨 OpenTelemetry span 追踪智能体推理的约定。
- **下一步最重要的方向**：Kubernetes 原生注入基准，在分层消融下测量效用与攻击成功率，让平台团队能基于证据选择自主权层级。

## 7. 优点

- **问题定位精准且立场鲜明**："模型不是安全边界"这一命题具有重要的实践指导意义，将讨论从"如何让模型更安全"转向"如何在假设模型失败的前提下约束后果"，与 Saltzer & Schroeder 的完全中介、最小特权、混淆代理等经典原则形成有力呼应。
- **"致命组合"三要素框架（不可信输入 / 敏感访问 / 外部通信）极具操作性**：三要素在 Kubernetes 中分别映射到可控制的资源（工具授权、RBAC 与密钥放置、出站策略），为工程实践提供了清晰的结构性抓手。
- **层次化设计与强制点独立性**：强调每个威胁至少有一个主控位于智能体进程之外，并通过"绕过测试"（禁用上层验证下层）来验证独立性，这是纵深防御论证中少见且严谨的设计意图。
- **具体可落地**：提供六个真实策略工件（VAP/CEL、Sandbox CRD、Cilium FQDN 策略、OPA/Rego、Tetragon、GKE FQDNNetworkPolicy），而非停留在抽象原则。
- **多云差异化分析扎实**：明确指出 EKS/AKS/GKE 在沙箱、FQDN 出站、身份绑定三处的实际差距（含 AKS ACNS 付费与吞吐退化、GKE 每 FQDN 50 地址上限、EKS 无托管沙箱），并给出"策略跨云统一、隔离实现随云变化"的设计原则，对多平台组织有直接价值。
