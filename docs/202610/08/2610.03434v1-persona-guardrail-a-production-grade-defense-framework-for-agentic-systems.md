## 摘要
基于大语言模型的智能体正越来越多地通过与企业知识、工具和外部服务交互来执行特定领域任务。现有的运行时护栏主要针对黑盒威胁模型下的提示注入和其他特定攻击行为，但难以保证智能体在其预期功能范围内运行。因此，生产环境中的智能体仍然容易受到恶意请求和域外查询的影响，而现有防御往往无法区分这些请求。我们提出 Persona Guardrail，这是一种生产级运行时防御框架，通过由语义允许列表和阻止列表规范驱动的同步输入和输出验证，为面向客户的智能体 AI 系统强制实施明确的功能边界。我们还引入 PAGE（Persona-Aware Guardrail Evaluation），这是一个用于评估功能特定护栏的基准，涵盖用户轮次和智能体轮次上的良性、对抗性和域外交互。与通用的基于 LLM 的护栏相比，Persona Guardrail 将总体准确率从 85.7% 提高到 95.9%，将域外检测率从 57.3% 提高到 93.5%，并将误批准率从 25.0% 降低到 4.7%。Persona Guardrail 目前已部署在生产环境中，在满足其延迟预算的同时，在真实生产负载下保持极低的误拦截率和误放行率。这些结果表明，Persona Guardrail 为保护智能体 AI 系统提供了实用、可扩展且可投入生产的基础。

## Abstract
Large language model-based agents are increasingly deployed to perform domain-specific tasks by interacting with enterprise knowledge, tools, and external services. Existing runtime guardrails primarily target prompt injection and other attack-specific behaviors under a black-box threat model, but provide limited guarantees that agents operate within their intended functionality. As a result, production agents remain vulnerable to malicious requests and out-of-domain queries that existing defenses often fail to distinguish. We present Persona Guardrail, a production-grade runtime defense framework that enforces explicit functional boundaries for customer-facing agentic AI systems through synchronous input and output validation driven by semantic allowlist and blocklist specifications. We also introduce PAGE (Persona-Aware Guardrail Evaluation), a benchmark for evaluating function-specific guardrails across benign, adversarial, and out-of-domain interactions on both user and agent turns. Compared with a generic LLM-based guardrail, Persona Guardrail improves overall accuracy from 85.7% to 95.9%, increases out-of-domain detection from 57.3% to 93.5%, and reduces the false-approved rate from 25.0% to 4.7%. Currently deployed in production, Persona Guardrail meets its latency budget while sustaining a very low false-block and false-allow rate under realistic production workloads. These results demonstrate that Persona Guardrail provides a practical, scalable, and production-ready foundation for securing agentic AI systems.

## 2. 论文提出的方法论

### 2.1 核心思想：功能边界（Functional Boundary）

- 将智能体可接受的所有查询空间 \(Q\) 划分为：
  - \(Q = Q_{\text{allow}} \cup Q_{\text{block}}\)
  - \(Q_{\text{allow}}\)：符合智能体预期功能、应被处理的查询。
  - \(Q_{\text{block}}\)：应被拒绝的查询，包括恶意/不安全查询，以及部署配置中选择拒绝的域外查询。
- 由于自然语言空间近乎无限，无法显式枚举集合，因此用**语义允许列表（allowlist）和阻止列表（blocklist）**近似表示功能边界。
- 论文比较三种表示：
  - 仅允许列表；
  - 仅阻止列表；
  - 允许列表 + 阻止列表混合。
- 关键设计判断：
  - 仅允许列表安全性强，但容易因枚举不全导致误拦；
  - 仅阻止列表只能枚举已知攻击，难以识别“能力范围内但不在职责范围内”的请求；
  - 允许列表与阻止列表应尽量不重叠，重叠会造成分类冲突和不确定性。

### 2.2 功能边界的构建

- **初始构建来源**：
  - 分析智能体实现与产品规格：使用代码导向 LLM 分析工具、API、检索组件、系统提示和外部资源，推断支持的请求类别，生成初始语义允许列表。
  - 安全驱动的阻止列表：纳入提示注入、间接提示注入、越狱、目标劫持、功能边界违规、工具滥用等已知攻击模式，以及部分域外查询类别。
- **上线后演化**：
  - 先在 **shadow 模式**观察生产流量，不执行拦截；将未被初始规范覆盖的合法交互补充进允许列表。
  - 通过生产遥测、攻击模拟和人工反馈持续精化边界。
  - 新攻击出现或用户行为漂移时，更新阻止列表和允许列表。

### 2.3 输入护栏与输出护栏

- **输入护栏**：
  - 在请求到达智能体前运行。
  - 判断用户请求是否落在功能边界内，决定放行或拦截。
- **输出护栏**：
  - 在智能体生成响应后、返回用户前运行。
  - 验证响应是否符合预期功能、组织政策和安全要求。
  - 可拦截政策违规响应，即使攻击已经影响智能体；但不检查中间工具调用或推理步骤。

### 2.4 分类器架构选择

论文评估了四种输入/输出护栏架构：

1. **Embedding 检索**：将查询嵌入，与允许/阻止示例做向量相似度比较，按最近邻和阈值分类。
2. **LLM 分类**：低延迟推理模型接收查询和功能边界规范，直接输出 allow/block。
3. **混合检索 + LLM**：高置信度查询用嵌入模型分类，低置信度转给 LLM。
4. **微调分类模型**：用智能体特定的允许/阻止示例微调分类器。

比较维度：分类性能、推理延迟、运维复杂度、跨异构智能体的泛化能力。

- 最终选择 **LLM-based 分类器 Qwen3-30B-A3B**：
  - 采用 MoE 架构，总参数约 30B，每 token 激活约 3B；
  - 量化为 FP8；
  - 输入和输出护栏共用同一分类模型；
  - 功能边界以语义规范表达，而非智能体特定示例，因此同一模型可服务多个智能体。

### 2.5 生产部署与持续演化机制

- **模型服务**：
  - 使用 vLLM on NVIDIA Dynamo；
  - 推理解耦为 CPU 前端和 GPU worker；
  - 前缀缓存感知路由器将请求分发到 decode worker；
  - 限制上下文长度，超限请求在 GPU 调度前拒绝；
  - 单 token 输出，延迟主要由 prefill 主导。
- **延迟预算**：
  - 目标是每次护栏调用 P90 低于 100 ms；
  - 利用大共享提示前缀（约 93% 输入 token）做前缀缓存复用。
- **版本化与安全发布**：
  - 每个智能体维护独立策略，包含用户请求和智能体响应的允许/阻止意图；
  - 候选更新需通过安全、效用、可靠性、延迟阈值；
  - 策略作为声明式配置发布，不重新部署共享服务栈；
  - 新策略先 shadow，再有限放量，最后激活；
  - 人工审核独立把关，失败则保留旧策略。
- **持续演化**：
  - 主要精化人类可读的意图分类体系，而非重新训练分类器；
  - 发现池与保留验证池分离；
  - 使用更强 judge 模型辅助标注，但 judge 或策略不一致本身不被直接视为错误标签；
  - 去重、来源追踪、采样限制，减少评估泄漏。
- **多智能体部署**：
  - 智能体特定功能边界存储在 MySQL，通过 Registry 管理；
  - 共享安全阻止列表集中维护，一次添加即可全局生效；
  - 分离“每智能体允许列表”和“全局安全阻止列表”，提高扩展性。

## 3. 实验设计

### 3.1 基准：PAGE（Persona-Aware Guardrail Evaluation）

- **定位**：首个同时覆盖用户轮次和智能体轮次、跨四个生产域、包含良性/对抗/域外/混合意图的功能特定护栏基准。
- **规模**：
  - 共 2,180 条带标签消息；
  - 其中 2,076 条围绕四个 persona 合成，104 条来自 AgentHarm 投影；
  - 组成：1,004 良性、448 对抗、444 域外、180 混合；
  - 标签参考：1,184 应允许、892 应阻止；
  - 轮次分布：1,280 用户轮次、796 智能体轮次；
  - 四个 persona 各 519 条消息。
- **四个域**：Workspace、Slack、Banking、Travel，取自 AgentDojo 的域定义；论文只使用域定义，不运行 AgentDojo 环境、工具或间接注入攻击套件。
- **请求类型**：
  - benign：良性且在范围内；
  - adversarial：对抗性攻击；
  - out-of-domain：域外但可能良性；
  - mixed：良性在范围请求与越界/对抗附加内容混合。
- **生成来源**：
  - AgentDojo 人工任务：234 条良性 + 对抗种子；
  - LLM 合成：Claude Opus 4.8，生成 972 条良性 + OOD 幻觉内容；
  - 确定性对抗模板：582 条对抗 + 混合；
  - 跨 persona 投影：288 条困难 OOD；
  - 使用不同模型家族生成与评估，避免自评偏差。
- **对抗覆盖**：六类攻击家族——未授权接收方、第三方数据访问、社会工程/权威冒充、数据外泄、提示注入、权限/配置篡改。
- **OOD 覆盖**：
  - 跨 persona 违规（最难，因为流畅且任务化）；
  - 通用域外用户查询；
  - 智能体幻觉内容（诗歌、代码、观点）。
- **长度多样性**：5–152 词，良性中位数 17，对抗 14，OOD 23，混合 37。
- **指标**：
  - 将 block 视为正类；
  - TP：正确拦截；TN：正确放行；FN：误放行；FP：误拦截；
  - \(FAR = FN / (FN + TP)\)，误批准率；
  - \(FBR = FP / (FP + TN)\)，误拦截率；
  - 同时报告准确率、精确率、召回率、F1。

### 3.2 对比配置

在同一 PAGE 划分上比较五种配置：

1. **Baseline（LLM judge）**：只给通用自然语言智能体描述，无允许列表、阻止列表或 persona。
2. **+ Allowlist**：提供 persona 允许列表，只有匹配允许意图才放行。
3. **+ Iterated allowlist**：根据上一配置的误放行和误拦截样本精化允许列表措辞，做一次数据驱动迭代。
4. **Blocklist only**：仅用不允许意图的阻止列表。
5. **Allowlist + Blocklist**：同时使用允许列表和阻止列表。

### 3.3 模型选择实验

- 对比模型：
  - Qwen3-VL-30B；
  - Qwen3-30B-A3B（8-bit / FP8 部署）；
  - Qwen3-8B（8-bit）；
  - Qwen2.5-7B；
  - Qwen2.5-3B。
- 评估数据：代表生产智能体的良性、OOD、对抗查询。
- 良性评估包含三个子集：最高频查询、随机采样、扩展良性集。
- 指标：批准率、OOD/对抗误批准率、中位推理延迟。

### 3.4 其他实验

- **Per-label 分析**：按良性、对抗、OOD 分解性能。
- **Per-agent 分析**：Workspace、Slack、Banking、Travel 四个智能体分别报告 FBR、对抗检测率、OOD 检测率。
- **Mixed-intent 消融**：比较“无混合”“混合标为应允许”“混合标为应阻止”三种策略。
