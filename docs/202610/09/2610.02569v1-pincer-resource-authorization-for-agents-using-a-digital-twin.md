## 摘要
编码智能体已变得越来越长时程、自主，依赖通用 shell，并维护自身的持久记忆以实现自我改进。尽管这些能力使智能体变得强大，但也使它们更难防御外部对手。限制这种架构的防御手段——类型化工具、信息流控制或策略预测引擎——放弃的功能太多，难以被采用。如今部署的智能体（如 Claude、Codex）主要依靠用户介导与自动模式沙箱相结合作为主要防御。在用户介导的沙箱中，用户维护的策略会随时间衰减，反复的权限请求会导致用户疲劳，而自动模式的工具调用分类器不会学习用户特定策略，也并非用于防御对抗性设置。Pincer 是一种新的防御，作用于资源层，并与工具调用层已有的防御（如自动模式）协同工作。Pincer 的核心是数字孪生，一种隔离上下文的模型，可自动学习并执行动态的、用户特定的最小权限策略。数字孪生持续学习用户偏好，使其能够作为用户代理来处理智能体的权限请求。为了模拟学习阶段，我们提出了一个新的以用户为中心的数据集，其示例遵循多天的用户-智能体交互记录。我们的评估表明，与若干基线（包括 LLM 评判器的变体以及 Conseca (HotOS '25) 的改编版本）相比，Pincer 在安全性和实用性上均表现强劲。我们重点指出了一些攻击类型，在这些攻击类型上，Pincer 的设计相比所有其他基线带来了显著的安全提升，同时即使在其他类型的攻击上也能优于基线。

## Abstract
Coding agents have become increasingly long-horizon, autonomous, reliant on general-purpose shell and maintain their own persistent memory for self-improvement. While these capabilities have made the agents powerful, they have also made them harder to defend against external adversaries. Defenses that restrict this architecture --- typed tools, information-flow control, or policy prediction engines --- give up too much functionality to be adopted. Agents deployed today (e.g. Claude, Codex) rely on a combination of user-mediated and automode sandboxing as their primary defense. In user-mediated sandboxing, user-maintained policies decay over time and repeated permission requests cause user fatigue, while auto mode's tool-call classifiers learn no user-specific policy and are not meant to defend against adversarial setups. Pincer is a new defense that operates at the resource layer and works alongside existing defenses at the tool-call layer like the auto mode. At the core of Pincer lies a digital twin, an isolated-context model that automatically learns and enforces dynamic user-specific least-privilege policies. The digital twin keeps continually learning the user's preferences allowing it to act as the user's proxy for the agent's permission requests. To emulate the learning phase, we propose a new usercentric dataset with examples following a multi-day transcript of user-agent interaction. Our evaluation shows that Pincer performs strongly on both security and utility in comparison to several baselines which includes variants of LLM judges and adaptations of Conseca (HotOS '25). We highlight attack types where Pincer's design leads to a significant security improvement compared to all other baselines, while outperforming the baselines even for other types of attacks.

## 1. 核心问题与研究背景

- **背景**：编码智能体（如 Claude Code、Codex）正变得**长时程、自主化**，依赖通用 shell 工具，并维护**持久记忆**以自我改进。这带来强大自动化能力，同时打开了攻击面（间接提示注入、记忆投毒、误导性文件名等）。
- **核心矛盾**：
  - **学术界**主张强防御（类型化工具、信息流控制、可信规划器），但**牺牲过多功能**，无法被实际采用（例如禁止执行数据中的指令、禁止维护记忆）。
  - **工业界**（Claude、Codex）主要靠**用户介导沙箱 + 自动模式（auto mode）分类器**，但存在两类顽疾：
    - **权限蔓延（privilege creep）**：用户维护的策略随时间衰减、累积、变得过度宽松。
    - **权限疲劳（permission fatigue）**：反复弹窗导致用户审查下降。
  - 自动模式分类器**不学习用户特定策略**，且仅工作在**工具调用层**，无法推理代码深层依赖链的效果（例如把 `rm -rf *` 藏进 `test.py` 即可绕过）。
- **论文含义**：提出 **Pincer**，一种部署在**资源层**（文件、网络等）的防御，与工具调用层防御（如自动模式）**互补共存**，在不牺牲功能的前提下自动学习并执行**用户特定的最小权限策略**。

## 2. 方法论

### 2.1 核心思想
- 引入**数字孪生（digital twin）**：一个隔离上下文的 LLM 判官，持续学习用户偏好，作为用户在智能体权限请求上的代理。
- 两大安全原则：**完全中介（complete mediation）** 与 **最小权限（least privilege）**。
- 系统由四类组件构成：LLM（worker 与 twin）、专用状态（memory / twin state）、工具（含特殊"资源请求工具"）、资源。
- 工作流：用户 prompt → worker 执行任务 → 工具访问资源 → 未授权则通过资源请求工具向 twin 请求 → twin 决策 grant/deny → 授权在任务结束后撤销。

### 2.2 关键技术细节

- **信任模型与上下文分类**：
  - **可信上下文（tctx）**：仅来自用户（当前/历史 prompt、历史授权）。
  - **不可信上下文（uctx）**：可能被攻击者影响。
  - **优势无关上下文（advantage-agnostic context, actx）**：经预处理函数 P 处理的不可信上下文，满足对任意 PPT 决策过程 D，攻击者优势 ≤ negl(λ)。
- **可信状态（trusted state）**：仅含可信上下文，但不足以推导最小权限策略（缺少访问模式信息）。
- **访问模式（access patterns）**：将工具调用日志中实际访问的资源路径附加到每条 prompt 记录，用于学习最小权限。
- **误导性资源名攻击（Section 5.3）**：攻击者通过命名 `taxreturn2025-corrected.txt` 或"内容洗白/来源洗白"诱导 twin 误判。
- **净化（sanitization）**：对路径各段分别施加 **PRF**（而非哈希，哈希易被 LLM 反演），生成 `a3321a/ddd9dd/77a111` 形式的优势无关路径，保留目录前缀结构以支持匹配。
- **双重投票（double voting）**：
  - `v1 = D((tctx, uctx′), rsrc′)`：仅可信 + 优势无关上下文，构成安全基石。
  - `v2 = D((tctx, uctx′, conts, prior), (rsrc′, reasn))`：额外纳入文件内容、worker 理由、会话历史，支持内容相关策略，但面临范围扩展风险。
- **预承诺策略（pre-committed policy）**：
  - 在会话首条 prompt 到达时，基于 prompt、工作区、文件名、可信状态生成结构化策略（Listing 1 的 pathGlob/access/operations/permission 模式）。
  - 生成后净化得到 `policy′`，用于第三票 `v3 = D((tctx, uctx′, policy′), rsrc′)`。
  - 经验显示，用未净化上下文生成 policy 可将攻击成功率从 40% 降至 20%。
- **最终决策**：`v1 ∧ v2 ∧ v3` 的合取。
- **定理 1（Grant Integrity）**：若 Pincer 授权，则仅凭可信 + 优势无关上下文也会授权，即 `D(tctx, actx, uctx; r) = grant ⇒ LLM(tctx, actx; r) = grant`。

### 2.3 攻击面与防御定位
- 资源层决策针对**具体命名对象 + 有限访问模式**（读/写/创建），避免工具调用层命令空间不可枚举的问题，且 token 成本更低（资源请求数通常远少于工具调用数）。
- 资源层粒度较粗（如无法判断文件内容被替换），故需与工具调用层防御**纵深防御**。

## 3. 实验设计

### 3.1 数据集
- **全新用户为中心合成数据集**（据称是首个此类数据集）：
  - 通过四步流水线生成：Persona 选择 → 用户引导（自然语言策略 + 合成工作区）→ 用户模拟（生成 prompt 与访问模式历史）→ 标注安全/效用样本。
  - 两个 persona：
    - **软件开发者**：33 个工作区文件、2 个项目、40 条历史 prompt、33 条用户策略、66 个安全样本、81 个效用样本。
    - **民事诉讼辩护律师**：95 个工作区文件、5 个项目、60 条历史 prompt、33 条用户策略、72 个安全样本、80 个效用样本。
  - 关注点差异：开发者侧重架构（共享密钥、跨项目访问），律师侧重法律（律师-客户特权、对方律师通信）。
- **攻击类型**：DI（直接注入请求）、II（间接注入）、MP（记忆投毒）、CL（内容洗白）、PL（来源洗白）。

### 3.2 指标
- **ASR / cASR**（攻击成功率 / 条件攻击成功率，越低越好）。
- **BGR / cBGR**（良性授权率 / 条件良性授权率，越高越好）。

### 3.3 基线方法
- **NanoClaw**：无资源请求机制，worker 拥有全部资源访问（无 gate）。
- **Static-Judge**：LLM 判官，通用安全指令，无历史。
- **Dynamic-Judge**：LLM 判官，含完整历史，维护自身状态（可被不可信上下文污染）。
- **Conseca+**：将 Conseca (HotOS '25) 适配到资源层，prompt 到达时承诺策略文件，用正则匹配执行。
- **Conseca-Gemini+**：在 Gemini CLI 中实现，用 LLM 判官替代正则匹配。
- **Pincer / Pincer-P2**：两者共享 v1、v3，区别在于 v2 是否纳入预承诺策略。

### 3.4 实现
- 基于 **NanoClaw** 实现；worker 与工具跑在容器内，资源在宿主 bind-mount，通过 **OS 内核 + POSIX ACL** 做中介（worker 用非特权 UID，容器不做 user-namespace remapping）。
- 容器任务结束后销毁；聚焦文件系统资源，其他资源可用 capability-based 访问控制。
- 代码与数据集计划开源：`https://github.com/ucbsky/Pincer`。

## 6. 主要结论与发现

- **安全-效用前沿**：Pincer 在保持与基线相当效用的同时，安全性显著提升。
- **条件率（Table 2）**：

- **按攻击类型**：
  - 在所有攻击类型上 Pincer 优于多数基线。
  - **记忆投毒（MP）**：Pincer 显著优于 Dynamic-Judge（后者状态未隔离，被持久污染）。
  - **来源洗白（PL）**：Pincer 在两个 persona、两个模型家族上均显著优于所有基线。
- **成本**：Pincer 开销约为基线 2–3×，但作者给出三种降低途径（状态压缩为常设策略、批量资源请求、预批准路径匹配）。

## 7. 优点

- **架构定位巧妙**：在资源层而非工具调用层做授权，规避命令空间不可枚举问题，token 成本更低，且与现有部署（自动模式）兼容、可纵深防御。
- **形式化保证**：提出 advantage-agnostic context 与 grant integrity 定义，并用 PRF 构造满足该定义，给出 Theorem 1 证明。
- **多重投票设计清晰**：v1 提供安全骨架、v2 支持内容相关策略、v3 抑制范围扩展，各票职责明确、互不替代。
- **攻击面分析细致**：识别并形式化"误导性资源名攻击"，并区分哈希（可被反演）与 PRF 的差异。
- **数据集贡献**：首个面向多天用户-智能体交互、同时含安全与效用标签的用户为中心数据集。
- **工程落地**：基于 NanoClaw 完整实现，使用 OS 内核 + POSIX ACL 做中介，保证 worker 无法绕过。

## 8. 不足与局限

- **数据与偏差**：数据集完全合成，persona 灵感来自公开博客但内容虚构，存在分布偏差风险；仅两个 persona，覆盖职业有限。
- **模型覆盖**：每个 persona 仅用一个模型（Haiku 4.5 与 Muse Spark 1.2），未在同一 persona 上交叉验证多模型，结论的泛化性受限。
- **消融不足**：未单独评估去掉 v1/v2/v3、去掉 PRF、去掉预承诺策略等组件的贡献。
- **对比基线限制**：未直接对比生产环境中的 auto mode 分类器；Conseca 的适配版本可能未完全复现原方法。
- **成本问题**：Pincer token 开销为基线的 2–3×、NanoClaw 的 4–15×，作者虽给出优化方向但未实现验证。
- **资源类型局限**：当前仅实现文件系统资源；web API、云资源等仅提出可用 capability-based 访问控制，未实现。
- **粒度限制**：资源层无法检测"内容被替换"等细粒度问题，必须依赖工具调用层

防御形成纵深防御。

- **可扩展性与延迟**：twin 每次决策需多次 LLM 调用（v1/v2/v3 至少三次推理），在高频资源访问场景下可能成为延迟瓶颈；论文未报告端到端延迟数据。
- **策略可解释性**：twin 的决策对用户而言仍是黑盒，用户难以审计"为什么这次授权被拒绝"，可能削弱用户对系统的信任与纠错能力。
- **撤销粒度**：授权在任务结束后统一撤销，缺少任务中途细粒度的即时回收机制；若 worker 在任务内被污染，撤销窗口仍然存在。
- **预承诺策略的时效性**：策略在首条 prompt 时生成并冻结，若用户在会话中途改变意图，策略可能滞后于真实偏好。

## 9. 启示与展望

- **部署启示**：
  - 资源层授权可作为**低成本、高兼容性**的安全增量，叠加在现有沙箱与自动模式之上，无需替换既有工程栈。
  - "数字孪生"范式可推广到其他需要**持续学习用户偏好**的场景（如浏览器智能体、企业内网助手、多智能体协作中的委托授权）。
  - PRF 净化 + 优势无关上下文的构造思路，对任何"不可信内容进入 LLM 决策链"的系统都具有参考价值，可独立于 Pincer 复用。
- **研究方向**：
  - 将 twin 状态**压缩为常设策略**，把每次决策的推理开销摊薄为一次性学习成本。
  - 支持**批量资源请求**与**预批准路径匹配**，降低 token 与延迟开销。
  - 扩展资源类型至网络、云 API、数据库，并探索 capability-based 访问控制与 Pincer 决策的融合。
  - 在**同一 persona 上交叉验证多个模型**，并引入真实用户数据以检验分布外泛化。
  - 引入**人机协同审计**（如决策理由可视化、用户反馈回路），缓解黑盒决策带来的信任与纠错问题。
  - 与工具调用层防御（如 auto mode 分类器）做**联合评估**，量化纵深防御的边际收益。

## 10. 总体评价

Pincer 是一篇问题定位精准、设计层次分明的系统安全论文。其核心贡献不在于发明新的密码学原语，而在于**把成熟的"完全中介 + 最小权限"原则，通过数字孪生与优势无关上下文的构造，重新适配到 LLM 智能体的资源授权场景**，并给出可证明的授权完整性保证（Theorem 1）。多重投票（v1 安全骨架 / v2 内容感知 / v3 抑制范围扩展）与预承诺策略的组合，体现了对"安全性与功能性张力"的务实权衡。

其局限同样清晰：合成数据集、单一模型 per persona、消融不充分、token 成本偏高、资源类型单一。这些并非致命缺陷，而是指向明确的后续工作清单。总体而言，论文为"如何在不牺牲自主性的前提下为长时程智能体做权限治理"提供了一个有理论支撑、可工程落地、且与现有部署兼容的候选答案，具备较强的启发意义与实用潜力。
