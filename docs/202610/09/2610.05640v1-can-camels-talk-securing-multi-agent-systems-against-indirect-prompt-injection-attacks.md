## 摘要
间接提示注入攻击——嵌入在大型语言模型所处理内容中的恶意指令——仍然是安全部署使用工具的智能体的主要障碍。CaMeL [Debenedetti 等，2025] 通过将可信控制流与不可信数据分离，并在运行时执行基于能力的安全策略，缓解了单个智能体面临的这一威胁。在这项工作中，我们研究了 CaMeL 的安全保证在分层多智能体系统中是否可组合，其中智能体将其他智能体作为工具调用。我们发现 CaMeL 的保证并不具备可组合性。我们构造了一个具体的提示注入攻击，尽管所有组成智能体都各自运行 CaMeL，该攻击仍能成功。我们的攻击利用了这样一个事实：不可信数据可被下游智能体重新解释为可信输入。然后，我们提出了 multi-CaMeL，一种智能体到智能体的通信协议，它通过将可信自然语言指令与通过独立数据通道传递的不可信数据分离，在跨智能体边界时保留溯源信息。我们在 AssetOpsBench 上评估 multi-CaMeL 的效用，并在 MultiAgentDojo 上评估其安全-效用权衡；MultiAgentDojo 是我们通过将 AgentDojo 扩展到多智能体场景而开发的基准。我们发现，multi-CaMeL 将攻击成功率（ASR）降至 0.0%，而单个智能体 CaMeL 为 0.2%，无 CaMeL 时为 12.9%。multi-CaMeL 会带来效用成本，但该成本随着模型能力提升呈下降趋势，并且对于最强模型而言较为有限，这表明能力更强的模型能更好地适应该协议所施加的约束。

## Abstract
Indirect prompt injection attacks - malicious instructions embedded in content processed by large language models - remain a major obstacle to safely deploying tool-using agents. CaMeL [Debenedetti et al., 2025] mitigates this threat for an individual agent by separating trusted control flow from untrusted data and enforcing capability-based security policies at runtime. In this work, we investigate whether CaMeL's security guarantees compose in hierarchical multi-agent systems, where agents invoke other agents as tools. We find that CaMeL's guarantees do not compose. We construct a concrete prompt-injection attack that succeeds despite all constituent agents individually operating CaMeL. Our attack exploits the fact that untrusted data can be reinterpreted as trusted input by a downstream agent. We then introduce multi-CaMeL, an agent-to-agent communication protocol that preserves provenance across agent boundaries by separating trusted natural-language instructions from untrusted data passed through a distinct data channel. We evaluate multi-CaMeL's utility on AssetOpsBench and its security-utility tradeoff on MultiAgentDojo, a benchmark we develop by extending AgentDojo to the multi-agent setting. We find that multi-CaMeL reduces attack success rate (ASR) to 0.0%, compared with 0.2% for individual-agent CaMeL and 12.9% with no CaMeL. Multi-CaMeL incurs a utility cost, but this cost trends downward as model capability increases and is modest for the strongest models, suggesting that more capable models better accommodate the constraints imposed by the protocol.

## 1. 核心问题与整体含义

- **背景**：间接提示注入（indirect prompt injection）指攻击者把恶意指令嵌入网页、邮件、文档等外部内容中，由 LLM 智能体在处理任务时"顺带"读取并执行。随着智能体被赋予外部数据源、工具与服务访问权限，攻击面显著扩大。
- **既有防御谱系**：
  - 模型级：微调 / 偏好优化，让模型学会区分特权指令与低权限内容（如 Instruction Hierarchy、Meta SecAlign）。
  - 输入级：DataFilter、prompt sanitization、sandwich prompting、spotlighting——依赖学习到的模型行为，**不提供硬安全保证**。
  - 系统级：Willison 的 **Dual LLM 模式**（Privileged LLM + Quarantined LLM）、信息流控制、细粒度权限控制。
- **CaMeL**（Debenedetti 等，2025）是 Dual LLM 的具体实例：PLLM 只接收可信指令，把控制流表达为一段 Python 程序；QLLM 处理不可信数据；自定义解释器跟踪数据依赖并在工具调用边界执行基于能力的安全策略。它在 AgentDojo 上显著优于工具过滤、spotlighting、prompt sandwiching。
- **核心问题**：CaMeL 的安全保证是为**单个智能体**设计的。在日益常见的**分层多智能体 / agent-as-tool（父智能体把子智能体当工具调用）**架构中，这些保证能否**组合（compose）**到系统层面？
- **整体含义**：论文给出否定答案——**逐智能体加固不足以保护系统**。不可信数据跨越智能体边界后可被下游智能体重解释为可信输入，作者称之为 **boundary laundering（边界洗白）**。由此提出一条更广义的安全原则：**跨越智能体边界不应隐式提升信息的信任等级**。

## 2. 方法论

### 2.1 形式化设定

- **分层 agent-as-tool 系统**定义为三元组 \(M = (A, H, T)\)：
  - \(A = \{A_i\}_{i\in I}\) 为智能体集合；
  - \(H \subseteq A\times A\) 是以 \(A_0\) 为根的有向树（父子关系）；
  - \(T = \bigcup_i T_i\) 为工具集，\(T_i\) 是 \(A_i\) 可用工具。
  - 用户只与根智能体交互；每个非根智能体被其唯一父智能体"当作自己的用户"调用，调用返回值像普通工具调用一样回传给父智能体。
- **关键定义**：
  - **控制流计划（control-flow plan）**：预先指定的程序，作为中间工具返回值与计算的函数，确定性地规定工具调用的顺序与选择。
  - **控制流完整性（CFI）**：智能体/系统的执行被限制在由用户指令与其他可信信息（如工具、环境描述）所决定的控制流计划内。
  - **安全策略 S** 与 **CaMeL-secure**：系统满足 CFI 且 S 在工具调用上被全局执行。CFI 等价于平凡策略（S = ∅）下的 CaMeL 安全性。

### 2.2 攻击构造：boundary laundering

- 场景：Orchestrator + SQL Agent + Notification Agent 三个**各自都运行 CaMeL** 的智能体，用户指令为"把求职者信息摘要发给 Julie"。
- 注入点：SQL 数据库中的恶意指令要求把申请人数据外泄到 `ruth@email.com`。
- 失败链路：
  - SQL Agent 与 Orchestrator 的控制流计划**不受影响**（工具返回值只作为运行期变量，PLLM 从不观察其内容）；
  - 但 Orchestrator 把**被污染的**摘要值拼进了传给 Notification Agent 的自然语言参数；
  - Notification Agent 把该参数当作**自己的用户指令**，于是 PLLM 直接读到注入文本，**新增一个 `send_email(ruth@email.com)` 调用**，完成外泄。
- 结论：单个智能体的 CFI 成立，但系统级 CFI 被破坏——这是"不可组合性"的具体反例。

### 2.3 不可组合性的理论刻画

- **表达性假设**：(i) 对任意智能体与任意工具，存在某用户指令，其控制流计划会调用该工具并把结果返回给用户；(ii) 对任意智能体、任意一对工具（含 agent-as-tool 接口）与参数 \(q\)，存在某用户指令，其计划先调用 \(T_1(q)\)，再用依赖于其返回值的参数调用 \(T_2\)。
- **Claim**：若 \(M\) 是**非平凡**（\(|A|>1\)）的分层 agent-as-tool 系统，且存在某个返回值不可信的工具 \(T\)，则 \(M\) **不满足 CFI**，即使每个 \(A_i\) 单独满足 CFI。
- **证明思路**（分两种情形）：
  - 情形 1：\(A_i\) 是 \(A_j\) 的父节点。由假设 (ii)，存在指令使 \(A_i\) 先调用 \(T\)，再用依赖 \(T\) 返回值的指令调用 \(A_j\)，于是 \(A_j\) 的计划依赖不可信数据。
  - 情形 2：\(A_j\) 是 \(A_i\) 的父节点。由假设 (i) 令 \(A_i\) 调用 \(T\) 并回传结果给 \(A_j\)；再由假设 (ii)（取 \(T_1^j=T_2^j=A_i\)）令 \(A_j\) 以依赖首次调用返回值的方式再次调用 \(A_i\)，该指令即依赖不可信数据。

### 2.4 multi-CaMeL 协议

- **接口改造**：把 agent-as-tool 调用从
  `query_agent_j(message: str) -> str`
  改为
  `query_agent_j(message: str, variables: dict[str, Any]) -> str`
  - `message`：**可信**自然语言指令，是子智能体 PLLM 唯一可见的输入；
  - `variables`：不透明数据字典，子智能体 PLLM **不直接观察其内容**。
- 子智能体通过新增工具 `get_variable(variable_name: str) -> Any` 在运行期取用这些值。
- **解释器扩展**（保证协议被真正强制执行）：
  1. **指令通道完整性**：agent-as-tool 调用的 `message` 参数不得依赖任何工具输出——从机制上堵死边界洗白。
  2. **跨智能体溯源保持**：经 `variables` 传递的值，其能力标签与溯源信息跨边界保留，从而使非平凡安全策略 S 可在每个智能体内局部执行即等价于全局执行。
- 与单智能体 CaMeL 不同：multi-CaMeL 的**解释器是 CFI 的必要条件**，与是否配置安全策略无关。

### 2.5 安全保证

- 归纳论证：根智能体的控制流计划仅由可信输入固定；递归地把每个 agent-as-tool 调用点展开为子智能体的计划，得到**系统级控制流计划**，同样只由原始用户指令与可信信息决定。
- **branch steering（分支导向）**：不可信数据仍可决定预定义计划中走哪条分支（例如父智能体按工具返回值选择 `child_agent(query_1)` 或 `child_agent(query_2)`），但两条路径本就已在计划中——这**不构成 CFI 违规**。
- 该行为比信息流非干扰性质（Garby 等的 TIPNI）更宽松，作者明确将二者的形式化关系留作未来工作。

  3.
