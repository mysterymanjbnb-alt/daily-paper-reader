## 摘要
使用工具的LLM智能体仍然容易受到间接提示注入攻击，因为可信指令与不可信观察共享同一上下文，使恶意内容能够影响具有严重后果的输入过滤防御。多路径共识防御仍留下较高的攻击成功率，因为它们检查内容或聚合输出，而不是对效果进行授权，尤其是对于工具内攻击而言，该攻击保留预期工具但操纵其参数。诸如CaMeL的数据流控制提供了更强的保证，但会带来显著的时间延迟，限制了实际部署。我们提出ToolFence，它在执行前编译类型化授权蓝图，通过确定性监控器强制执行；当蓝图不完整时，要求评判器授予新能力，而不是对每个具体调用进行裁决。ToolFence提供两个关键优势。第一，其细粒度且感知来源的授权使系统能够区分用户授权的值与不可信观察，有效应对工具内攻击。第二，其确定性快速路径与能力级运行时授权大幅减少昂贵的评判器调用频率，提高运行时效率。在AgentDojo与Qwen3-max上，ToolFence将总体ASR降至接近零，仅有3.80个百分点的干净效用下降和实际可接受的运行时开销。

## Abstract
Tool-using LLM agents remain vulnerable to indirect prompt injection because trusted instructions and untrusted observations share one context, allowing malicious content to steer consequential input-filtering defenses. Multi-path consensus defenses still leave a high attack success rate because they examine content or aggregated outputs rather than authorizing effects, especially for the within-tool attack, which preserves the intended tool but manipulates its arguments. Data-Flow Control such as CaMeL provides stronger guarantees, but incurs substantial time latency that limits practical deployment. We introduce ToolFence, which compiles a typed authorization blueprint before execution, enforces it through a deterministic monitor, and when the blueprint is incomplete asks a judge to grant new capabilities rather than adjudicate each concrete call. ToolFence provides two key advantages. First, its fine-grained provenance-aware authorization enables the system to distinguish user-authorized values from untrusted observations, effectively addressing the within-tool attack. Second, its deterministic fast path and capability-level runtime grants substantially reduce the frequency of expensive judge calls, improving runtime efficiency. On AgentDojo with Qwen3-max, ToolFence reduces overall ASR to near zero with only a 3.80 percentage-point clean-utility drop and practical runtime overhead.

## 1. 核心问题与研究背景

- **根本矛盾**：工具调用型 LLM 智能体的系统策略、用户请求、检索文档、邮件、网页、工具输出共享同一个上下文，模型无法可靠区分"携带权威的指令"与"不可信数据"。攻击者可在外部内容中嵌入指令，诱导智能体执行用户从未授权的动作——即**间接提示注入（Indirect Prompt Injection）**。
- **威胁演进**：攻击已从简单的"忽略先前指令"扩展到针对工具描述、聊天模板边界、记忆、多步交互循环的结构化攻击（如 ToolHijacker、ChatInject、ASB）。因此仅保护初始 prompt 不够，授权必须覆盖完整执行轨迹。
- **现有防御的三类失败模式**：
  - **工具内劫持（within-tool hijacking）防御不足**：攻击者保留被授权的工具，只篡改其权威敏感参数（收件人、金额、URL、目标账户）。RepeatPrompt、ToolFilter、输入过滤、SecInfer 共识防御均忽视"可执行权威"。
  - **强隔离开销过高**：CaMeL 通过来源追踪与能力强制实现强控制/数据流隔离，但需定制执行管线，延迟与成本高（12.95×）。
  - **静态工具过滤损害效用**：静态白名单无法预知所有合法能力，导致计划外的合法调用被拒，任务无法完成。
- **核心洞察**：安全相关单元既不是单次调用（太细、重复裁决浪费），也不是整个会话（太粗、无法适应），而是**能力（capability）**——即"工具 + 效果类别 + 权威敏感参数的来源约束"这一抽象形状。形状可复用，具体值不可复用。

## 2. 方法论

### 2.1 整体框架（四组件）
ToolFence 是推理时防御，将"能力授权"与"动作执行"分离，流程为：编译授权蓝图 → 确定性监控（快路径）→ 运行时能力授予（慢路径）→ 跨会话缓存。

### 2.2 类型化授权蓝图（Typed Authorization Blueprint, §3.2）
- **策略架构师**：一个隔离的 LLM 调用，仅可见认证查询 q 与控制器拥有的工具 schema，**绝不接触不可信内容**，将 q 编译为类型化计划 **P = (M, C)**。
- **M（工具清单）**：为每个工具赋予效果标签 e ∈ {READ, LOCAL_COMPUTE, COMMUNICATION, FINANCIAL, EXTERNAL_WRITE, DELETE, …} 及逐参数的权威敏感性标记。
- **C（能力集合）**：每个能力为元组
  **c = (tool, e, {pⱼ ↦ βⱼ}, κ, r)**
  分别指定工具、效果、参数绑定、调用预算 κ、可复用标志 r。
- **四种绑定类型 βⱼ**：
  - `LITERAL`：值直接来自用户请求 q；
  - `DERIVED`：值来自指定源工具 s 的输出，即 v ∈ Obs(s)；
  - `TEMPLATE`：值匹配一个锚定于 q 与源工具的认证模板；
  - `FREE`：参数非权威敏感，可由智能体自选。
- **关键点**：蓝图记录的是**来源约束而非具体值**，这是后续"授权能力形状而非具体动作"的前提。
- 示例：`send_money(recipient ← read_file("bill.txt"), amount ← q)`，而非仅"允许 send_money"。

### 2.3 确定性监控器（Deterministic Monitor, §3.3）
对每个拟议调用 a = (tool, x) 做**零 LLM 成本**的三项检查：
1. **能力匹配**：存在 c ∈ C 覆盖所有参数；
2. **绑定合规**：LITERAL 须出现在 q 中；DERIVED 须出现在已执行的声明源工具输出中；TEMPLATE 须匹配模式且源工具已执行；
3. **预算**：已提交调用数低于 κ（或 r=TRUE 的可复用只读能力）。
- **读自动放行（Read Auto-Allow）**：仅当所有参数来源为 USER 时自动放行；若参数派生自工具输出或模型（如从被注入网页提取的 URL），则不自动放行而送交 judge。论文报告无条件下信任读操作会带来 60% ASR。

### 2.4 动态运行时能力授予（§3.4）
- 当调用未命中蓝图时，**不立即拒绝，也不问"这个具体动作是否可接受"**，而是请求授予新能力并扩展运行蓝图。
- 控制器为每个参数计算来源标签 **π(pⱼ) ∈ {USER, TOOL, MODEL}**。
- **关键防护**：若任一权威敏感参数的来源为 MODEL（模型自创），则提案直接置空 **ĉ = ⊥**，在咨询 judge 之前即阻断经典注入形状。
- Judge 只看到**能力形状**（工具、效果、来源约束、敏感性标记），**不看具体参数值**，输出 Grant(ĉ) ∈ {GRANT, DENY}。批准后追加至运行计划并注册预算；拒绝则回退到单次调用裁决作为最后手段。

### 2.5 跨会话能力缓存（§3.5）
- 以**无值签名**为键：**sig(c) = (tool, e, {pⱼ ↦ (βⱼ, source_toolsⱼ)})**。
- 缓存**仅存形状**（绑定类型与源工具名），从不存具体值、证据文本或先前工具输出。
- 复用时，每个具体参数仍须针对**当前会话**已执行的声明源重新校验，因此授权不会被跨会话搬运。实验中判官调用减少 43%。

### 2.6 安全性质（附录 A.2）：Fail-Closed 授权
- **式(5)**：a ∉ C ∪ G ∧ Grant(ĉ) ≠ GRANT ⟹ 不派发；
- **式(6)**：∃ pⱼ 权威敏感 ∧ π(pⱼ)=MODEL ⟹ ĉ = ⊥；
- **式(7)**：PARSE_FAIL(ĉ) ⟹ Grant(ĉ) = DENY。
- 即使模型完全被不可信输出操控，控制器（而非模型）把守权威边界，注入问题被降维为带安全默认值的"能力授权问题"。

### 2.7 算法流程（Algorithm 1 概要）
编译蓝图 → 注入缓存 → 循环：接收拟议动作 → 监控器确定性检查（通过即派发）→ 来源计算 → 读自动放行 → 构建授予提案（模型生成的权威敏感参数则置空）→ 缓存命中则授权派发 → 否则 judge 裁决授予 → 仍失败则单次调用裁决 → 拒绝则返回诊断消息。
