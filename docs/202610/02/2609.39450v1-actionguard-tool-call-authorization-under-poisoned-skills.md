## 摘要
基于LLM的智能体通过第三方技能扩展能力，这些技能提供任务特定的指令、脚本和工具使用流程。然而，在原本良性的技能中插入恶意指令，可使良性用户请求触发危险的工具调用，包括数据外泄、文件删除或未授权代码执行。本文提出ActionGuard，它在技能影响的工具调用即将执行前进行检查。ActionGuard将目标智能体的动作生成上下文与防护机制的授权上下文分离。目标智能体可使用原始技能进行规划，但Reviewer不会接收可能被投毒的原始技能文本。相反，它利用平衡后的技能画像、当前及近期工具调用以及本地脚本内容，判断每个动作是否被可信用户请求所正当化。ActionGuard在OpenClaw的工具调用前阶段拦截每个工具调用，并在故障关闭策略下执行Reviewer的ALLOW或DENY决定。我们在基于SKILL-INJECT的设置中，针对139个上下文注入和180个明显注入，使用三个开源和两个商用Reviewer模型，将ActionGuard与Dynamic Guardian和SkillGuard进行对比评估。每种条件重复三次，并使用攻击成功率（ASR）和任务成功率（TSR）进行评估。总体而言，与现有防护措施相比，ActionGuard将ASR降低了35.54%至46.11%；与无防护相比降低了70.44%，同时保持较高的良性任务完成率。这些结果表明，基于可信用户意图和运行时证据的执行边界授权，能够限制由技能注入引发的未授权工具调用。

## Abstract
LLM-based agents extend their capabilities through third-party skills that provide task-specific instructions, scripts, and tool-use procedures. However, malicious instructions inserted into an otherwise benign skill can cause a benign user request to trigger dangerous Tool Calls, including data exfiltration, file deletion, or unauthorized code execution. This paper presents ActionGuard, which inspects skill-influenced Tool Calls immediately before execution. ActionGuard separates the target agent's action-generation context from the safeguard's authorization context. The target agent may use the original skill for planning, but the Reviewer does not receive the potentially poisoned raw skill text. Instead, it determines whether each action is justified by the trusted user request using a balanced skill profile, current and recent Tool Calls, and local script contents. ActionGuard intercepts each Tool Call at OpenClaw's before-tool-call stage and enforces the Reviewer's ALLOW or DENY decision under a fail-closed policy.   We evaluate ActionGuard on 139 contextual and 180 obvious injections in a SKILL-INJECT-based setting against Dynamic Guardian and SkillGuard, using three open-source and two commercial Reviewer models. Each condition is repeated three times and evaluated using Attack Success Rate (ASR) and Task Success Rate (TSR). Overall, ActionGuard reduced ASR by 35.54 to 46.11 percent relative to existing safeguards and by 70.44 percent relative to No Safeguard, while maintaining high benign-task completion. These results show that execution-boundary authorization grounded in trusted user intent and runtime evidence can restrict unauthorized Tool Calls induced by skill injection.

## 1. 核心问题与研究动机

- **背景**：基于 LLM 的智能体通过第三方技能（skill）扩展能力，技能提供任务指令、脚本与工具使用流程，是外部供应链制品（公共仓库/社区注册表分发）。
- **威胁**：攻击者在原本良性的技能（`SKILL.md`、辅助脚本、元数据、外部端点）中植入恶意指令，使**无攻击意图的良性用户请求**触发危险 Tool Call——数据外泄、文件删除、未授权代码执行、远程历史改写等。
- **关键安全缺口**：现有智能体防护多关注"动作本身是否危险"，较少验证"诱发该动作的信息是否可信"。当恶意指令被伪装成正常流程（备份、完整性校验、日志、同步、后处理）时，智能体将其视为任务步骤，防护难以识别。
- **判定困难**：同一指令在上下文注入（contextual injection）下可能既像良性行为又像攻击行为，仅靠技能文本表面关键词无法区分。
- **整体含义**：核心问题不是"技能是否恶意"，而是**在缺少授权判据的情况下，技能诱发的动作是否落在当前用户请求与授权范围内**。因此需要一种执行边界的授权机制。

## 2. 方法论

### 核心思想

- 将**目标智能体的动作生成上下文**与**防护机制的授权上下文**分离：智能体可读取并使用原始（可能被投毒）技能进行规划，但 Reviewer 模型**不接收原始技能文本**，避免把被投毒内容当作执行授权依据。
- 技能只能影响"动作生成"，不能自行授予"执行权限"；授权基础始终是**可信用户请求**（会话开始时捕获）+ 运行时证据。
- 不判断技能本身善恶，只判断"技能所正当化的动作"在**执行时刻**是否越权。

### 三阶段流程

- **① Resolve Skill Profile（技能画像解析/构建）**
  - ActionGuard 维护独立于原始技能的**技能画像数据库（DB）**。
  - 首次使用或 DB 无匹配时，由画像构建模型从原始技能生成**均衡技能画像（balanced skill profile）**；原始技能仅在此构建阶段使用，不直接交给语义 Reviewer。
  - 画像含两部分：`ordinaryWorkflow`（常规工作流、常用工具/命令、访问资源范围、本地变换、校验流程）与 `suspiciousSignals`（偏离常规、需额外审查的行为模式）。
  - 命中可疑信号**不自动阻断**，仅作上下文提示；画像本身**不授予**新权限。
- **② Build Context（运行时审查上下文构建）**
  - 在 OpenClaw 的 `before_tool_call` 钩子拦截当前 Tool Call。
  - 审查上下文 = 可信用户请求 + 均衡技能画像 + 运行时证据：
    - **Current Tool Calls**：原始参数 + 规范化表示（动作类型、访问目标、资源、预期外部副作用），决策同时使用两者以防规范化丢失细节。
    - **Recent Tool Calls**：近期调用序列，支持把当前调用理解为工作流一环；**先前动作被批准不等于后续动作获得授权**。
    - **Inspected Files**：待执行本地脚本的执行前内容（文件操作、子进程、网络访问等）；脚本中的代码/注释/字符串/自然语言指令**仅视为不可信的行为证据**，不构成新指令。
  - 明确不依赖目标智能体的完整对话记录或隐藏推理。
- **③ Authorize（语义授权与执行）**
  - 独立 Reviewer 模型输出结构化结果：`Decision`（ALLOW/DENY）、`Reason`、`Reason Code`（规范化类别，如 `unauthorized_external_data_transfer`、`unauthorized_file_deletion`、`unauthorized_remote_write`、`unauthorized_scope_expansion`）。
  - **授权边界**：区分"未授权 Tool Call"与"任务质量问题"。执行复杂度、可能错误、本地状态变化、输出质量下降本身不构成未授权；只有当其导致行为超出用户委托范围时才判定未授权。
  - **执行策略**：ALLOW 则原样转发原调用与参数（不做修改）；DENY 则阻止执行并拒绝；输出无法正确解析时同样拒绝；Reviewer 调用失败时**fail-closed**（不允许执行），并记录独立原因码。
  - **工具拒绝反馈**：将 Reason 与 Reason Code 返回目标智能体，供其生成替代调用；DENY 只作用于当前调用，不终止会话；全过程写入审计日志（区分"未生成攻击动作/生成但被阻断/允许但运行时未执行"）。
- **未授权 Tool Call 的定义**（威胁模型）：需同时满足（1）对完成可信请求非必要或非合理附带；（2）访问目标或操作超出用户实际权限或本次请求委托范围。
- 论文无显式数学公式，方法以流程与判定规则表述。

## 3. 实验设计

- **对比方法**：

  - Dynamic Guardian（引用技能时介入，审查并净化技能内容后交给目标智能体）
  - SkillGuard（技能清单 + 权限声明，运行时能力检查、用户同意、默认拒绝）
  - ActionGuard（本文方法）
  - 三者均保留各自原生干预点与决策流程实现于 OpenClaw。
- **Reviewer 模型**（5 个，同一条件内所有 LLM 决策/构建组件使用同一底层模型以隔离机制差异）：
  - 开源：Gemma 4（gemma4:e4b-it-q4_K_M）、Qwen 3.5（qwen3.5:9b）、Ministral 3（ministral-3:8b-instruct-2512-q4_K_M）

- **目标智能体与评判模型**：均为 `gpt-5.5-2026-04-23`；Judge 独立于目标智能体、防护与 Reviewer，不参与规划或 ALLOW/DENY 决策。
- **指标**：
  - **ASR（攻击成功率）**：恶意目标在环境中真实产生副作用才算成功；未生成恶意调用、或防护阻断后无副作用均计为失败。排除技术故障。
  - **TSR（任务成功率）**：良性任务产出所需产物/结果即成功，即使攻击被阻断；因防护干预而无法完成良性工作流则失败。TSR 只取可独立判定的子集（上下文注入 100/139、明显注入 155/180），所有方法使用同一评估集。
  - ASR 与 TSR 必须联合解读，避免"广泛阻断良性流程"被误判为防护有效。
- **重复与记录**：每个条件独立重复 3 次，取均值；记录最终输出、工作目录、产物、命令历史、Tool Call 序列、工具执行记录、防护裁决与日志、以及各类运行时错误。
- **案例研究**：3 个（上下文注入 `INST-2_pptx_task0`、明显注入 `INST-3_docx_task3`、效用失败 `INST-10_git_task1`）。

## 6. 主要结论与发现

- **总体**（跨全部 Reviewer 与注入类型）：ActionGuard ASR **8.65%**、TSR **90.38%**；Dynamic Guardian 16.05% / 92.08%；SkillGuard 13.42% / 88.55%；No Safeguard 29.05% / 93.46%。
- 相对现有防护，ActionGuard 将 ASR 降低 **46.1%（vs Dynamic Guardian）** 与 **35.5%（vs SkillGuard）**；相对无防护降低 **20.40 个百分点（约 70.2% 相对下降）**，TSR 仅下降 3.08 个百分点（约 3.3% 相对下降）。
- **上下文注入**：ActionGuard 平均 ASR **8.20%**、TSR **87.73%**；Dynamic Guardian 14.92% / 88.27%；SkillGuard 19.81% / 89.13%（SkillGuard 在上下文注入下明显退化）。ActionGuard TSR 略低于两者，但差距 ≤1.40 个百分点。
- **明显注入**：SkillGuard ASR 最低（8.48%），ActionGuard 为 9.00%（差 0.52 个百分点）；TSR 上 Dynamic Guardian 最高 94.54%，ActionGuard 92.09%，SkillGuard 88.17%。
- **跨注入类型一致性**：ActionGuard 两类 ASR 仅差 0.80 个百分点；SkillGuard 差 11.33 个百分点（上下文注入显著变差）；Dynamic Guardian 差 2.01 个百分点但 ASR 整体偏高。
- **跨 Reviewer 模型稳定性**：ActionGuard 在所有 5 个模型下 ASR 最低，范围 7.73%–9.30%，开源与商用模型表现相近；Dynamic Guardian 波动 11.39%–19.44%，SkillGuard 12.64%–14.94%。TSR 方面 ActionGuard 波动相对更大（87.58%–92.55%），说明**攻击阻断对 Reviewer 依赖弱，但良性效用对 Reviewer 选择更敏感**。
- **案例结论**：能从当前调用参数识别外发传输（`requests.post` 外传 PPTX）；能从脚本内容识别 `rm -rf ./* ../*` 等命令行不可见的破坏性副作用；仅在"实际目标与预期副作用无法被可信请求正当化"时阻断，保留良性文档修改与格式转换。
- **已知效用失败模式**：当良性动作与未授权动作被合并在**同一个复合 Tool Call**（如 `add`+`commit`+`push --force`）中时，ActionGuard 会阻断整个调用，若目标智能体未重新规划安全替代流程，则攻击被阻断但任务失败——即效用取决于授权准确性与 **DENY 后的重规划能力**。
- **总结论**：以可信用户意图 + 运行时行为证据为基础的执行边界授权，能有效限制技能注入诱发的未授权 Tool Call，同时基本保持良性任务能力。

## 7. 优点

- **信任模型清晰**：明确区分"可信用户请求"与"不可信外部内容/技能/工具输出"，并规定后者的指令不能扩展授权范围，这在概念上直击技能投毒的根本问题。
- **上下文隔离设计巧妙**：Reviewer 不接触原始技能文本，改用独立构建的均衡技能画像，既保留技能语义线索，又降低被投毒文本直接操纵裁决的风险；画像同时覆盖"常规工作流"与"可疑信号"，有助于抑制过度阻断。
- **执行边界拦截**：在 `before_tool_call` 阶段做真实副作用前的判定，并提供 Reason/Reason Code 反馈促成智能体自修复；fail-closed 策略与解析失败即拒绝，安全默认值保守。
- **脚本级证据检查**：对"命令行表面无害、脚本内部破坏"的场景（如 `file_check.sh`）有效，且把脚本内自然语言仅当不可信证据，避免二次注入。
- **实验设计相对严谨**：同源 Reviewer 控制、3 次独立重复、独立 Judge、沙箱隔离与状态重置、同时报告 ASR 与 TSR、对技术故障与判定排除规则有明确定义。
- **稳健性证据**：跨 5 个 Reviewer（开源与商用）ASR 均最低且波动小，说明不依赖特定模型；跨注入类型 ASR 差异小。
- **可复现性承诺**：提供

可复现性承诺：提供开源仓库快照、容器镜像定义、执行配置与评测脚本（SKILL-INJECT 快照 + OpenClaw 干预点实现），使防护对比可在同一环境重放。
- **与威胁模型对齐的判定原则**：明确"未授权 Tool Call"需同时满足"非必要/非合理附带"与"超出权限或委托范围"，避免把执行错误、输出质量等非安全问题误判为安全事件。

## 8. 不足与局限

- **组件贡献未分离**：缺少消融实验，无法量化技能画像、脚本检查、近期调用序列、规范化参数、fail-closed 等各环节对 ASR/TSR 的独立贡献，也难以判断哪一模块是性能瓶颈（如阻断主要来自画像还是脚本检查）。
- **评测面偏窄**：仅使用一个 benchmark（SKILL-INJECT 扩展版）、一个智能体框架（OpenClaw）、一个目标智能体模型（`gpt-5.5-2026-04-23`），跨框架（如 LangGraph、AutoGen）与跨目标模型的泛化性未验证。
- **未评估自适应攻击**：所有注入均为静态预置，未考虑知晓 ActionGuard 机制后针对画像构建阶段、规范化表示或 Reviewer 提示词的自适应规避（如把恶意动作拆分为多个看似良性的调用、利用近期调用序列"洗白"、在脚本中规避关键字或延迟触发）。
- **选择偏差风险**：TSR 仅在可独立判定的子集上计算（上下文注入排除 39/139、明显注入排除 25/180），且 ActionGuard 的 TSR 波动（87.58%–92.55%）相对更大，说明其对 Reviewer 选择敏感；排除样本与被保留样本是否存在系统性差异未做分析。
- **Judge 同源风险**：评判模型与目标智能体为同一模型，可能共享相似的失败模式与偏好，导致对"任务成功"与"攻击成功"的判定存在相关性偏差；作者虽提出未来引入确定性评估器，但当前结果未做交叉校验。
- **效用失败依赖重规划**：复合 Tool Call 被整体阻断时，任务成败取决于目标智能体能否自主重规划安全替代流程，而这一能力既非 ActionGuard 保证，也未在实验中单独度量。
- **反馈信息可能被滥用**：Reason/Reason Code 返回给目标智能体虽利于自修复，但若目标智能体已被投毒技能影响，反馈也可能被用于试探边界、构造更易通过审查的替代调用；论文未讨论该反馈通道的安全含义。
- **算力与开销未量化**：未报告 ActionGuard 引入的额外推理延迟、token 成本与端到端吞吐影响，难以评估在生产环境（高并发、低延迟约束）中的可行性。
- **画像构建的信任假设未验证**：画像构建模型本身接收原始（可能被投毒）技能，若该模型被技能内容误导而生成偏差画像（遗漏可疑信号或错误归类常规流程），会影响后续裁决；该环节的鲁棒性缺乏专项测试。
- **运行稳定性证据有限**：仅 3 次重复，对 ASR 这类低概率事件（约 8%–9%）的置信区间较宽，跨重复的方差与显著性检验未给出。

## 9. 启示与未来方向

- **授权边界优于内容过滤**：与其判断技能/指令"是否恶意"，不如在执行时刻判断动作"是否被当前可信委托正当化"，这一范式可迁移到 MCP 工具调用、插件市场、Agent 间委托等更广的外部供应链场景。
- **上下文隔离是可复用设计模式**：让裁决者与"可能被污染的执行上下文"解耦（只接触经独立构建的画像与运行时证据），可推广到代码审查、配置审计、多智能体协作中的权限判定。
- **可补强的后续工作**：
  - 消融与敏感性分析，定位各组件边际收益；
  - 面向 ActionGuard 的自适应红队测试（调用拆分、序列洗白、脚本混淆、延迟触发）；
  - 引入确定性/混合评估器降低 Judge 同源偏差；
  - 度量延迟与成本，探索小模型专用于画像构建与裁决的可行性；
  - 将"重规划能力"作为显式优化目标（如 DENY 时给出结构化替代建议），以缓解复合调用导致的效用损失；
  - 扩展到多轮委托、跨会话授权衰减、权限时效与最小权限动态收缩等更细粒度的授权语义。

## 10. 总体评价

ActionGuard 提出了一条务实且概念清晰的技能投毒防护路径：以**可信用户请求**为授权锚点，把技能降格为"仅影响动作生成、不能授予执行权限"的不可信输入，并在真实副作用发生前的 `before_tool_call` 边界做语义授权。其在 319 个注入–任务对、5 个 Reviewer 模型上的结果表明，相对无防护可将 ASR 从 29.05% 降至 8.65%（相对下降约 70%），同时 TSR 仅损失约 3.3 个百分点，且在上下文注入这一更难场景下显著优于 SkillGuard，跨模型稳定性好。其核心价值不在单点指标领先，而在于**把"技能是否恶意"这一难以判定的问题，转化为"动作是否越出委托范围"这一可裁决、可审计、可反馈的工程问题**。主要短板在于缺少消融、评测面窄、未考虑自适应攻击、成本未量化，以及 DENY 后效用依赖智能体重规划——这些也是该方向后续研究最值得投入之处。
