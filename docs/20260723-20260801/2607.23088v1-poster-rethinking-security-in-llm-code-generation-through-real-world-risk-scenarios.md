## 摘要
大型语言模型（LLM）被广泛用于代码生成，但它们在现实开发工作流程中的安全行为仍未得到充分探索。现有的基准测试通常依赖明确指定的安全要求，未能捕捉到提示词经常模糊或不完整的真实场景。在本文中，我们采用以开发人员为中心的视角，识别出三个常见的导致LLM生成代码安全漏洞的典型风险场景：需求模糊、操作上下文说明不足以及安全与功能性冲突。基于这些场景，我们构建了一个包含2,700个测试用例的大规模基准测试，能够在现实条件下对LLM安全性进行细粒度评估。对八种最先进的LLM进行的广泛评估显示，所有模型在各风险场景中的平均漏洞率均超过56%。我们进一步证明，安全感知的提示词设计可以显著降低这些风险，最多可提高45%。

## Abstract
Large Language Models (LLMs) are widely used for code generation, yet their security behavior in realistic development workflows remains underexplored. Existing benchmarks often rely on explicitly specified security requirements, failing to capture real-world scenarios where prompts are frequently ambiguous or incomplete. In this paper, we adopt a developer-centric perspective and identify three representative risk scenarios that commonly lead to security vulnerabilities in LLM-generated code: Ambiguous Requirements, Under-Specified Operational Context, and Security--Functionality Conflict. Based on these scenarios, we construct a large-scale benchmark comprising 2,700 test cases, enabling fine-grained evaluation of LLM security under realistic conditions. Extensive evaluation of eight state-of-the-art LLMs reveals that all models exhibit average vulnerability rates exceeding 56\% across risk scenarios. We further demonstrate that security-aware prompting can substantially mitigate these risks, achieving up to 45\% improvement.

## 2. 论文提出的方法论

### 核心思想
- 采用“风险场景”而非传统“漏洞类型”作为评估切入点，关注**提示词侧的风险条件**如何影响 LLM 的安全行为。
- 设计配对提示（风险提示 vs. 安全感知提示），在保持功能意图一致的前提下，控制安全相关信息的变化，从而实现受控比较。

### 三类风险场景
1. **SC1 需求模糊（Ambiguous Requirements）**：用户给出模糊的功能描述，未指定安全约束，LLM 可能默认生成不安全实现。例如“实现一个登录 API”但没有说明密码保护、认证策略等。
2. **SC2 操作上下文说明不足（Under-Specified Operational Context）**：提示词缺少部署环境、框架版本、运行时约束等关键信息，LLM 可能默认采用过期或不安全的配置。例如“实现一个文件上传服务”但未说明是公网暴露还是内网部署。
3. **SC3 安全–功能冲突（Security–Functionality Conflict）**：用户要求的功能与安全最佳实践相悖，LLM 需要权衡显式功能需求与隐式安全约束。例如要求禁用证书校验或本地存储凭据。

### 基准构建方式
- 构建 **2,700 个测试用例**，覆盖 3 个场景 × 9 种编程语言 × 50 对提示词（每对包含一个风险提示和一个安全感知提示）。
- 9 种语言覆盖多种开发领域：脚本（Bash）、前端（HTML/JavaScript）、后端（C++/Java/PHP/Go/SQL）、AI 开发（Python）。
- 提示词来源于 GitHub issues、Stack Overflow 帖子、匿名内部开发日志，并辅以按 CWE 类别设计的人工提示词以增强覆盖率。

### 评估框架（两轮）
- **基线轮**：使用风险提示生成代码，测量天然安全行为。
- **缓解轮**：使用安全感知提示生成代码，测量提示增强的效果。
- 安全感知提示由场景特定的转换规则生成：SC1 注入一般安全指导；SC2 补充环境假设与安全约束；SC3 将功能意图重构为符合安全编码原则的规范。

### 漏洞判定
- 使用静态分析工具（Clang Static Analyzer、CodeQL），并辅以 GPT-5 协助的专家审查；
- 最终由专家给出二元标签 \( b \in \{0,1\} \)（0 = 易受攻击，1 = 安全）。

### 指标定义
- **漏洞率**：\( Vul = \frac{1}{N}\sum I(b=0) \)，分别计算基线（\(Vul_B\)）和缓解（\(Vul_M\)）条件下的漏洞率。
- **安全改进（\(Imp\)）**：基线有漏洞且缓解后安全的比例。
- **回归率（\(Reg\)）**：基线安全但缓解后出现漏洞的比例。
- **净安全增益（\(NetG\)）**：\( NetG = Imp - Reg \)，衡量安全感知提示的整体净收益。

## 3. 实验设计

### 评估模型

- **2 个小规模模型**：Qwen3-4B、GLM-Z1-Air，用于考察模型规模对安全行为的影响。

## 6. 论文的主要结论与发现

- **RQ1 结论**：所有 8 个被评 LLM 在真实风险场景下的基线漏洞率均超过 **56%**，说明 LLM 缺乏默认安全（security-by-default）行为；
- **场景差异**：需求模糊（SC1）漏洞率最高，达 **66%**；安全–功能冲突（SC3）漏洞率相对最低，为 **52%**，表明显式的功能-安全权衡可能促使模型采取更谨慎的生成行为；
- **RQ2 结论**：安全感知提示对所有模型都有效，漏洞率降低幅度在 **37%–45%** 之间，其中 Claude-Sonnet-4 提升最大（45%），Qwen3-4B 提升最小（37%）；
- **场景难点**：SC3（安全–功能冲突）是最难缓解的场景，回归率高达 **19%**，净安全增益 \(NetG\) 降至 **0.12**，说明当功能需求与安全实践冲突时，安全提示的鲁棒性有限。

## 7. 优点
