## 摘要
理解大型代码库对大型语言模型（LLM）智能体而言是一项长时程任务：回答单个问题可能需要构建并运行软件、跨文件追踪执行流程，并在数十分钟内综合证据。在SWE-Atlas QnA（一个面向生产仓库长时程问题的基准）上，单个Claude Code智能体（Opus 4.6）仅能解决32.3%的任务。在清晰的上下文中划分工作给多个智能体可缓解这一局限。然而，代码理解的子任务相互依赖：一个智能体的发现可能改写另一个智能体的任务，因此智能体必须在执行过程中协调，而不仅仅在阶段边界。现有的大规模多智能体系统仅在阶段之间支持此类交换，形式为分阶段交接或同步轮次。通信与工作仍然互斥：执行中途的发现要等到下一个边界才能共享。我们提出AgentRadio，一个异步消息传递层，为编码智能体框架提供三种原语：线程、消息和等待提及。其中等待提及作为后台任务运行，在不打断前台工作的情况下呈现队友消息，使每个智能体被动感知同伴并将新发现融入进行中的任务。在包含分工与协商的五阶段协议下，由AgentRadio组织的四个智能体解决了62.1%的任务，比单个智能体高出29.8个百分点，也优于使用更新版Opus 4.8的Claude Code（57.2%）。评分标准层面的分析显示，增益随任务难度增加而增加，与中期修正作为潜在机制一致。我们的代码可在 https://github.com/Coral-Protocol/AgentRadio 获取。

## Abstract
Understanding large codebases is a long-horizon task for Large Language Model (LLM) agents: answering a single question can require building and running the software, tracing execution across files, and synthesizing evidence over tens of minutes. On SWE-Atlas QnA, a benchmark of long-horizon questions over production repositories, a single Claude Code agent (Opus 4.6) resolves only 32.3% of tasks. Dividing the work among agents with clean contexts mitigates this limitation. However, the subtasks of code comprehension are interdependent. One agent's findings can rewrite another's task, so agents must coordinate during execution, not only at phase boundaries. Existing multi-agent systems support such exchange only between phases, through staged handoffs or synchronized rounds. Communication and work remain mutually exclusive. A discovery made mid-execution cannot be shared until the next boundary. We present AgentRadio, an asynchronous message-passing layer that equips coding-agent harnesses with three primitives: threads, messages, and waiting for mentions. The last runs as a background task, surfacing teammates' messages without interrupting foreground work, so each agent remains passively aware of its peers and folds new findings into its ongoing task. Under a five-phase protocol of division of labor and negotiation, four agents organized by AgentRadio resolve 62.1% of tasks, 29.8 points above a single agent and above Claude Code with the newer Opus 4.8 (57.2%). Rubric-level analysis shows the gain growing with task difficulty, consistent with mid-course correction as the underlying mechanism. Our code is available at https://github.com/Coral-Protocol/AgentRadio.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **长时程任务的兴起**：LLM Agent 面临的任务越来越长，从单步问答扩展到软件工程、研究复现等。据估计，前沿智能体能完成的软件任务长度大约每七个月翻倍。
- **单智能体的瓶颈**：在 SWE-Atlas QnA 基准（针对生产代码库的长时程理解任务）上，单个 Claude Code 智能体（Opus 4.6）只能解决 32.3% 的任务。原因在于：智能体的有效注意力随上下文增长而退化，而代码库理解任务往往需要跨文件追踪、构建运行软件、综合证据，单个上下文难以容纳全部信息。
- **多智能体分工的天然直觉**：将任务分配给多个智能体，各自使用干净的上下文，可以缓解上下文坍缩问题。但难点在于**子任务并非相互独立**——一个智能体的发现可能重塑另一个智能体的工作方向，因此智能体必须在执行过程中实时协调。
- **现有系统的根本缺陷**：论文指出，现有多智能体系统的通信与工作互斥（communication and work remain mutually exclusive），主要有三类模式：
  - 并行但隔离（如 Anthropic 研究系统）；
  - 并行但按轮同步（round-synchronized，如辩论系统）；
  - 仅限相邻形式的异步（如任务队列、共享内存但需主动读取）。
  
  这些系统**无法让正在工作的智能体同时“倾听”同伴**。因此，执行中途的发现无法及时传达到队友那里。

- **核心问题**：能否让并发工作的智能体之间实现“被动感知”（passive awareness），即在不中断前台工作的前提下，将队友的关键发现实时融入当前任务？

## 2. 方法论

### 核心思想

论文提出 **AgentRadio**——一个异步消息传递层（asynchronous message-passing layer），使编码智能体框架获得三种原语，其中最关键的是将**等待提及**作为后台任务运行，从而把非阻塞式消息传递转化为“被动感知”。其类比是：广播如同司机在开车时收听电台，手不离开方向盘，消息自然浮现。

### 三种通信原语

1. **create_thread(name, participants)**：在消息服务器上创建一个命名对话线程，返回标识符。
2. **send_message(thread, content, mentions)**：向线程追加消息，立即返回，无论是否有人监听；消息可通过 @ 提及特定智能体。
3. **wait_for_mention(timeout)**：阻塞直到收到提及本智能体的消息，返回该消息及所有线程的完整快照，无需二次读取。

关键在于 wait_for_mention 的执行位置：
- **前景（foreground）**：阻塞式接收，智能体为听而停止工作（作为阻塞基线）；
- **后台（background）**：变为被动感知，智能体继续工作，消息在下一步边界浮现。

形式化表述：若智能体运行为步骤序列 s1, s2, ...（每步一次工具调用），M(t) 为第 t 步可见的队友消息集合。阻塞接收使每次监听都消耗一个步骤，而被动感知使 M(t) 包含所有在 s_t 之前发送的消息，且无需任何“监听步骤”的开销。

### 五阶段协议（算法流程）

- **P1 探索（Explore）**：每个智能体独立探索仓库，草拟子问题；后台 watcher 启动。
- **P2 分工（Divide）**：组装者（agent-1）打开规划线程；智能体汇集发现，协商子问题划分，直到所有智能体批准。
- **P3 执行（Execute）**：各智能体独立工作；当发现影响队友、与计划矛盾、或遇到障碍时立即发布到 worklog。
- **P4 审查（Review）**：各智能体在结果线程发布带证据的发现；冲突、证据不足、遗漏观察触发审查消息；必要时可重开 P3。
- **P5 提交（Submit）**：组装者基于批准的结果草拟最终答案，经全部批准后提交。

核心对比：阻塞接收下 P3 阶段“静默”，发现只能等到 P4 才能共享；被动感知则让发现“即时广播”。

### 实现细节

- 消息服务器：独立进程，存储线程/消息/提及。
- 客户端：三个薄 shell 脚本。
- 对 harness 要求极低：只需支持后台运行 shell 命令（主流 harness 已具备），harness 本身无需修改。
- **无额外 LLM 调用**：切换通信模式不增加 token 开销（watcher 是操作系统进程而非 agent 步骤）。

- 评分严格：每个任务平均 12.3 条 rubric，每条都是原子化事实陈述，需经两轮人工审查和三名专家多数票；全部 rubric 通过才计为任务解决；修改源文件即失败。

| 配置 | 含义 |

## 6. 主要结论与发现

1. **核心成果**：4 个 Opus 4.6 智能体在 AgentRadio 下解决 62.1% 的任务，比单智能体（32.3%）高 29.8 个百分点（相对提升 92%），**且超过**使用更新模型 Opus 4.8 的单个 Claude Code（57.2%）。
2. **每一层都有帮助**：分工（+7.2）、协商（+12.1）、被动感知（+10.5），在 DeepSeek 上同样成立（+2.4、+8.1、+11.3）。
3. **被动感知是统计显著的**：两个模型上的 McNemar 检验均 p<0.01。
4. **结构优于算力**：完整系统远超计算量匹配的 best-of-6 采样（62.1% vs 37.9%）；被动感知仅增加约 25% 的花费却带来 10+ 点的提升。
5. **增益随任务难度增长**：对 L2 错过 5 条 rubric 的任务，被动感知每任务多恢复 2.0 条 rubric；对错过 1 条的任务仅恢复 0.3 条。这暗示**中期纠正**（mid-course correction）是核心机制。
6. **Rubric 层面的净增益**：被动感知净增 +24 条 rubric（+47 得 / -23 失），说明消息也可能带来干扰，但收益大于代价。
7. **类别差异**：架构和系统设计类问题获益最大（+15 任务），因为该类问题最易跨分工边界。

## 7. 优点

- **概念清晰**：“被动感知” vs “阻塞接收”的单比特差异被严格定义、精确测量，避免了多因素混杂。
- **工程侵入性极低**：不改 harness、不增加 LLM 调用、不要求智能体角色的复杂编排，一个后台进程即可实现，实用价值高。
- **实验设计严谨**：五级阶梯式消融配对比较；计算量匹配的 B1 控制预算；双模型验证；统计检验充分。
- **分析层次深入**：从任务级、rubric 级、难度分层到具体案例的多粒度分析，不仅指出“有效”，还揭示了“在什么条件下有效、为何有效”。
- **失效模式也有讨论**：Grafana 案例如实呈现被动感知无法弥补智能体集体盲区（没有人形成“不自动选择”的否定性结论），体现了客观性。
- **经济性报告**：明确透明的成本对比，为实际部署提供参考。

## 8. 不足与局限

- **未报告硬件资源**：没有 GPU 型号、数量、推理基础设施等信息，限制了可复现性和成本评估的完整性。
- **单次运行问题**：主实验每个配置仅运行一次，虽然方差子集显示排序稳定，但 124 任务上的单次结果仍可能受随机性影响。
- **成本高企**：完整配置花费约为单智能体的 6 倍（$19.45/任务），虽然在任务准确率上值得，但大规模部署可能不经济。
- **可泛化性存疑**：仅在 SWE-Atlas QnA 一个基准上验证；论文引用了 Kim et al. 关于任务可分解性的理论，但没有在更多任务族（如顺序任务、生成式任务）上检验被动感知的边界条件。
- **无法创造新知识**：Grafana 案例说明，AgentRadio 只能传导智能体已经形成的发现，无法帮助团队跳出集体盲区。
- **消息噪声的代价未充分分析**：被动感知净损失 23 条 rubric，论文未深入讨论什么类型的消息造成干扰、能否过滤。
- **协议固定性**：五阶段协议是人为设定的，未探讨不同协议（如更少或更多阶段）下被动感知的收益变化。
- **单通道**：只测试了 4 个智能体的配置，没有研究规模扩展（更多智能体是否会增加消息噪声超过收益阈值）。
- **跨模型比较的局限**：与 Opus 4.8 的对比虽是亮点，但并非受控实验（不同模型、不同时间点），只能作为参考。
