## 摘要
LLM智能体日益依赖外部工具，这扩展了能力，同时也创造了新的安全边界：第三方工具可能在接口层面看似良性，但在实现中嵌入不安全行为。现有防御依赖于弱元数据，将特征描述与策略判断合并为单一决策，或采用缺乏确定性、可审计推理的启发式/LLM强制执行，无法对任务上下文和多工具组合进行推理。本文提出了ToolGuardian，一个策略驱动的框架，通过预准入审查和任务感知的运行时授权来保障智能体-工具交互的安全。ToolGuardian使用渐进式特征化将证据转换为结构化事实：描述捕获声明意图，系统调用轨迹暴露粗略行为，模拟执行揭示观察到的效果，源码分析识别潜在行为。ToolGuardian的核心贡献是基于答案集编程（ASP）的声明式策略层，该策略层显式地对能力、效果、任务上下文和组合进行推理。我们使用相同的输入和输出契约，将ASP与启发式和基于LLM的策略实现进行了比较。我们在16个MCP风格工具（包括8个源自真实开源工具的恶意变体）和20个运行时场景上评估了ToolGuardian。对于审查，ASP利用描述、系统调用和观察效果证据，达到了0.86的拒斥类F1分数和88%的准确率。对于运行时授权，完全规范的实现正确分类了所有场景，而消融实验表明，移除组合和一致性规则会显著降低性能。

## Abstract
LLM agents increasingly rely on external tools, expanding capability while creating a new security boundary: third-party tools may appear benign at the interface level while embedding unsafe behavior in implementation. Existing defenses rely on weak metadata, collapse characterization and policy judgment into a single decision, or use heuristic/LLM enforcement that lacks deterministic, auditable reasoning over task context and multi-tool composition.   This paper presents ToolGuardian, a policy-driven framework for securing agent-tool interactions through pre-admission vetting and task-aware runtime authorization. ToolGuardian uses progressive characterization to convert evidence into structured facts: descriptions capture declared intent, system-call traces expose coarse behavior, mock execution reveals observed effects, and source analysis identifies latent behavior. ToolGuardian's core contribution is an Answer Set Programming (ASP)-based declarative policy layer that reasons explicitly over capabilities, effects, task context, and composition. We compare ASP against heuristic and LLM-based policy realizations using identical inputs and output contracts.   We evaluate ToolGuardian on 16 MCP-style tools, including 8 malicious variants derived from real open-source tools, and 20 runtime scenarios. For vetting, ASP reaches a deny-class F1 of 0.86 and 88% accuracy using description, syscall, and observed-effect evidence. For runtime authorization, fully specified realizations classify all scenarios correctly, while ablations show that removing compositional and conformance rules substantially degrades performance.

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 整体架构
ToolGuardian 位于 LLM 智能体与外部工具之间，分为四个阶段：工具特征化、事实生成、策略评估、强制执行，支持两种互补的强制阶段。

### 2.2 渐进式特征化（Progressive Characterization）
将异构证据组织为四个累加层：
- **L0（描述特征化）**：从工具描述、README、API 规范中提取声明功能。该证据由工具提供方供应，视为不可信。
- **L1（系统调用特征化）**：通过系统调用迹线观察粗粒度的 OS 交互（文件读写、网络访问、进程执行）。缺乏应用层语义（如区分正常 API 访问与隐蔽外泄）。
- **L2（模拟执行与观察效果）**：在受控环境中以代表性输入和模拟外部依赖执行工具，记录出站请求、访问的数据类别、命令调用和状态更改。可覆盖有限，未测试分支不可见。
- **L3（静态源码分析）**：使用 AST 分析工具实现，识别未在动态执行中出现的潜在行为（条件分支、隐藏端点、危险 API 组合）。可能过度近似（误报不可达代码），对闭源二进制不可用。

### 2.3 效果一致性（Effect Conformance）
将 L0 声明与 L2 观察效果做对比，检测不一致之处（如未声明的网络通信、意外的敏感数据访问、静默状态变更等），作为策略事实输出，由策略层决定是拒绝、限制还是警告。

### 2.4 事实表示（Fact Representation）
所有特征化输出规范化为公共事实词汇表，示例：
```
capability(T, network_access).
data_access(T, env_vars).
observed_http_post(T, Endpoint).
modifies_remote_state(T, github_issue).
effect_mismatch(T, undeclared_network_access).
```
同一事实词汇表同时用于工具审查与运行时授权。运行时额外结合任务级事实（如任务允许哪些网络访问、敏感数据处理、状态修改权限）。

### 2.5 策略框架（Policy Framework）
- **政策模型**：两个阶段——工具审查（准入决策）与运行时授权（特定调用是否允许）。
- **设计原则**：最小权限、零信任、能力导向访问控制、信息流限制。
- **审查策略**：四种输出——拒绝、受限准入、警告准入、无限制准入。硬拒绝规则针对隐蔽网络通信、未授权代码执行、破坏性文件系统活动等症状组合。
- **运行时策略**：考虑能力授权、效果授权、声明-观察行为一致性、多工具交互风险。可阻断"单独合理、组合危险"的调用序列。

### 2.6 三种策略实现（Policy Realizations）
为公平比较，所有实现使用相同输入与相同输出契约（决策结果 + 解释标签 + 可选限制标注）：
- **ASP 实现**：用 Clingo 求解器，编码拒绝条件、异常、效果一致性检查、组合约束为显式规则。确定性、可审计。
- **LLM 实现**：使用 openai/gpt-oss-120b（通过 OpenRouter 访问，temperature=0），通过提示词解释结构事实与策略指令。
- **启发式实现**：确定性风险评分、阈值和手写条件判断的 Python 基线代码。

## 6. 主要结论与发现

### 6.1 审查（Vetting）方面
- **最佳审查性能出现在 P2 层**（描述 + 系统调用 + 观察效果）：ASP、启发式、LLM 三种实现均达拒斥类 F1=0.86、准确率 88%。
- **特征化深度并非单调增益**：P0→P1→P2 改进检测，但 P3（静态分析）暴露良性高能力工具的强组合，导致过度拦截——ASP 和 LLM 各硬拒绝 2 个良性工具，启发式硬拒绝 5 个。
- **启发式**在 P3 实现恶意工具 100% 召回（8/8），但以 5 个良性工具误拒为代价；ASP 与 LLM 更能平衡安全-效用权衡。

### 6.2 运行时授权方面
- **完全规范的三种实现均在 20/20 场景全部正确**（12 原子 + 8 组合全对）。
- **消融实验结果**：
  - LLM 提示词消融：准确率从 100% 降至 75%（F1 从 1.00 降至 0.84），出现 4 个误拒和 1 个漏拒——说明结构事实本身不足，显式策略指引必不可少；
  - 启发式去除组合推理：准确率降至 80%，4 个组合拒斥场景被漏放；
  - 启发式进一步简化：准确率降至 60%，出现 2 个原子误拒和 6 个组合漏拒。
- **结论**：原子授权不难，困难的是组合推理；ASP 天然适合表达多条件组合约束（源-汇关系、敏感读取+外部更新）。

### 6.3 其他发现
- **LLM 性能高度依赖提示词质量**：在结构化输入与显式指引下表现良好，但从独立安全权威的角度看并不可靠；
- **部分干预（受限准入）是重要中间态**：二分指标无法体现操作性限制的价值；
- **ASP 的工程成本从运行时转移到策略编写**：策略规范成为可审查、可测试、可修改的具体产物。

## 8. 缺点与局限性

### 8.1 实验语料规模有限
- 仅 16 个工具、20 个运行时场景，且为研究者自行构造的受控基准，无法代表 MCP 生态中工具类型的多样性和恶意行为的丰富变体。
- 恶意变体是从良性工具直接修改而来，保留了公开接口；真实恶意工具可能更隐蔽或更复杂，导致评估结果可能低估实际难度。

### 8.2 场景与策略规则共同设计
- 运行时场景（尤其是组合场景）是基于已有的策略规则模板生成的，相当于“为验证规则而设计场景”，存在一定循环论证风险。实际部署中可能遇到规则未覆盖的新兴攻击模式，效果会打折。

### 8.3 L3 静态分析的实际约束
- L3 层仅适用于开源、可解析的工具源码；对闭源二进制或混淆代码无法生效。
- 静态分析可能产生大量误报（不可达代码、条件分支），在论文中直接导致 P3 层误拒良性工具，说明该层证据的“分辨率”仍需改进。

### 8.4 策略编写与维护成本
- ASP 策略虽然可审计，但规则编写需要专业逻辑编程知识，普通开发者难以直接维护。
- 策略的覆盖面依赖于人工定义的症状模式与例外规则；若需适应新工具类型，需手动扩展事实词汇表与规则，缺乏自适应学习能力。

### 8.5 对 LLM 对照实现公平性的质疑
- LLM 实现的性能高度依赖提示词工程，论文通过精心构造提示词（包含显式规则表与组合风险表）才能达到 100% 准确率；消融后性能大幅下降。这暗示其结论更多是“提示词工程的能力”，而非 LLM 本身的安全推理能力。
- 使用单一模型（gpt-oss-120b）难以评估不同 LLM 的泛化情况。

### 8.6 缺少对抗性自适应评估
- 论文中恶意工具是静态的，未考虑攻击者会根据防御机制动态调整恶意行为（如规避特定系统调用特征、伪装成良性工具行为），因此对真实世界高级威胁的防御效果未得到充分验证。

### 8.7 部署集成层面信息不足
- 论文未详细说明 ToolGuardian 如何集成到现有 LLM 智能体框架中运行时的性能开销、误判概率对用户体验的影响，以及与 MCP 协议兼容层的具体实现。

## 9. 个人见解与启发

### 9.1 最重要的启示
ToolGuardian 的价值不在某个具体技术（ASP 或特征化）的胜负，而在于它重新定义了智能体工具安全的问题边界：安全决策应基于“经过验证的事实”，而非“工具自述的声明”。将特征化（fact gathering）与策略（fact reasoning）解耦，使安全机制具备了模块化、可审计和可演进的能力。这一点对当前 MCP 生态的野蛮生长具有直接指导意义——平台方应当建立类似“工具体检 + 运行时权限”的双层机制，而不是仅依赖工具市场的评分或下载量。

### 9.2 关于 ASP 的思考
ASP 在该任务中的表现证明，逻辑编程在处理“确定性、多条件约束、组合灾难模式”时仍具独特优势。相比 LLM，ASP 没有幻觉风险、输出稳定、可解释性强，且能被静态验证。但这种优势的前提是事实库质量足够高。如果特征化层能输出噪声很大的事实（例如 L3 静态分析），ASP 同样会被带偏。因此，未来研究不应只优化策略层，更应关注证据层的置信度建模，例如为事实附加可信度权重或概率，再交给逻辑推理层处理。

### 9.3 关于 LLM 在安全决策中的角色
LLM 实现的失败消融说明了一个尖锐问题：当安全策略明确编码成规则文本时，LLM 可以像一个“规则解释器”那样运行；但一旦离开显式指引，它的安全判断就不可靠。这提示我们，将 LLM 用作主要的授权决策者，在安全关键场景中是短视的。更合理的角色可能是“实体抽取者”或“高层意图解析者”，将任务意图转化为结构化事实，然后交给确定性策略引擎裁决。可惜论文未充分探索这种“LLM + ASP”混合架构，未来值得研究。

### 9.4 对工程实践的启发
- 工具提供方应在交付时附带声明文件（capability manifest），但必须经过运行验证，不能盲目信任；
- 运行时监控应是“任务感知”的，不仅看单个调用是否合规，还要看跨调用的数据流（如“读敏感数据 → 外发”），这需要类似信息流控制的抽象；
- 安全策略应当是代码资产的一部分，纳入 CI/CD 版本管理，ASP 规则正好满足这一点（可 diff、可测试、可评审）。

### 9.5 与现有研究的衔接
论文在智能体安全框架上与“Agent Security”相关研究（如 AgentPoison、ToolPoison）互补：那些工作更多关注输入污染的免疫力，ToolGuardian 关注工具本身的恶性行为。未来的统一安全模型可能同时包含“工具审查 + 输入净化 + 运行时授权 + 行为日志审计”等多个防线，本文为其中最关键的一环——执行前和执行中的策略层——提供了扎实的设计范例。

### 9.6 总结性评价
这篇论文在思想上是稳健的，在工程上是可落地的，虽然实验规模偏小，但验证了核心机制的有效性与可组合性。特别值得称道的是作者主动披露了三种实现各自的劣势，并没有神话任何一种方案。对于想构建生产级 MCP 安全网关的研究者或工程团队，该文是一份非常有价值的蓝图。
