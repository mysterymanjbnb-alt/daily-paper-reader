## 摘要
大型语言模型（LLM）正越来越多地被部署为代理，在多个步骤中与有状态环境交互：收集隐藏信息、组合工具调用并提交状态更改。我们将这种能力称为多步骤工具使用。现有基准测试推动了工具使用代理评估的发展，但往往侧重于孤立的API调用、短轨迹或难以扩展或控制的设置。我们引入了E-Bench，这是一个完全合成的基准测试，包含三个产品领域的323个状态更改任务：王者荣耀、QQ音乐和腾讯会议。E-Bench将环境合成与任务合成解耦：图引导的数据库填充构建了可重用、无孤岛的产品环境，而生成器-求解器不对称性则创建了同时具有信息差距和工具差距的任务，要求代理在更改状态之前发现隐藏数据并组合多个工具调用。结果通过数据库状态差异以确定性方式评分。由于环境和任务都是合成的，E-Bench在环境层面可控，在任务层面可扩展。对11个前沿LLM的基准测试表明，多步骤工具使用仍然具有挑战性：最强模型的Pass^3保持在60%以下，即使在E-Bench-Code扩展中执行代码，可靠性（Pass^3）仍低于70%。

## Abstract
Large Language Models (LLMs) are increasingly deployed as agents that interact with stateful environments over multiple steps: gathering hidden information, composing tool calls, and committing state changes. We refer to this capability as multi-step tool use. Existing benchmarks have advanced tool-use agent evaluation, but often focus on isolated API calls, short trajectories, or settings that are difficult to scale or control. We introduce E-Bench, a fully synthetic benchmark with 323 state-changing tasks across three product domains: Honor of Kings, QQ Music, and Tencent Meeting. E-Bench decouples environment synthesis from task synthesis: graph-guided database filling builds reusable, orphan-free product environments, while generator-solver asymmetry creates tasks with both an information gap and a tool gap, requiring agents to discover hidden data and compose multiple tool calls before changing state. Outcomes are graded deterministically by database-state diffs. Since both environments and tasks are synthetic, E-Bench is controllable at the environment level and scalable at the task level. Benchmarking 11 cutting-edge LLMs shows that multi-step tool use remains challenging: Pass^3 stays below 60% for the strongest models, and even with code execution in the E-Bench-Code extension, reliability (Pass^3) remains below 70%.

# E-Bench 论文总结

## 1. 核心问题与研究动机

- **背景**：LLM 正从“回答问题”转向“作为智能体与环境交互”，需要在多步骤中收集隐藏信息、组合工具调用、提交状态更改，即**多步骤工具使用（multi-step tool use）**。
- **现有基准的不足**：
  - 多聚焦于孤立 API 调用、短轨迹或静态 QA，未覆盖部分可观测性、异构工具、长程依赖和精确状态变更。
  - 基于真实系统的基准难以扩展、成本高、存在数据安全/隐私问题，且随服务演化不复现不稳定。
  - 真实任务容易造成数据污染，模型可能依赖先前见过的公共事实，而非主动通过工具获取隐藏状态。
- **本文目标**：构建一个完全合成、可控、可扩展、可确定性评估的多步骤工具使用基准，衡量智能体在真实产品场景中的信息获取、工具编排和状态修改能力。

## 2. 方法论

### 2.1 总体设计：环境合成与任务合成解耦

- 先为每个域构建一个**可复用的、完全模拟的产品环境（数据库）**，再基于该共享环境合成大量状态变更任务。
- 生成器（privileged task generator）拥有 SQL 和代码访问权限，可以查看完整数据库；求解器（solver）只能通过领域专用 MCP 工具与环境交互。
- 这一**生成器-求解器不对称性**引入了两种差距：
  - **信息差距**：求解器无法从 prompt 直接获得隐藏目标，必须主动检索完整数据。
  - **工具差距**：求解器不能使用 `query_sql` 或 `exec_code`，必须通过普通业务工具组合完成计算与操作。

### 2.2 环境合成：图引导数据库填充

- 将关系模式转换为表级依赖图，按拓扑顺序填充表，外键约束保证引用完整性，构造无孤儿记录的产品世界。
- 使用 LLM 作为约束合成器，生成时提供表结构、键标注、生成要求、全局领域上下文和相关现有记录；依赖上游表的记录须基于真实父记录生成。
- 插入仅通过工具完成，数据库在插入时强制执行主键唯一性和外键有效性。
- 生成后运行确定性验证与修复脚本，修正时间顺序、聚合计数、状态字段等语义错误。
- 在数据库之上构建领域特定 MCP 工具（CRUD 接口，面向产品语义），并用单元测试验证工具实现。

### 2.3 任务合成：生成器-求解器不对称

- 任务生成流程：检查数据 → 决定目标 → 修改状态 → 总结意图。
- 对数据库写操作前后快照，记录精确状态差异（DB diff）作为 ground truth。
- 丢弃无状态变化、意图不可解析或工具使用过度的候选任务。
- 由三个强验证器（GPT-5.5、Claude Opus 4.7、GLM-5.1）在相同全信息工具下校验，至少两个验证器复现一致状态变更才接受；再过滤弱基线也能轻易解决的任务，并按能力类型分层。
- 每个任务保存为 JSON：用户查询、预期数据库变更、能力标签。

### 2.4 能力分类

六种能力类型：Full-Data Acquisition、Multi-Condition Filtering、Aggregation and Computation、Cross-Step Dependency、Precise Boundary Judgment、Cross-Entity Cascade。生成时用能力类型指导任务覆盖。

### 2.5 E-Bench-Code 扩展

- 额外授予求解器 `exec_code` 工具，允许通过 Python 调用领域 MCP 工具进行分页、聚合、集合操作。
- 仍不开放 `query_sql` 或原始数据库访问，因此信息差距保留，仅部分闭合工具差距。
- 对比 E-Bench（手工编排长工具调用序列）与 E-Bench-Code（代码封装）可分离“编排机制”与“信息获取推理”的难度来源。

### 2.6 评估方式

- 每任务 3 次独立尝试，每次从全新数据库副本开始。
- 直接比较最终数据库状态与 ground-truth diff，规则确定性判定，无 LLM 裁判。
- 指标：Avg@3（每次尝试成功率均值）、Pass@3（至少一次成功）、Pass^3（三次全成功，衡量可靠性）。

## 6. 主要结论与发现

- **多步工具使用远未解决**：最强模型 Kimi-K3 在 E-Bench 上 Avg@3 仅 73.79%，Pass^3 58.82%；所有模型平均 Avg@3 约 54.56%。
- **可靠性是核心瓶颈**：Pass@3 与 Pass^3 差距大，说明模型间歇性成功；即使顶级模型 Pass^3 也低于 60%，弱模型接近崩溃。
- **代码执行普遍提升性能但可靠性仍受限**：E-Bench-Code 下所有模型 Avg@3 提升，Opus-4.8 升到 81.11% 跃居第一；但最佳 Pass^3（Opus-4.8）仍只有 68.66%，最差仅 21.13%。
- **代码执行重塑排行榜**：强代码模型（Opus-4.8、Gemini-3.5-Flash）利用 exec_code 大量打包工具调用，排名上升。
- **代码执行降本增效**：平均 MCP 工具调用从 60.42 降至 15.86（-73.8%），轮数从 14.87 降至 9.87（-33.6%），同时 Avg@3 提升。
- **代码执行对计算类能力帮助大，对推理类能力帮助有限**：Multi-Condition Filtering、Full-Data Acquisition、Aggregation 增益最大；Cross-Step Dependency、Precise Boundary Judgment 增益较小。
- **域难度不均**：王者荣耀最难，QQ音乐最易；排名跨域不稳定，需要在多域评测。
- **交互成本与性能关系随设置反转**：基础 E-Bench 下更多工具调用与更好性能正相关（r=+0.57）；E-Bench-Code 下负相关（r=-0.36），说明代码可将大量工作折叠进单次调用。

## 7. 优点

- **完全合成高可控**：环境与任务均可重复生成，避免真实服务的重置难、漂移和隐私问题；可防止基准特定过拟合（不公开环境）。
- **环境可复用、任务可扩展**：同一环境支撑约百个任务，新任务通过调整目标/约束/推理模式即可产生，无需重新设计数据。
- **确定性评分**：基于数据库状态差异，无需 LLM 裁判，稳定、可复现、客观。
- **信息与工具双差距设计**：迫使智能体真正地下隐藏信息，组合多步甚至并行工具调用，反映真实产品闭环交互。
- **两设置对照**：E-Bench 与 E-Bench-Code 隔离了编排机制与信息获取推理，为分析瓶颈提供清晰视角。
- **丰富的能力分类和多维度分析**：不仅报告总体分数，还按域、能力、代码使用、成本效率剖析模型行为。
- **严格任务验证流程**：三验证器一致性检查、弱基线过滤、任务难度分层，提高基准质量。

## 8. 不足与局限

- **未报告硬件算力**：缺乏 GPU 型号/数量/训练时长等资源信息，难以复现计算成本。
- **实验统计细节有限**：每任务 3 次尝试的重复次数较少，未提供置信区间或方差，对低可靠性模型判断可能存在噪声。
- **领域局限**：三个域均为腾讯系产品模拟，虽然覆盖游戏、音乐、协作，但未覆盖金融、医疗、代码等更多真实场景，跨域泛化结论有限。
- **E-Bench-Code 的实验分组不均衡**：部分模型几乎全部任务都用代码（如 Gemini-3.5-Flash 100%、Opus-4.8 99%），导致 no-C/partial 组样本极少，相关结论只能视为提示性。
- **API 成本估算依赖公开价格且可能过时**：某些模型按人民币价格手动换算，汇率固定，价格变动会影响效率分析。
- **环境与任务合成依赖强大 LLM（如 Claude Opus 4.7）**：生成和验证环节对封闭模型有依赖，若这些模型不可用，管道复现受限。
- **合成现实性有限**：尽管模仿真实产品，但数据库和工具都是模拟的，无法完全替代真实系统生态效度（论文也承认未来向真实 CLI/后端扩展）。
- **模型集合时间点局限**：使用 2026 年前后的模型，快速迭代后排行榜可能迅速过时；且未测试开源本地部署模型（如 Llama-4 系列等）。
- **无训练/微调实验**：未展示 E-Bench 作为训练数据提升代理能力的证据，相关工作留待未来。
