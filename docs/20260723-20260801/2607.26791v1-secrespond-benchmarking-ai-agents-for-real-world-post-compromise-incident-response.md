## 摘要
大语言模型（LLM）代理越来越多地被部署于真实世界安全运营中，可访问主机工件和命令行界面（CLI），因此彻底评估其安全能力至关重要。然而，现有网络安全基准侧重于入侵前场景，即代理在攻击发生前被置于干净且理想化的环境中。这导致入侵后场景未被充分探索。为填补这一空白，我们提出了SecRespond，这是首个在入侵后事件响应工作流中评估LLM代理的基准。给定被入侵主机的取证磁盘快照，以及主机安全产品报告的警报、漏洞扫描和基线检查，代理需生成关于入侵、基线风险和漏洞风险的取证报告，以及修复计划。我们在10个网络靶场上实例化该任务，每个靶场由不同的被入侵云主机构建，涵盖4种入口点类型、21种ATT&CK技术和5种操作系统。我们在OpenCode代理框架上评估了23个前沿LLM。实验结果表明，尽管当前代理能可靠地揭示警报暴露的问题，但它们在主动调查磁盘以发现静默入侵、生成全面且经验证的修复计划方面存在困难，且没有任何模型能在任何单一靶场上实现完整检测与修复。这揭示了构建面向真实世界事件响应的代理的根本瓶颈。该基准公开可用：https://github.com/Alibaba-NLP/qqr/tree/main/data/secrespond。

## Abstract
Large Language Model (LLM) agents are increasingly adopted in real-world security operations with access to host artifacts and command-line interfaces (CLIs), making it critical to thoroughly assess their security capabilities. However, existing cybersecurity benchmarks focus on pre-compromise settings where agents are placed in a clean and idealized environment before an attack occurs. This leaves the post-compromise setting underexplored. To address this gap, we introduce SecRespond, the first benchmark for evaluating LLM agents on the post-compromise incident-response workflow. Given a forensic disk snapshot of a compromised host together with the alerts, vulnerability scans, and baseline checks reported by a host security product, agents are required to produce forensic reports on intrusions, baseline risks, and vulnerability risks, together with a remediation plan. We instantiate this task across 10 cyber ranges, each constructed from a distinct compromised cloud host, spanning 4 entry-point types, 21 ATT&CK techniques, and 5 operating systems. We evaluate 23 frontier LLMs on the OpenCode agent harness. Experimental results show that although current agents can reliably uncover the problems exposed by alerts, they struggle to proactively investigate the disk for silent intrusions and to produce comprehensive, verified remediation plans, with no model achieving complete detection and remediation on any single range. This reveals a fundamental bottleneck in building agents for real-world incident response. The benchmark is publicly available at https://github.com/Alibaba-NLP/qqr/tree/main/data/secrespond.

## 2. 方法论

### 2.1 核心思想
提出 **SecRespond**，首个针对**入侵后事件响应工作流**的LLM代理评估基准。任务要求代理分析被入侵主机的取证磁盘快照，结合安全产品报告（警报/漏洞扫描/基线检查），生成入侵取证报告和修复计划。

### 2.2 任务构建（三层解耦设计）
- **蓝图层（Blueprint）**：定义场景的评估目的，包括目标技术栈、标注MITRE ATT&CK技术ID的攻击链、要覆盖的能力项
- **实例层（Instance）**：在受害主机上实现蓝图，约束条件包括：
  - 真实漏洞（公开CVE或配置缺陷，而非合成缺陷）
  - 真实攻击（通过网络协议交付，而非直接放置恶意文件）
  - 真实入侵痕迹（由攻击自然产生）
- **检查点层（Checklist）**：将结果工件转换为带通过/失败标准的检查点

### 2.3 构建流水线
采用12阶段流水线：蓝图设计→攻击脚本开发→受害实例策划→受害环境部署→受害就绪验证→攻击前干净快照→攻击环境部署→攻击执行→攻击验证→安全数据收集→修复验证→攻击后快照。人工专家在关键阶段参与审计。

### 2.4 五维能力（CAP）分类学
包含52个能力项，跨五个维度：

| 维度 | 含义 | 能力项数量 |
|------|------|-----------|
| **入侵实体（ENT）** | 定位和处理入侵遗留的恶意进程、文件、网络实体 | 12 |
| **持久化机制（PER）** | 恢复攻击者安装的各类持久化机制 | 21 |
| **基线风险（BAS）** | 检查主机配置是否符合安全基线 | 7 |
| **漏洞风险（VUL）** | 确认主机上的弱点 | 4 |
| **调查与响应质量（Q）** | 评估调查的透彻性、诚实度、修复完整性和业务影响评估 | 8 |

### 2.5 层级检查点评估框架
- 共**280个检查点（CHK）**，每个检查点沿两个独立轴评分：
  - **检测轴（Detection）**：满分3分 = 发现问题（1）+ 证据充分（1）+ 根因归因正确（1）
  - **规划轴（Planning)**：满分2分 = 修复步骤正确（1）+ 计划完整（1）
- 归一化：CHK-score = s/M（M_det=3, M_plan=2）
- 聚合到能力级CAP-score和靶场级CHK-score
- 采用**LLM-as-a-Judge**方法，由三个来自不同开发方的强专有模型独立评分，取平均以减轻单一评判者偏差

### 2.6 提示词设计特点
- 任务提示区分Linux/Windows（Windows提供取证工件访问等价表）
- 包含评估基础设施清单（如BENCHMARK-CONTROL密钥），要求代理区分平台痕迹与攻击者活动
- 修复计划需标注风险等级和自动化级别，禁止提供可能切断控制面的具体命令

## 6. 主要结论与发现

### 靶场层级（5个主要发现）
1. **检测普遍优于规划**：所有模型在检测轴得分高于规划轴，差距最大达34.7%（GPT-5.5：检测70.7% vs 规划36.0%）。规划差距主要源于修复不完整而非动作错误——模型往往提出初步修复（如终止进程）但遗漏后续步骤（如轮换泄露凭证、阻止出站、验证业务服务状态）
2. **模型性能差异大**：最强模型为Claude Opus 4.7（79.0%/65.7%），开源模型（GLM、DeepSeek）可与专有模型竞争甚至超越GPT/Gemini系列
3. **版本演进总体改善但非普适**：Claude Opus系列稳步提升，但Kimi K2.6规划得分低于K2.5，Gemini 3.1 Pro低于3 Flash
4. **靶场难度与攻击链复杂度正相关**：无任何模型在任一靶场实现完整检测与修复。Log4j-RCE最易（CVE知名），Shiro-Fastjson、RDP-Service-Abuse、NPM-Worm、ASP.NET-ViewState最难
5. **共同能力瓶颈**：模型倾向于响应显式线索而非主动全方位扫描；修复计划常止步于可见工件，遗漏二级风险和未检测到的持久化机制；很少验证修复是否真正生效

### 能力层级（5个主要发现）
1. 模型在**入侵实体检测**上表现最强（多数>70%），在**持久化机制检测**上最弱（平均58.8%）
2. 模型在**标准化风险修复**（基线/漏洞）上表现良好，但实体清理弱于检测——发现恶意实体只需一次观察，清理则需多步复杂过程
3. **调查与响应质量**持续最弱：攻击链重构难、修复验证缺失
4. 不同模型在不同维度各擅胜场——无任何模型全面主导五个维度
5. 代理模型**显著优于传统无代理扫描器**，尤其在持久化检测上差距最大（代理58.8% vs 扫描器2.1%）

### 技能增强实验结论
- 提供程序性先验（专家调查/修复流程模板）可显著提升规划得分，尤其对初始规划能力弱的模型（如GPT-5.4在SSH-Miner从26%升至83%）
- 但对广播式靶场并非总有效（GLM-5.1在Shiro-Fastjson上检测下降12%），说明模型可能止步于技能边界而不再探索

### 评判可靠性结论
- 三个LLM评判者在72–75%的检查点上给出相同分数，Spearman相关性0.86–0.87
- 与人类专家一致性高：Pearson相关系数0.96，Cohen's kappa 0.94，MAE仅0.15

### 成本结论
- 性能与价格仅弱相关；GPT Pro模型成本最高但性能仅中等；GLM-5.1、DeepSeek V4 Pro、Qwen3.7系列以极低成本达到可比性能

## 7. 优点

### 研究贡献方面
- **首创性**：首个针对入侵后事件响应全流程的LLM代理基准，填补现有安全基准（均聚焦入侵前）的空白
- **真实性和生态效度**：任务基于真实云主机、真实漏洞、真实攻击协议和自然产生的入侵痕迹（而非合成日志），包含噪音、伪装和故意清除的痕迹
- **场景多样性**：覆盖4种入口点、21种ATT&CK技术、5种操作系统、10个独立靶场，并基于372个真实受害云主机的关联分析设计，匹配实际事件分布

### 评估方法方面
- **层级评估框架**：从检查点（280个）→能力项（52个）→维度（5个）→靶场级的多层次聚合，同时支持精细诊断和跨靶场比较
- **双轴评分设计**：每个检查点独立评估“检测”（发现/证据/归因）和“规划”（正确/完整），避免将两个不同能力混淆
- **反浅层归因设计**：仅30–40%攻击动作触发警报，强制评估代理的主动深度取证能力而非显式线索追踪
- **多评判者机制**：三个独立开发方的评判者交叉验证，排除单一评判者偏见；严格性与人类专家校准（LLM评判者稍严格，不易高估）
- **负向扣分规则**：对虚构事实、错误归因和危险建议设置明确惩罚机制

### 实践应用方面
- 技能增强实验揭示了程序性先验的实际效果与边界
- 提供成本/性能对比，对安全团队进行模型选型有直接参考价值
- 基准已公开，可复现性强

## 8. 不足与局限

### 实验覆盖方面
- **单一代理框架**：仅使用OpenCode harness，未探索不同代理架构的影响
- **单次运行**：每个模型-靶场组合仅运行一次，缺少多次运行的方差分析（可能受随机性影响）
- **无代理基线仅做检测**：与扫描器的比较仅限四个可比维度（ENT、PER、BAS、VUL），修复质量无基线可比
- **技能增强实验仅覆盖少数模型**：未揭示技能对所有模型的影响模式

### 评估方法方面
- **LLM-as-a-Judge固有的局限**：虽然通过三评判者平均和人类验证缓解，但评判者可能仍存在系统性偏差（如对结构化输出的偏好），且人类验证覆盖范围有限（60个检查点）
- **检查点设计依赖人工专家**：280个检查点的设计成本高，扩展至新场景需要大量人工作业
- **简化评分粒度**：检测轴3分、规划轴2分的粒度较粗，可能无法完全区分细微能力差异

### 场景构建方面
- **包含已知CVE靶场可能随模型知识更新而失效**（如论文提及Log4j-RCE是最易场景，因为模型已熟知该CVE），基准的时效性需要持续维护
- **攻击类型覆盖仍有限**：虽涵盖21种ATT&CK技术，仍是入口点/攻击链的有限抽样，未覆盖所有现实中的入侵模式

### 伦理与安全限制
- 论文明确声明仅用于防御研究，但评测内容涉及真实攻击技术，存在被滥用于攻击性目的的双重用途风险
- 所有数据由作者自建，但真实漏洞信息（如CVE）本身具有敏感性
- 评测了第三方专有模型（如GPT、Gemini、Kimi、MiniMax等），可能面临模型服务条款限制或API变化导致的复现困难

### 结论的通用性
- 结论基于2026年7月的模型版本，LLM发展迅速，结论的长期有效性有限
- 事件响应场景本身可能受文化/地区合规影响（如修复计划的自动化水平依赖于组织流程），基准的通用适用性有待验证
