## 摘要
大型语言模型（LLM）代理的快速发展使其能够广泛应用于各种真实世界任务。为了标准化LLM代理与外部环境之间的交互，模型上下文协议（MCP）工具已成为事实上的标准，并已广泛集成到这些系统中。然而，MCP工具的使用也带来了新的安全风险，因为LLM代理可能被诱导执行恶意或未经授权的操作。尽管先前的工作已经提出了保护LLM代理中工具使用的防御措施，但大多数方法依赖于静态分析，即检查提示和生成的输出，这限制了防御的有效性和鲁棒性。为了解决这些局限性，我们提出了MTGuard，一种基于混合分析的防御框架，通过利用生命周期感知的静态-动态协同分析来保护LLM代理中MCP工具的使用。广泛的评估表明，MTGuard在不同LLM代理上有效缓解了多类有害工具使用，同时保持了对良性用户任务的性能。

## Abstract
The rapid development of large language model (LLM) agents has enabled their broad adoption across diverse real-world tasks. To standardize interactions between LLM agents and external environments, Model Context Protocol (MCP) tools have emerged as a de facto standard and have been widely integrated into these systems. However, the use of MCP tools also introduces new safety risks, as LLM agents can be induced to perform malicious or unauthorized actions. Although prior work has proposed defenses for securing tool use in LLM agents, most methods rely on static analysis, i.e., inspecting prompts and generated outputs, which limits the defense effectiveness and robustness. To address these limitations, we propose MTGuard, a hybrid analysis-based defense framework designed to safeguard the use of MCP tools in LLM agents by leveraging lifecycle-aware static-dynamic co-analysis. Extensive evaluation demonstrates that MTGuard effectively mitigates multiple categories of harmful tool use across different LLM agents while maintaining performance on benign user tasks.

- **背景**：LLM（大语言模型）代理通过规划、调用工具并与外部环境交互，已广泛应用于金融分析、网页自动化、科学研究等真实场景。Model Context Protocol（MCP）作为连接 LLM 代理与外部工具/数据源的事实标准，极大推动了生态发展。
- **核心问题**：MCP 工具的统一接口也引入了新的安全边界——不可信或被攻陷的 MCP 工具可诱导代理执行恶意操作（如敏感文件读取、未授权命令执行、数据外泄等）。现有防御（如基于提示词与输出检查的静态分析）主要在消息层运作，存有一个**根本盲区**：恶意工具在元数据和返回消息中看似正常，但运行时却执行有害行为（工具执行劫持攻击）。
- **整体含义**：该论文旨在回答"如何为 LLM 代理的 MCP 工具调用提供全生命周期、运行时可见的安全防护"这一问题，提出了 **MTGuard**——一个结合**协议级静态语境检查**与**系统级动态执行分析**的混合防御框架，弥补了单纯静态分析或单纯沙箱都难以独立解决的语义鸿沟。

## 二、论文提出的方法论

### 2.1 核心思想
- 将 MCP 工具调用生命周期划分为三个阶段：**执行前（pre-execution）、执行中（in-execution）、执行后（post-execution）**，对应部署三个组件。
- **核心洞见**：低层执行轨迹本身无法判定行为是否安全；同一文件访问或网络请求取决于工具声明功能、输入参数及代理任务上下文。因此需要将**运行副作用**与**调用语义上下文**相连接——即"声明 vs. 实际行为"的一致性校验。

### 2.2 问题形式化
- 定义状态转移：$(c, e) \xrightarrow{T} (\hat{c}, \hat{e})$，其中 $c$ 为任务上下文，$e$ 为环境状态。
- 不安全调用判定条件：$\hat{c} \in C_{usf} \lor \hat{e} \in E_{usf}$。
- 安全调用集合：$T_{safe}(c,e) = \{T \in \mathcal{T} \mid \hat{c} \notin C_{usf} \land \hat{e} \notin E_{usf}\}$。
- MTGuard 目标函数：$M(T; c, e) \to \{\text{approve}, \text{deny}\}$。

### 2.3 三大组件（框架架构）
1. **预执行参数审计器（Pre-execution Parameter Auditor）**
   - 在调用发送至执行器之前，收集对话历史、当前用户任务、工具名称、参数 schema（仅保留名称与参数规范，**剔除自由文本工具描述**，防止投毒元数据影响守卫模型）。
   - 评估两类策略：**程序化/代码策略**（可执行函数，优先评估，违规即拒绝）和**自然语言策略**（由固定 System Prompt 与实例化 User Prompt 驱动的 LLM 审计）。
2. **执行中行为监控器（In-execution Behavioral Monitor）**
   - 在 Docker 沙箱中使用 **eBPF**（cgroup v2 定位）捕获工具运行时的进程、文件、网络、DNS 事件。
   - 引入核心数据结构 **工具行为树（Tool Behavior Tree）**：以工具调用为根节点，包含进程分支与 DNS 分支，将异构运行时事件按来源与执行依赖组织为可解释的整体行为描述。
3. **执行后结果验证器（Post-execution Result Verifier）**
   - 对比"声明调用"与"实际执行行为"（行为树+执行结果+DNS），检测执行劫持等仅运行时刻可见的攻击。
   - 同样使用程序化策略 + LLM 文本策略的二级审计；LLM 验证采用 **allow-by-default** 原则，仅在证据明确显示不一致或违规时拒绝。
   - 使用简化行为树控制提示长度、滤除基础设施噪声。

### 2.4 威胁模型
- 覆盖三类攻击面：**MCP 服务器侧**（工具元数据/描述/实现投毒）、**MCP 主机侧**（规划/调度/消息路由篡改）、**用户侧**（恶意提示或恶意用户资源）。
- 排除训练时攻击、模型权重篡改、防御系统自身被攻陷、内核级攻击、多攻击面共谋等情形。

## 三、实验设计

### 3.1 基准场景
- 基于 **MCP-SafetyBench**，选取两个安全关键场景：
  - **浏览器自动化代理**（Playwright MCP 服务器；涉及航班预订、地图搜索、Hugging Face、学术论文搜索、体育网站等）。
  - **金融分析代理**（Yahoo Finance MCP 服务器）。
- 两个代理均可访问辅助工具（文件系统、终端、网络抓取）。
- 每轮代理最多 20 次推理-行动迭代。

## 六、主要结论与发现

1. **MTGuard 显著优于基线**：
   - 整体 DR：MTGuard 为 **48.3%**（116/240 个不安全调用），TCG 仅 8.3%，TRI 为 0%。
   - 主机侧攻击（含 Tool Call Hook）：MTGuard DR 达 **75.0%**，两个基线均为 0%——证明动态行为分析对执行劫持的不可替代价值。
   - 用户侧攻击：MTGuard DR 为 **100%**。
   - 服务器侧攻击：DR 为 32.5%（相对较低，因这类攻击倾向于保持语法有效性、运行时行为接近正常）。
2. **FPR 保持较低**：MTGuard 平均 FPR 为 **3.7%**（TCG 0.3%、TRI 0.4%），浏览器代理略高（3.9% vs. 金融 3.4%）。
3. **延迟适中**：预执行审计平均约 5.7–5.9 秒，执行后验证约 6.4–6.7 秒，LLM 审计合计约 **12 秒/调用**（不含确定性规则和沙箱监控开销）。
4. **消融实验证明混合架构的必要性**：PRA-only（25.0%）和 PRV-only（31.7%）均显著低于完整 MTGuard（48.3%）；两阶段互补性明确——PRA 对用户侧攻击有效但完全漏掉主机侧劫持，PRV 恰好相反。

## 七、优点与亮点

1. **填补了运行时可视性盲区**：首次将系统级执行证据（eBPF 事件）与协议级语义上下文（工具声明、参数、任务上下文）系统性地联合分析，能检测纯静态/纯运行时方法各自无法发现的攻击（如工具执行劫持）。
2. **工具行为树设计**：将异构低层审计日志转译为可解释的结构化行为描述，实现了从"碎片化事件"到"可判读行为"的语义提升，是方法论上的亮点。
3. **生命周期感知的架构**：按执行前/执行中/执行后三阶段各司其职，程序化规则与 LLM 语义审计双层递进，兼顾精确性与语义理解。
4. **防御设计克制**：LLM 审计采用 allow-by-default 原则，系统提示明确"仅基于证据"拒绝，在实际部署中对良性调用的干扰有限（FPR 3.7%）。
5. **正面应对双用途风险**：明确说明恶意载荷仅在一次性 Docker 沙箱中运行、不涉及真实数据，并遵循安全研究规范。

## 八、不足与局限

1. **可见性边界**：当前仅捕获进程、文件、网络与 DNS 元数据，**不检查网络负载内容或应用层数据流**，可能漏掉加密流量中的恶意行为、纯内存操作或外部服务上的未观察副作用。
2. **无法回滚副作用**：执行后验证只能"拒绝返回结果"以阻断对推理链的影响，**不能撤销已发生的系统级副作用**（如已写入的文件、已建立的连接）。
3. **部署范围受限**：原型与评估专注于**本地部署的 MCP 工具**；对远程执行或无兼容沙箱/追踪能力的平台，需额外提供方侧插桩。
4. **服务器侧攻击检测率偏低**（32.5%）：偏好操纵、工具选择操纵等攻击变化在合法参数空间内，验证器难以区分，说明语义级操纵仍具挑战。
5. **误报率高于规则基线**（3.7% vs. 0.3%）：浏览器场景中重复导航等正常行为可能触发审计器，存在对良性任务的潜在干扰。
6. **实验规模有限**：攻击用例总量 99 个、细类别样本数偏少；仅两个应用域（浏览器、金融），未覆盖代码执行代理、科研代理等更多场景；后端 LLM 仅三家，未测试开源模型变体。
7. **未报告延迟的完整开销**（排除工具执行时间与 eBPF 监控成本），实际端到端开销可能更高；延迟约 12 秒/调用对高频交互场景的可用性仍是挑战。
