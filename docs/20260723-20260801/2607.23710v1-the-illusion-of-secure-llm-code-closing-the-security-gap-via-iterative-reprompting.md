## 摘要
大型语言模型（LLM）日益融入软件开发工作流，但其自主生成安全认证代码的能力仍不确定。本文通过结合静态代码分析与动态渗透测试的双模态评估框架，并映射至NIST SP 800-63B指南，评估了五种主流AI编程助手所生成认证系统的安全架构。研究考察了模型在四种提示策略（基础、安全、基于NIST、重提示）下的行为，以反映不同级别的开发者指导。实证结果表明，由功能性或泛安全提示生成的代码始终遗漏关键保护，尤其是在抗暴力破解、会话管理和稳健密码处理方面。尽管提供明确的单次NIST上下文显著提升了合规性，但研究发现这在结构上仍然不足。相反，迭代重提示——强制模型进入上下文自审计循环——是达成全面纵深防御安全架构的严格必要条件。最终，本研究证明当前AI编程助手无法生成默认安全的应用程序，这要求企业部署必须从单次提示工程转向持续的、标准驱动的验证流水线。

## Abstract
Large Language Models (LLMs) are increasingly integrated into software development workflows, yet their ability to autonomously generate secure authentication code remains uncertain. This paper evaluates the security architecture of authentication systems generated by five prominent AI coding assistants through a bi-modal assessment framework combining static code analysis and dynamic penetration testing, mapped to NIST SP 800-63B guidelines. The study examines model behavior across four prompting strategies Basic, Secure, NIST-Based, and Reprompting to reflect varying levels of developer guidance. Empirical results demonstrate that code generated from functional or generically secure prompts consistently omits critical protections, particularly concerning brute-force resistance, session management, and robust password handling. While providing explicit, single-shot NIST context significantly improves compliance, the findings reveal that this remains structurally inadequate. Instead, iterative Reprompting: forcing models into a contextual self-auditing loop is strictly required to achieve a comprehensive, defense-in-depth security architecture. Ultimately, this study proves that current AI coding assistants do not produce secure-by-default applications, dictating that enterprise deployments must transition from single-shot prompt engineering to continuous, standards-driven verification pipelines.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：当前AI编程助手（LLM）在生成用户认证系统的代码时，能否真正做到"默认安全"（secure-by-default）？如果开发者仅提供功能性描述或模糊的安全要求，模型会生成怎样的安全代码？
- **研究动机**：认证系统是软件安全的第一道防线，涉及密码存储、会话管理、暴力破解防护、CSRF防御等多个关键环节。然而，LLM基于大规模公开代码库训练，很可能复制历史漏洞、不安全默认值和过时实现模式。此前研究已表明：LLM生成的代码即使功能正确，也可能保留不安全模式，且仅靠安全提示无法一致性地消除这些弱点。尤其值得警惕的是，新手开发者往往直接使用功能性提示并接受生成结果，安全负担完全落在用户身上。
- **整体含义**：本研究通过系统实验证明，AI编程助手目前**不具备**默认生成安全认证代码的能力。安全必须通过显式的标准指导、迭代自审计和独立验证来"榨取"出来——这从根本上挑战了"AI自动生成安全代码"的行业乐观叙事，并对企业AI辅助开发的部署方式提出了重要警示。

## 2. 论文提出的方法论

### 核心思想
构建一个**统一安全合规评估框架**，通过三阶段流水线系统性地评估LLM生成认证代码的安全表现：

1. **Phase 1 — 提示工程**：设计四层递进的提示策略，模拟不同安全经验的开发者
2. **Phase 2 — 代码生成**：在受控条件下让五种AI助手生成认证代码
3. **Phase 3 — 双模态评估**：结合静态代码审查与动态渗透测试，映射至NIST/OWASP安全矩阵

### 四层提示策略（核心方法论创新）
| 提示类型 | 模拟对象 | 内容特征 |
|---------|---------|---------|
| **BP（Basic Prompt）** | 新手开发者 | 仅功能描述，无任何安全关键词 |
| **SP（Secure Prompt）** | 中级开发者 | 功能描述 + 泛泛的"secure and clean"要求 |
| **NP（NIST-Based Prompt）** | 专家级开发者 | 功能描述 + 从NIST SP 800-63B提取的结构化安全指南（借助NotebookLM辅助文档抽取） |
| **RP（Reprompting）** | 迭代式开发流程 | 要求模型先自审计初始代码（列出已完成/部分完成/未完成的安全参数清单），再修改完善以完全满足NIST指南 |

### 技术细节
- **受控生成环境**：所有提示强制模型生成Flask应用 + SQLite3 + **raw SQL（禁止ORM）**，含四个页面（landing、registration、login、dashboard）。该约束是为了移除框架自带的安全防护（如ORM的参数化），从而暴露模型自身的安全推理能力。
- **双模态评估**：
  - **静态分析**：手动逐行审查源码，对照统一安全矩阵（34个安全参数），覆盖密码策略、KDF选择（PBKDF2/Argon2id/Scrypt vs SHA-256）、会话标志位等
  - **动态渗透测试**：部署本地环境，使用Burp Suite（手动攻击）和HackingBuddyGPT（LLM驱动的自主渗透测试代理）实施真实攻击，包括暴力破解（Burp Intruder + 密码字典）、会话劫持（Cookie重放）、CSRF（恶意HTML表单载荷）和HTTP头缺失检测
- **评分方法**：完全合规（✓）记1.0分，缺失（✗）记0.0分，部分合规（∼）记0.5分，用于量化各模型的合规得分。
- **评估矩阵**：从NIST SP 800-63B提取认证要求，与OWASP及Flask安全最佳实践对齐，构建34项参数的统一矩阵，覆盖7大安全域。

## 6. 论文的主要结论与发现

| 发现 | 具体内容 |
|------|---------|
| **BP代码严重缺乏安全防护** | 功能性提示生成的代码普遍缺少暴力破解防护、账户锁定、会话加固、CSRF防御和HTTP安全头；密码哈希依赖框架默认值 |
| **SP收益甚微** | 泛泛的"secure"要求无法一致触发安全机制，不同模型对模糊安全意图的解释差异极大 |
| **NP显著改善但仍不足** | 提供单次NIST指南后，模型更可能实现密码策略、强度更高的KDF（PBKDF2/Argon2id）、超时控制；但会话安全和响应头加固等架构层面仍有大量缺口 |
| **RP效果最强** | 强制模型对自己的代码进行NIST对照自审计和修订，显著弥补NP遗留的架构性缺陷，是唯一达到全面纵深防御的策略 |
| **高严重性 vs 低严重性** | 参数化查询等局部语法控制被多数模型一致实现；而会话超时设计、CSRF防护、HTTP头配置等需要全局推理的控制始终薄弱 |
| **模型表现分层** | GitHub Copilot（Claude Sonnet 4.6）综合表现最佳；OpenAI Codex需要更强提示才能达到同等完整度；Cursor和Google Antigravity在深层架构推理上持续较弱 |
| **跨框架迁移** | 仅提供NIST上下文时，较强模型（如Sonnet 4.6）还实现了OWASP风格控制（CSP、CSRF、错误信息净化），说明标准引导可产生泛化安全收益，但这取决于模型能力，并非必然 |

**直接回答三个研究问题（RQ）**：
- **RQ1**：AI助手在无显式安全指导下**不能**生成默认安全的认证代码
- **RQ2**：提示特异性越高、迭代轮次越多，安全表现越好；单次标准注入不足，迭代重提示是必要条件
- **RQ3**：会话安全、CSRF防御和HTTP头等**状态架构型控制**是所有模型最一致的弱点

## 7. 优点

1. **选题聚焦且务实**：将安全评估窄化到认证系统这一高风险的特定领域，比泛泛研究"LLM代码安全"更有实践指导价值
2. **双模态评估方法**：静态审查 + 动态渗透测试的组合，既识别理论漏洞，又通过真实攻击确认可利用性（如CSRF的HTML PoC载荷），证据链完整
3. **受控实验设计**：强制使用raw SQL去掉ORM等框架安全护栏，能真正隔离和检测模型自身的参数化意图，这是方法论上的精巧设计
4. **提示策略分层科学**：BP/SP/NP/RP对应新手→中级→专家→迭代开发者的演进，使结论能映射到真实开发场景
5. **跨框架分析**：将NIST和OWASP交叉考量，分析了标准"溢出"效应，增加了发现的信息量
6. **引入AI驱动的渗透测试代理**（HackingBuddyGPT），评估了"AI攻击AI生成代码"的现实威胁场景，贴合未来安全对抗趋势
7. **可复现性**：所有提示全文公开，实验使用隔离会话防止上下文泄漏

## 8. 不足与局限

1. **外部效度有限**：仅测试Flask + SQLite + raw SQL单一技术栈；不同框架（Django、Spring）、不同数据库（PostgreSQL、MySQL）、不同语言下的表现可能明显不同
2. **采样不足**：每个模型-提示组合仅生成一次，无法评估生成随机性对安全性的影响；缺少重复采样的稳定性和方差报告
3. **动态测试覆盖偏窄**：仅覆盖暴力破解、会话劫持、CSRF和Header四类攻击；未涵盖SQLi的实际注入攻击（尽管静态分析确认了参数化查询）、JWT/令牌安全、授权绕过、敏感数据泄露等
4. **手动静态分析存在主观偏差风险**：论文承认静态审查是手动的，尽管有明确矩阵支架，但审查者的判断可能影响合规性认定；且无第二审查者的信度评估
5. **模型选择时效性**：论文使用2026年的模型版本，商业模型更新迅速，结论的时效窗口较短
6. **NIST指南抽取过程不够透明**：使用NotebookLM辅助提取NIST文档，但未详细说明提取的完整过程和可能的信息丢失/偏差
7. **未考虑集成到IDE的真实Copilot工作流**：评估处于孤立聊天会话中，真实开发中LLM的补全行为、多次接受/拒绝修改可能与一次性生成有显著差异

9. **统计严谨性不足**：未报告置信区间、效应量或显著性检验，结论多为描述性陈述
