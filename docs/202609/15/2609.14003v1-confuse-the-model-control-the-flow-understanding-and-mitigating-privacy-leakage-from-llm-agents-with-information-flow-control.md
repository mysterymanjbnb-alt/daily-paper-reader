## 摘要
基于大语言模型（LLM）的个人AI智能体正越来越多地被授权访问用户的私人数据和通信，以提供个性化协助。这种访问带来了持续存在的隐私风险：智能体必须决定是否应将特定敏感信息披露给某一方。现有防御通过更强的系统提示、训练或显式同意检查流程，使智能体后端LLM更具隐私保护性来应对这一问题，但这种方法存在结构性挑战：只要执行判断是LLM对攻击者所控制的同一对话上下文作出的判断，执行机制与攻击面就会重合。我们通过三种新攻击对现有防御证明了这一点，这些攻击仅需普通的智能体交互，无需提示注入：协作工作区诱饵（Collaborative Workspace Lure）将提取尝试重新包装为协作工作；语义混淆攻击（Semantic Obfuscation Attack）通过省略而非智能体所写的任何内容来诱导披露；而信道解耦攻击（Channel Decoupling Attack）将提取请求与信息披露拆分到相互独立的信道中。这三种攻击的泄露率均显著高于这些防御最初设计所能抵御的攻击。受此观察启发，我们提出FLOWSEAL，这是一种在LLM上下文之外通过工具级拦截器来执行机密性保护的防御方法，其基础是数据溯源和带有受控降密的信息流控制格。在三个基准、五个基于提示的基线以及八种攻击（包括通过MCP执行实时工具调用的真实智能体）上进行评估后，FLOWSEAL在保持任务效用的同时，将泄露率降至接近零（例如，针对协作工作区诱饵从52.2%降至0.5%），且不受底层LLM后端影响。

## Abstract
Personal AI agents built on large language models (LLMs) are increasingly given access to a user's private data and communications in order to provide personalized assistance. This access creates a persistent privacy risk: the agent must decide whether a given sensitive information should be disclosed to a particular party. Existing defenses address this by making the agent's backend LLM more privacy-preserving through stronger system prompts, training, or explicit consent-checking procedures, but this approach has a structural challenge: whenever enforcement is a judgment the LLM makes over the same conversational context an adversary controls, the enforcement mechanism and the attack surface coincide. We demonstrate this against existing defenses with three new attacks that require only ordinary agent interaction and no prompt injection: Collaborative Workspace Lure reframes an extraction attempt as collaborative work; Semantic Obfuscation Attack induces disclosure through omission rather than through anything the agent writes; and Channel Decoupling Attack splits the extraction request and the disclosure across independent channels. All three achieve substantially higher leak rates than the attacks these defenses were originally designed to withstand. Guided by this observation, we present FLOWSEAL, a defense that enforces confidentiality through a tool-level interceptor outside the LLM's context, grounded in data provenance and an information-flow-control lattice with controlled declassification. Evaluated across three benchmarks, five prompt-based baselines, and eight attacks, including a real agent executing live tool calls through MCP, FLOWSEAL reduces leak rates to near zero (e.g., 52.2% to 0.5% against Collaborative Workspace Lure) while preserving task utility, regardless of the underlying LLM backend.

## 1. 核心问题与整体含义

- **研究动机**：基于 LLM 的个人 AI 智能体被赋予访问用户私密数据（邮件、日历、文档、记忆等）的权限以提供个性化服务，但这带来了持续性的隐私风险——智能体必须判断某条敏感信息是否应披露给特定接收方。隐私是否适当取决于"谁在问、为什么问、与数据主体是什么关系"，而非固定访问规则。
- **结构性弱点**：现有防御（更强的系统提示、偏好训练、同意检查流程等）均假设"只要给出正确指令，LLM 就能识别隐私决策并正确执行检查"。但**执行机制与攻击面重合**——当隐私执行是 LLM 对攻击者所控制的同一对话上下文做出的判断时，攻击者只需让模型无法识别"这是隐私相关交互"，即可绕过所有下游检查。
- **核心研究问题**：当同一个 LLM 既要解释对抗性请求、又要判断自身行为是否泄露私密数据时，它能否执行稳健的上下文隐私保护？
- **三种新攻击**（仅需普通交互，无需提示注入）：
  - **协作工作区诱饵（CWL）**：将提取请求包装为共享文档的协作编辑任务，使智能体不将其归类为信息请求。
  - **语义混淆攻击（SOA）**：通过"省略"而非"写出"来泄露——要求清理真假混合记录，智能体删除假条目、保留真条目，泄露模式本身。
  - **信道解耦攻击（CDA）**：将提取请求与披露动作拆分到两个独立信道（如邮件请求 + Notion 写入），使会话级同意跟踪失效。
- **整体含义**：论文主张将隐私推理与安全关键的执行分离，机密性不能在被攻击者操纵的上下文内部可靠执行。

## 2. 方法论：FLOWSEAL

### 核心思想
将执行机制移出 LLM 上下文，放到攻击者无法操纵的程序化层。三大支柱：
- **数据溯源**：每条记录携带来自底层系统（邮件发件人字段、文档 ACL、联系人库）的所有权标签，发布决策直接查询这些标签，而非让 LLM 推断敏感性。
- **双层中介**：强制性的代码拦截器 + 协作式提示与 API 层。
- **信息流控制（IFC）**：以带受控解密的安全格形式化安全保证。

### 关键技术细节

- **安全格**：$L = \{\bot, \text{agent}, \top\}$，序关系 $\bot \sqsubseteq \text{agent} \sqsubseteq \top$；join 为 max，meet 为 min。
  - $\top$（高）：数据主体的所有敏感记录。
  - $\text{agent}$：智能体读取 $\top$ 对象后的工作记忆。
  - $\bot$（低）：外部接收方（非数据主体/智能体）。
- **主体划分**：可信 $P_T$（白名单，写入始终允许）、不可信 $P_U$（黑名单，无条件阻止）、未知 $P_?$（经内容检查器审查；可通过授权协议提升为可信）。
- **污点传播**：读取对象 $o$ 后 $\ell(\text{ctx}) \leftarrow \ell(\text{ctx}) \sqcup \ell(o)$；派生对象 $o'$ 的标签为所有来源的 join $\ell(o') = \bigsqcup_i \ell(o_i)$，确保派生内容不能移除溯源。
- **释放边界**：仅当 $\ell(c) \sqsubseteq \ell(d) \lor \text{declassify}(c, d) = \text{SAFE}$ 时允许写入。数据主体授权后 $\ell(d) \leftarrow \top$，将 $d$ 从 $P_?$ 提升为 $P_T$。
- **定理 1（机密性）**：除非 declassify 错误返回 SAFE，否则任何执行轨迹都不能产生写入动作 $a_i = \text{write}(c, d)$ 满足 $\ell(d) = \bot$ 且 $c$ 派生自任何 $\ell(r) = \top$ 的记录（类似 Bell-LaPadula 的 no-write-down）。
- **内容检查器（解密预言机）**：与主推理循环隔离的独立 LLM 调用，仅接收两个输入（所有相关污点记录 + 提议输出），只返回一个词 SAFE/BLOCKED，不给解释。优势在于：由拦截器在工具调用边界无条件触发；接收完整污点记录集，可检测间接派生（改述、选择性删除、编码引用）。
- **四个协作隐私 API**：`RequestAccess`（请求授权）、`ListRecords`（枚举受保护记录元数据）、`CheckDataOwners`（检查输出涉及哪些记录及目的地是否授权）、`Declassify`（提交内容解密，返回 SAFE 或 REDACTED）。
- **拦截器算法流程**：读函数 → 执行并更新污点；写/分享函数 → 提取内容与目的地，若可信直接执行，若不可信硬阻止，否则获取未授权污点记录，为空则执行，非空则调用内容检查器，SAFE 执行 / BLOCKED 阻止并提示重写；隐私 API → 相应处理。

## 6. 主要结论与发现

- **现有防御结构性失效**：SPR-D2 面对新攻击泄露率达 43.8–75.6%（条目级），而 SPR 原始攻击仅 1.9–3.0%。SOA 对每种 SPR 防御都最强（D1 54.7%、D2 75.6%、D3 69.7%），因为其从不直接请求敏感内容。
- **FLOWSEAL 效果显著**：条目级泄露率降至 0–3.3%（SPR-A1/A2 为 0.0%，A3 为 0.3%，PrivacyLens-Seeds 0.5%，ConVerse-Seeds 3.3%）。新攻击下：CWL 从 52.2% 降至 0.5%，SOA 从 75.6% 降至 2.3%，CDA 从 38.5% 降至 2.2%。
- **效用保持良好**：FLOWSEAL 效用率 72.4%，接近最佳基线 SPR-D1 的 75.9%；而 FAN-LCF 仅 25.1%。
- **跨后端稳定性**：SPR-D2 泄露率随智能体 LLM 变化（DeepSeek-V3.2/GPT-4.1-mini/Gemini-Flash-2.5 分别为 52.2/59.2/61.9 LR_I），FLOWSEAL 始终低（0.5/1.9/0.6 LR_I）。
- **真实世界验证**：在实时 Gmail/Notion MCP 端点上，SOA 对 PrivacyChecker 达 34.7% LR_I、48.0% LR_B、34.7% LV，FLOWSEAL 将三项指标全部降至 0.0%。
- **组件贡献**：禁用拦截器泄露率升至 28.4%；内容检查器 fail-closed 保持低泄露（1.3%）但效用归零，fail-open 恢复高效用（79.4%）但泄露升至 24.9%；移除提示使泄露从 0.5% 升至 8.8%。
