## 摘要
AI 智能体将语言模型与可修改文件、调用 API 或执行代码的外部数据和工具相结合。当对抗性内容改变智能体的工具使用方式，或当周边软件包含路径遍历、命令注入等漏洞时，就可能出现安全失效。我们研究经授权的白盒部署前审计，其中审计者可以访问目标仓库和受控运行时，但成功的攻击仍必须通过任务定义的攻击者接口实施，并由外部验证器确认。我们提出 AgentXploit，一个双角色审计系统，将仓库级攻击路径发现与运行时利用分离。分析器智能体（Analyzer Agent）将攻击者控制的输入追踪到敏感操作，并记录有代码支持的候选攻击路径；利用器智能体（Exploiter Agent）将这些路径转化为具体攻击，并利用运行时反馈进行修正。我们还提出 AgentXploit-Bench，包含跨 12 个开源 AI 智能体系统和框架的 72 个可复现漏洞。在三次运行中，AgentXploit 达到 59.3% 的端到端成功率，而 Codex 为 38.4%。在 token 预算匹配的比较下，Codex 达到 46.3%。在提供注入点的 AgentDojo 上，Exploiter Agent 达到 79.2% 的攻击成功率，而 AgentVigil 为 52.7%。这些结果凸显了仓库发现与运行时利用是端到端智能体安全审计中两个不同的挑战。

## Abstract
AI agents combine language models with external data and tools that can modify files, call APIs, or execute code. Security failures can arise when adversarial content changes an agent's tool use or when the surrounding software contains vulnerabilities such as path traversal or command injection. We study authorized white-box pre-deployment auditing, where the auditor has access to the target repository and a controlled runtime, but successful attacks must still act through the task-defined attacker interface and be confirmed by an external verifier. We present AgentXploit, a two-role auditing system that separates repository-level attack-path discovery from runtime exploitation. The Analyzer Agent traces attacker-controlled inputs to sensitive operations and records code-supported candidate attack paths; the Exploiter Agent turns these paths into concrete attacks and revises them using runtime feedback. We also introduce AgentXploit-Bench, containing 72 reproducible vulnerabilities across 12 open-source AI-agent systems and frameworks. Across three runs, AgentXploit reaches 59.3% end-to-end success, compared with 38.4% for Codex. Under a token-budget-matched comparison, Codex reaches 46.3%. On AgentDojo, where injection points are provided, the Exploiter Agent reaches 79.2% attack success versus 52.7% for AgentVigil. These results highlight repository discovery and runtime exploitation as distinct challenges in end-to-end agent security auditing.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体把语言模型与文件、浏览器、代码执行、API、通信服务等外部工具连接起来，能力增强的同时引入两类安全失效：
  - **模型行为层面**：对抗性内容（如检索到的文档、工具响应）诱导模型发起敏感工具调用；
  - **周边软件层面**：实现本身存在路径遍历、命令注入、SQL 注入、SSRF、不安全 eval 等常规漏洞。
- **现有方法的缺口**：绝大多数智能体红队方法**预设注入点或攻击面已知**（黑盒/灰盒设定），只优化"给定注入位置后如何构造对抗输入"，而不检验审计者能否**从实现本身发现一条可行攻击路径**。
- **本文设定的场景**：**经授权的白盒部署前审计**——审计者可检查目标仓库与受控运行时，但攻击必须经由任务定义的攻击者接口实施，并由**外部确定性验证器**（而非智能体自己）确认成功。该设定对应开发者、内部红队或外包审计方的部署前评审，而非典型外部攻击者能力。
- **核心论断**：在仓库级智能体系统中，"发现路径"不只是列出输入与敏感工具，而需判断：哪些输入真正被消费、值如何在组件间流动与变换、影响哪些模型/控制流决策、工具前置条件是否成立。因此**仓库发现与运行时利用是端到端审计中的两个独立挑战**，需分开处理与评估。

## 2. 方法论：AgentXploit 双角色系统

### 2.1 核心思想

将审计拆为两个角色，通过**机器可读的候选攻击路径记录**交接：Analyzer Agent 负责"仓库级攻击路径发现"，Exploiter Agent 负责"运行时利用"，二者之间以显式代码证据和前置条件为接口，避免把不可验证的自然语言摘要当作攻击依据。**路径记录在通过外部验证器之前始终只是假设（hypothesis）**。

### 2.2 威胁模型与权限分离

- **敏感操作**：文件修改、特权 API 调用、命令执行，可能导致数据丢失、未授权访问、数据外泄、代码执行。
- **攻击路径分类**（与漏洞机制正交）：
  - **直接路径**：入口点经攻击者接口可达（API、用户查询通道等）；
  - **间接路径**：起点在外部数据源（检索文档、工具响应等），需先被智能体消费再影响后续工具调用。
- **权限表**（Table 1）：

| 能力 | Analyzer | Exploiter | Verifier |
|---|---|---|---|
| 检查仓库工件 | 是 | 是 | 否 |
| 发送攻击者控制输入 | 否 | 是 | 否 |
| 读取受保护目标状态 | 否 | 否 | 按需 |
| 判定基准成功 | 否 | 否 | 是 |

- 运行时攻击由**攻击者容器**对**隔离目标容器**发起；Exploiter 不得直接读改受保护状态，也不能自行宣布成功。

### 2.3 Analyzer Agent（分析器）

- 使用**调查队列（investigation queue）+ 报告（report）**结构，报告存放于模型上下文之外，使长程搜索中的证据得以保留与累积。
- 流程（文字化算法）：
  1. 映射仓库结构，为外部接口、工具定义、敏感 API、相关配置创建初始 Explore / Search / Read 任务；
  2. 执行优先级最高的任务，工具集包括目录遍历、文本搜索、文件读取、依赖分析、符号、AST、LSP；
  3. 将新代码位置、数据流关系、工具行为、未决链接写入报告；新证据可新增或重排队列条目；
  4. 当证据足以支撑可行路径时，创建/更新候选攻击路径记录；Summarize 任务汇总证据与当前候选；
  5. 队列耗尽或达到分析预算时结束，将候选记录交给 Exploiter。
- **优先级策略**：优先连接"外部值 → 敏感操作"的证据，或闭合候选路径中未决环节的证据。基准**不提供真值入口点**，Analyzer 需自行搜索外部可影响值（请求字段、检索内容、上传文件、工具响应）并逐一检查可达性。
- **路径记录字段**：路径类型、具体入口点、敏感操作、支撑代码位置、所需前置条件、可选利用提示。

### 2.4 Exploiter Agent（利用器）

- 不重复全仓库搜索，只把候选路径转化为可执行攻击：
  - **实现级漏洞**：标准 code-agent 循环——查看相关代码 → 构造输入 → 对目标执行 → 依据运行时错误修订；
  - **LLM 介导攻击**：选择与目标工作流匹配的注入种子，经攻击者接口执行，记录目标响应与允许的执行轨迹，据此构造下一次尝试。
- **初始攻击选择**：维护注入种子语料（含场景、攻击者目标、候选注入位置、payload 模式），模型选择匹配的种子并**适配**，而非回放固定 prompt。
- **执行后修订**：下一轮 prompt 包含上一次 payload、目标响应与允许的执行轨迹，实现有反馈的迭代而非重启。
- **多注入点**：可在多个外部记录/多轮交互中放置互相一致的指令（如早期记录建立身份或触发线索，后期记录重复或激活同一攻击目标），共享攻击目标但按位置适配 payload。

## 3. 实验设计

### 3.1 AgentXploit-Bench（主基准）

- **规模与来源**：72 个可运行实例，跨 **12 个开源 AI 智能体项目**；候选来自 2023–2025 公开披露的 CVE 与智能体安全 issue（含 NVD），经 LLM 辅助筛选后**逐条人工对照漏洞代码与运行时核验**。
- **入选三条硬性标准**：① 具体安全影响（命令执行、未授权文件访问、数据外泄、SSRF）；② 无需专有基础设施即可实例化；③ 存在**外部确定性验证器**。
- **框架分布**：GPT_Academic 22（30.6%）、OpenClaw 10（13.9%）、AgentScope 9（12.5%）、LangChain 8（11.1%）、LobeChat 8（11.1%）、LlamaIndex 4（5.6%）、AutoGPT 3（4.2%）、DB-GPT / GPT-Researcher / MetaGPT 各 2、OpenHands / RAGFlow 各 1。
- **路径构成**：直接 59 条，间接 13 条。
- **三种评估模式**：
  - **analysis-only**：只给仓库、不执行目标，测真值攻击路径恢复；
  - **exploit-only（oracle）**：给出漏洞描述、敏感操作、攻击目标，测已知路径下的利用构造（oracle 诊断，不依赖 Analyzer 成功）；
  - **end-to-end（主指标）**：给仓库与运行时，但**隐藏** CVE/issue 编号、漏洞描述、目标函数、利用字符串、补丁讨论、目标专属成功条件。

### 3.2 对比方法与基线

- **Codex CLI**（同为 `gpt-5.1-codex` backbone）作为端到端仓库基线：可搜索读取源码、用 shell、与可运行目标交互，接收相同任务输入、仓库、攻击者接口与成功判据，但**不获得**隐藏元数据与 Analyzer 报告。设三种预算条件：1× 默认、4× token 上限、token 上限与 AgentXploit 匹配。
- **AgentDojo**（注入点预定义，4 个 suite、629 个用户/注入任务组合）：仅测利用构造，隔离仓库发现；基线为 **handcrafted 模板**与**AgentVigil**（黑盒自动红队）；受害智能体统一用 GPT-4.1，所有方法共享 50 次攻击迭代上限。
- **消融实验**（AgentDojo）：① 去掉精选种子语料（换成 OpenPromptInjection + InjecAgent + AgentDojo + SecAlign 的合并语料）；② 去掉执行轨迹反馈（保留 prompt 历史与成功信号，去掉目标响应与允许轨迹）；③ 去掉多注入点适配（所有位置复用同一 payload）。
- **代码变异鲁棒性**：20 实例子集（15 直接 / 5 间接，每
