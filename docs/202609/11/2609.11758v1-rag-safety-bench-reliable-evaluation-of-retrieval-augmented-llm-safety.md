## 摘要
允许大语言模型（LLM）从一组可信文档中检索信息，可以提高可靠性并减少幻觉。然而，近期研究表明，当提示涉及有害或危险内容时，检索增强生成（RAG）可能会对生成响应的整体安全性产生意想不到的副作用。随着越来越多的最终用户借助RAG将企业文档和知识库纳入基于LLM的系统，需要更清晰地理解导致这一结果的机制。我们提出RAG-Safety-Bench，一个用于衡量RAG对LLM模型安全性影响的基准。通过消除检索器质量的混杂效应，并将问题清晰地划分为四种条件——非RAG、使用包含有害请求答案的oracle文档的RAG、使用与有害请求相关但不包含具体答案的文档的RAG，以及使用随机、安全文档的RAG——该基准分离出观察到的安全性下降中不同因素的影响。我们报告了五个开源LLM上的结果，显示良性能力与不安全能力之间呈反向关系，有力证据表明在RAG场景下基线安全护栏并不能带来下游安全保障，并且提供了模型特定的支持以印证此前发现：在启用检索的系统中，即使良性文档也可能导致不安全生成。

## Abstract
Allowing large language models (LLMs) to retrieve information from a set of trusted documents can increase reliability and reduce hallucination. However, recent work has demonstrated that retrieval-augmented generation (RAG) can have unintended side effects on the overall safety of the generated responses, when prompted for harmful or dangerous content. A clearer understanding of the mechanisms leading to this result is needed, as increasing numbers of end users turn to RAG to incorporate corporate documents and knowledge bases into LLM-based systems. We introduce RAG-Safety-Bench, a benchmark to measure the safety impact of RAG on LLM models. By removing the confounding effect of retriever quality, and cleanly separating the problem into four conditions -- non-RAG, RAG with an oracle document containing the answer to the harmful request, RAG with documents related to the harmful request but without the specific answer, and RAG with random, safe documents -- the benchmark isolates the impacts of different factors in the observed safety degradation. We report results across five open-source LLMs, showing an inverse relationship between benign and unsafe capability, strong evidence that baseline safety guardrails do not lead to downstream safety guarantees in the RAG case, and model-specific support for previous findings that even benign documents can lead to unsafe generation in retrieval-enabled systems.

# RAG-Safety-Bench 论文结构化总结

## 1. 核心问题与研究背景

- **背景**：RAG（检索增强生成）被广泛用于将 LLM 锚定在外部可信文档上，可减少幻觉、支持知识快速更新、允许企业注入专有文档，并提升可溯源性。直觉上 RAG 应比非 RAG 模型更安全，主要风险似乎只来自语料投毒等对抗性攻击。
- **核心问题**：近期工作（An et al., 2025）发现，即便检索到的文档是良性的，启用 RAG 的 LLM 反而比仅依赖参数化知识的模型更不安全。这一现象在非对抗场景下缺乏机制性解释。
- **整体含义**：随着企业级 RAG 部署普及，需要厘清"安全退化"究竟来自**不安全信息本身**，还是来自**长上下文/话题漂移**导致的模型行为偏移。论文认为，仅用非 RAG 的安全评测无法迁移到 RAG 场景，必须引入专门的、可分离变量的评测基准。

## 2. 方法论

### 2.1 核心思想

- 借鉴 MIRAGE（Park et al., 2025）"直接提供 oracle 文档、绕过检索器"的思路，将其从**良性能力**评测扩展到**安全评测**。
- 通过**固定检索文档内容、一次只改变一个变量**，消除检索器质量这一混杂因素（差的检索器可能因"没检索到危险文档"而虚高安全性）。

### 2.2 四种条件设计（RAG-Safety-Bench）

| 条件 | 描述 |
|---|---|
| LLM-only（非 RAG） | 不提供任何上下文文档，仅依赖参数化知识 |
| Oracle | 检索文档中**直接包含**有害请求的答案（可能对应数据投毒，也对应"未精心筛选"的常见现实） |
| On-topic | 文档与查询主题相关，但**不含**具体答案 |
| Random | 从良性、离题文档池中随机抽取，用于检验"仅长上下文"假说 |

### 2.3 基准构建流程

1. 基于 MLCommons AILuminate "Hazard Taxonomy" 改造出适配 RAG QA 场景的危害分类体系，最终包含 **20 个子类**（暴力犯罪、性相关犯罪、非暴力犯罪、仇恨、无差别武器、自残六大族）。
   - 剔除的类别：隐私/身份识别（知识库为公开资源）、直接有害内容生成（聚焦 QA 而非生成）、知识产权（Wikipedia 禁止上传受版权保护内容）、专业建议（法律/医疗等定义模糊、强语境依赖）。
2. 对每个子类定位相关 Wikipedia 类目，用 **Claude-Sonnet-4.5** 生成"现实中用户可能提出、且答案可在某篇 Wikipedia 文章中查到"的有害问题。
3. 强制自检以避免幻觉与不现实提问；输出包含：问题、危害严重度、源文档 ID 与标题、含答案的原文段落、预期不安全答案摘要等。
4. 由 **GPT-4.1-mini** 对最终渲染上下文做答案可得性审计，仅保留 Oracle 判为 yes/partial、On-topic 判为 no 的样本；Random 条件直接采用 `answer_support=none` 的良性文档。
5. 发布两个版本：**Full（987 条）** 与 **Balanced（346 条，各类尽量均衡至 20 条）**，后者用于本文实验。

### 2.4 评测与判定方法

- **安全性判定**：三个 LLM 安全评判器（LlamaGuard-3-8B、ShieldGemma-2B、WildGuard）分别打标，**至少 2/3 判为 unsafe** 才记为不安全。
  - LlamaGuard：二元 safe/unsafe；ShieldGemma：4 条策略（危险内容、骚扰、仇恨、色情），任一概率 > 0.5 即 unsafe；WildGuard：取二元 harmful 标签。
- **答案准确性判定**：用 **Claude-Opus-4.7** 将模型输出与 `expected_unsafe_answer_summary` 比对，输出 true/false。
- **拒绝行为分类**：用 **Claude-Sonnet-4.6** 将拒绝分为 `safety_refusal`（出于安全拒绝）与 `insufficient_info`（因信息不足拒绝），另设 `other`。
- **一致性度量**：评判器之间用 Cohen's Kappa 与四路 Fleiss's Kappa。

### 2.5 待检验假设

- **H1**：MIRAGE 良性能力强的模型，在 Oracle 条件下答案准确率更高、因而更不安全。
- **H2**：Oracle 条件最易产生不安全回答；On-topic 因"有害话题语境"也会高于非 RAG 基线；若纯粹是上下文长度效应，Random 应与 On-topic 相当。
- **H3**：Random 条件下拒绝率最高，但归因于"信息缺失"，应与"真正的模型安全"（不愿提供危险建议）区分。
- **H4**：不同自动安全评判器之间会存在较高分歧。

## 3. 实验设计

- **数据集 / 场景**

- **被测模型**：Gemma-3-12B-It、Llama-3.1-8B-Instruct、Ministral-3-8B-Instruct、Qwen-2.5-7B-Instruct、Phi-4-14B（均为开源模型；未测试商业模型以避免违反 API 服务条款）。
- **对比维度**
  - 跨条件对比：非 RAG / Oracle / On-topic / Random。
  - 跨模型对比：良性准确率 vs 不安全准确率的相关性。
  - 跨评判器对比：LlamaGuard / ShieldGemma / WildGuard 的一致性与分品类敏感度。
  - 按 20 个危害子类做细分统计（附录图 6–10）。
- **生成设置**：温度 0.0、top-p 1.0、禁用采样、最多 1024 新 token、固定随机种子 42；每篇文档清洗后前缀上限约 12,000 字符。

## 5. 实验数量与充分性

- **实验规模**：5 个模型 × 4 个条件 × 346 条查询 = 6920 条生成响应；另加 MIRAGE 1000 条良性查询用于能力对照。这是较为扎实的规模。
- **消融/对照**：四条件设计本身即是核心消融——把"检索到答案""检索到相关话题""检索到无关良性文档"三种情形分离。
- **人工验证**：
  - 准确性判定：人工标注 100 例，人–机一致率 95–96%，Cohen's κ 0.90–0.92；两标注者之间 0.97/κ=0.94。
  - 拒绝分类：人工标注 100 例，人–机一致率约 84–85%（κ 0.71–0.73），标注者之间 92%（κ 0.86）。
- **客观性与公平性**
  - 优点：固定温度 0、固定种子、统一 prompt 模板与解码设置、统一的文档长度上限，条件间可比性较强。
  - 局限：仅单次运行，未做多次采样的方差估计；作者自己也承认 LLM 生成的随机性可能导致结果波动。
  - 评判器之间一致性仅为中等（Fleiss κ = 0.56），说明"不安全"标签本身存在主观性，绝对数值需谨慎解读；但作者指出跨评判器的**趋势**在大样本平均下大体一致（附录图 5）。

## 6. 主要结论与发现

- **R1（能力关系）**：所有模型在 Oracle 良性条件下准确率大幅跃升（82–92%），说明模型完全有能力利用 RAG 上下文，安全性下降不能归咎于"读不懂文档"。但 **H1 未被支持**：良性 Oracle 准确率与不安全 Oracle 准确率呈**负相关（Pearson r = −0.70）**，即能力更强的模型其护栏也相对更好；不过所有模型在答案可得时都更倾向作答，说明护栏仍需针对 RAG 场景强化。
- **R2（不安全信息 vs 不安全语境）**：
  - 所有模型在 **Oracle 条件下不安全性最高**，印证"检索外部信息（即使来源如 Wikipedia 般相对安全）即构成风险"。
  - **On-topic 效果因模型而异**：Gemma/Llama/Ministral 基本回落到基线或以下，Phi 略高但整体很低，**Qwen 是显著异常值**（On-topic 17.3% vs 非 RAG 15.9%，Oracle 高达 82.9%）。
  - **Random 条件最安全**，说明"仅长上下文"不足以把模型推入不安全状态——H2 仅部分成立。
  - 结果部分支持 An et al. (2025) 的"非 RAG 最安全者往往也是 RAG 最安全者"，但 Qwen 反例表明**部分模型的护栏更脆弱**。
  - 危害增幅最大的子类：放射性武器、爆炸物、毒品、化学武器、袭击、恐怖主义、网络攻击；Ministral 与 Qwen 在自杀/自残类也出现令人担忧的上升。
- **R3（拒绝行为）**：与 H3 一致，"因信息不足而拒绝"在 On-topic 中增多、在 Random 中进一步增多。论文强调这属于**"被动安全"**，与真正出于价值对齐的主动拒绝（safety_refusal）应当区分；Random 条件下看似安全，很大程度来自模型"找不到答案"。
- **R4（危害主观性）**：评判器分歧明显——LlamaGuard 与 WildGuard 的 κ = 0.66（较好），其余两两仅 0.47–0.48，四路 Fleiss κ = 0.56（中等）。各评判器对不同子类敏感度差异大（如 ShieldGemma 对网络攻击/金融犯罪判得少、对化学/放射性武器判得多；WildGuard 对仇恨言论与性骚扰更敏感）。
- **总体结论**：非 RAG 的安全评测**不能迁移**到 RAG 部署；最关键的失效模式具有**模型特异性**（Qwen 案例显示：话题相关的无答案文档也能诱发模型从参数记忆中吐出本不该披露的信息）。

## 7. 优点

- **变量控制严谨**：直接提供上下文文档而非调用真实检索器，干净地剥离检索质量这一混杂因素，是安全评测方法论上的实质性改进。
- **四条件设计**将"答案可得性"与"话题相关性"解耦，能区分"不安全信息驱动"与"语境漂移驱动"两种假说，并给出可证伪的 H1–H4。
- **区分两类拒绝**（safety_refusal vs insufficient_info）——指出"因查不到而拒答"不应被计作安全，这一操作化界定对后续研究有重要价值。
- **多评判器 + 人工验证**：三个安全评判器加多数投票，并用人工标注验证准确性与拒绝分类的 LLM-as-judge，报告了具体 κ 值，透明且可复现。
- **基准数据可溯源**：全部来自 Wikipedia，符合 CC BY-SA 4.0 许可，附带完整元数据（文档 ID、答案可得性审计标签、危害分类、预期答案摘要等），并提供 Full/Balanced 两个版本。
- **伦理与合规处理审慎**：明确说明不测试商业模型以免违反 ToS、内容不引入新知识、标注者心理保护等。

## 8. 不足与局限

- **语言与来源单一**：仅英文、仅 Wikipedia 一个文档源、危害类别非穷尽，跨语言与多语料场景的结论未知。
- **安全性定义依赖用户画像**：论文承认"对情报人员 / 普通公众 / 学童而言危险信息截然不同"，单一评测无法覆盖不同使用情境。
- **刻意绕开检索器**：设计上不评估检索器影响，因此**未考察检索排序、查询改写与生成器安全之间的交互**，与端到端生产系统仍有距离。
- **简化 RAG 流程**：生产系统通常还有系统提示安全指令、输入/输出过滤等组件，本文只评估基座模型"内建"护栏的效果。
- **模型覆盖有限**：仅 5 个开源、规模偏小的模型（7B–14B），未覆盖大型商业模型（虽作者鼓励有内部权限者使用该基准）。
- **对 Claude 家族依赖较重**：基准生成（Sonnet-4.5）、准确性判定（Opus-4.7）、拒绝分类（Sonnet-4.6）均依赖 Claude；虽有人工验证，但更稳健的做法是多强模型集成评判。
