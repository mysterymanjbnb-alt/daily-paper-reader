## 摘要
多智能体系统可以通过并发执行任务来降低复杂任务上的延迟。若干开创性的 harness 框架支持多智能体系统。然而，当前多智能体 harness 的可扩展性往往受限于中心编排器分配任务与协调工作者的能力。为解决这一限制，我们提出 Agensh，一种无需中心编排器的可扩展自组织多智能体 harness：并发工作者执行多智能体协作循环，以异步方式持续收集上下文、认领并自我分配子任务、采取行动并共享发现、验证结果并合并进展。该循环由智能体组织基础设施支撑，包含三个组件：共享工作区保存已提出、进行中和已完成的工作；消息接口使工作者能够通信；共享上下文保留可复用的发现与工作意图。为测试 Agensh 的可扩展性，我们在 ProgramBench 的五个最难任务上使用 GPT-5.6-sol (high) 对其进行评估。智能体数量从 1 扩展到 128 时，平均最终测试通过率从 19.31% 提升至 28.78%，相对提升约 49%。更大的组织更早达到可比的测试通过率。在 pandoc 上，智能体数量从 1 扩展到 1,024 时，最终测试通过率从 33.89% 提升至 55.06%。工作者轨迹进一步表明，随着组织规模增长，不同形式的自组织协作逐渐涌现并趋于标准化。这些结果揭示，智能体数量可作为多智能体组织的新扩展维度，以拓展通用智能的前沿，为硬延迟约束或时间预算下的复杂任务提供了一种实用解决方案。

## Abstract
A multi-agent system can reduce latency on complex tasks by executing work concurrently. Several pioneering harness frameworks support multi-agent systems. However, the scalability of current multi-agent harnesses is often constrained by a central orchestrator's capacity to allocate tasks and coordinate workers. To address this limitation, we introduce Agensh, a scalable self-organized multi-agent harness without a central orchestrator: concurrent workers execute a multi-agent cooperation loop, continuously gathering context, claiming and self-assigning sub-tasks, taking action and sharing findings, verifying results, and merging progress in an asynchronous manner. The loop is supported by the agentic organization infrastructure comprising three components: a shared workspace holds proposed, ongoing, and completed work; a message interface lets workers communicate; and shared context retains reusable findings and work intentions. To test the scalability of Agensh, we evaluate it on the five hardest ProgramBench tasks with GPT-5.6-sol (high). Scaling from 1 to 128 agents raises the mean final test-pass rate from 19.31% to 28.78%, an approximately 49% relative improvement. Larger organizations reach comparable test-pass rates earlier. On pandoc, scaling from 1 to 1,024 agents raises the final test-pass rate from 33.89% to 55.06%. Worker trajectories further show that different forms of self-organized cooperation gradually emerges and standardizes as the organization grows. These results reveal the number of agents as a new scaling dimension for multi-agent organizations to expand the frontier of general intelligence, offering a practical solution for complex tasks under hard latency constraints or time budgets.

## 1. 核心问题与研究动机

- **单智能体的瓶颈**：单智能体受限于单一上下文窗口、单一动作流与单一记忆流，在复杂真实任务上必须串行执行，延迟高。
- **现有多智能体框架的瓶颈**：Codex sub-agent、Claude Code sub-agent/agent teams、Copilot fleet、Kimi Agent Swarm 等普遍采用 **orchestrator–worker（中心编排器）结构**：由主智能体规划、拆解任务、分派并管理 worker。该结构的整体可扩展性从根本上受限于**中心编排器的协调与集成能力**（且通常需要专门训练的编排器）。
- **论文含义**：提出 **Agensh**——一个**无中心编排器的可扩展自组织多智能体 harness**，让并发 worker 通过轻量"智能体组织基础设施"共享状态与进度，并主张**智能体数量（agent count）可作为多智能体组织的新扩展维度**，既提升复杂任务质量，也压缩达到给定性能所需的时间。

## 2. 方法论

### 2.1 核心思想
- 用**自组织（self-organized）协作**替代中心调度：每个 worker 自主发现、认领并完成子任务，个体进展通过共享基础设施沉淀为组织级成果。
- Agensh 是**叠加在单智能体 harness 之上的组织层**，而非替代它：底层 harness（如 Copilot、Claude Code）负责单个 worker 的推理、工具调用与本地循环；Agensh 负责"有多少 worker 接收事件、共享状态、协作并持续贡献"。

### 2.2 多智能体协作循环（五步，异步并发执行）
1. **Gather context**：读取共享用户目标、当前状态、同伴进展与消息、累积发现，并与环境交互规划下一步。
2. **Claim sub-task**：提出子任务并把范围作为 `CLAIM` 追加到共享上下文；出现重叠/冲突时通过**直接消息**协商解决。
3. **Take action**：本地用工具实现子任务，并把可能对他人有用的发现写入共享上下文。
4. **Verify results**：按验收标准自检，不满足则修正直至满足。
5. **Merge progress**：把成果合并进共享工作区，并发布变更说明、思路与验证证据；若合并冲突则拉取最新同伴进展、解决冲突后重试，随后回到步骤 1。

### 2.3 智能体组织基础设施（三大组件）
- **共享工作区（Shared workspace）**：保存已提出/进行中/已完成的工作，支持并发写、异步读、版本历史与合并冲突暴露；实现上使用 **Git 平台（Gitea）**，worker 在私有 checkout/分支上工作，合并到 main，并用 issue/PR 承载工作。
- **消息接口（Message interface）**：共享任务频道（团队公告，低优先级，循环开始时投递）+ 直接消息（高优先级、紧急一对一，工具调用返回时投递，可**打断对方当前轮次**）；保留历史、异步投递，用于解决认领重叠、协商依赖、请求协助。
- **共享上下文（Shared context）**：借鉴 **DeLM** 思路的 append-only 数据库 + 近期记忆，条目为类型化的短文本：`OBSERVED`（观察到的参考行为）、`FACT`（已确认事实）、`FAIL`（被证伪的假设，被视为最高价值条目）、`CLAIM`（正在做的工作）、`PATCH_SUMMARY`（`files= | idea= | evidence=`）；提供 `board_read`、`board_write`、`board_unfold`、`board_grep`（支持多关键词、`,` 为 OR、`&` 为 AND，可检索完整历史）。新条目作为高优先级更新，随其他 worker 的下一次基础设施工具调用返回而送达。

### 2.4 实现与工程细节
- **最小化、即插即用的接口**：协作循环通过 **worker 提示词中的工作流指令**实现，而非硬编码进运行时；所有 worker 提示词完全相同，仅 worker ID 不同（完整提示词见附录 A），因此可换接不同底层 harness（Claude Code、Copilot）。
- **事件驱动运行时**：每 worker 配 router，监听 Gitea 仓库活动（SSE 触发增量通知拉取）与 Mattermost 消息（长连接 + 重连补偿）；事件写入持久队列并唤醒 dispatcher，带唯一 ID 去重；按序合并为下一次 prompt 注入持久会话；失败重试采用递增退避，router 重启后未完成事件回队、会话尽量恢复。
- **鲁棒性/活跃性机制**：worker 空闲 10 分钟触发 idle detector 提示继续工作；某轮未产出共享上下文条目时追加提醒发布发现。

## 6. 主要结论与发现

- **智能体数量是新的扩展维度**：5 个最难任务上，平均最终 test-pass 率从 1 agent 的 **19.31%** 提升到 8/32/128 agent 的 **20.68% / 26.52% / 28.78%**；1→128 提升 **9.47 个百分点（约 +49% 相对提升）**。
- **延迟收益**：更大组织更早达到同等通过率。pandoc 上 128 agent 在 **30 分钟**超过 30% 通过率，32 agent 在 60 分钟、8 agent 在 90 分钟，单智能体在前 2 小时始终未超过该阈值。
- **千级规模可行**：pandoc 上 1→1,024 agent 使最终通过率从 **33.89% → 55.06%**（128 agent 为 50.94%），比 128 agent 再高 4.12 个百分点，比单智能体高 21.17 个百分点。
- **自组织协作随规模涌现并规范化**（所有 worker 提示词相同，仅 ID 不同）：
  - **8 agents**：同伴协作——约定技术接口后各自实现（gromacs 的模块接口）；自主发现并解决认领重叠（FFmpeg 中一方改换互补工作）。
  - **32 agents**：多 worker 集成管理——多名同伴评审同一贡献，有人给出反例导致先前批准被撤回、作者修复后重新评审并由同伴合并；参与沟通的同伴范围扩大。
  - **128 agents**：专业化与工作流标准化——按既往经验选择评审者并复用评审关系；把集成责任转交同伴；在 pandoc 上形成并复用"作者更新测试分支 → 发送 commit hash → 同伴验证并合并"的标准协议，并在失败后修订为"授权同伴完成整轮更新/测试/检查/合并"。
  - **1,024 agents**：组织级角色专业化——多名 worker 承担集成者角色，可同时联系多个候选集成者、选首个有效响应者、取消其余请求后再交付代码；同领域专家可在他人失败后接管工作，增强组织鲁棒性。

## 7. 优点

- **架构层面的去中心化**：显式针对"中心编排器容量上限"这一结构性瓶颈设计，把任务发现、认领、依赖协商与集成责任下沉到 worker。
- **最小侵入的即插即用设计**：协作循环以提示词指令而非运行时硬编码实现，接口极薄，理论上可挂接任意单智能体 harness。
- **复用成熟基础设施**：用 Gitea 承担并发写、版本历史、冲突检测与 PR 流程，用 Mattermost 承担频道/私信，共享上下文借鉴 DeLM 并扩展 `board_grep` 支持长时程检索——工程落地性强。
- **协作机制设计细致**：类型化上下文条目（尤其把 `FAIL` 视为最高价值）、私信可中途打断以快速消解冲突、事件去重/重试/会话恢复/空闲与产出提醒等鲁棒性机制完备。
- **实验控制变量严格且任务难度高**：选取 200 个实例中最难的 5 个、无互联网 6h 预算、官方评测；同时报告**最终分数**与**时间曲线**两个维度，兼顾质量与延迟。
- **对"涌现"现象给出分层证据**：按 8/32/128/1,024 四档给出可读的协作形态演进叙事，为后续研究提供了假设与观察起点。

- **成本与效率维度缺失**：论文只报告"质量—延迟"两个维度，却没有报告达到该性能所消耗的总 token、API 成本或节点机时。1,024 agent × 6 小时的算力投入若换算为成本，其相对 1 agent 的"性价比"可能并不单调递增；缺少单位成本收益（如 test-pass rate per dollar/token）的分析，使"agent count 作为新扩展维度"的主张在工程经济学上不够完整。
- **共享上下文可能成为新的隐性瓶颈**：论文批评中心编排器的容量上限，但 Agensh 把协调负担转移到共享上下文与消息接口上——`board_grep` 检索完整历史、所有条目按序投递到每个 worker 的下一轮 prompt，在 1,024 agent 规模下会带来上下文膨胀、信息过载与"信噪比"下降。论文未测量单 worker prompt 中共享上下文条目的增长曲线，也未分析信息过载是否反而限制了个体推理质量。
- **冲突与治理机制在超大规模下的鲁棒性未受压力测试**：Gitea 的合并冲突、PR 评审、CLAIM 重叠协商在 8/32 agent 下表现良好，但 1,024 agent 同时写同一仓库时的**写放大、评审队列拥塞、热点文件争用**等风险未被量化；论文也未讨论错误传播（如一个被误采纳的 `FACT` 被大量 worker 继承）或恶意/退化行为的抑制机制。
- **任务域单一，泛化性未知**：全部实验集中在 ProgramBench（软件工程/代码重建）这一"天然适配 Git 工作流与 PR 评审"的领域，Agensh 的共享工作区正建立在代码协作原语之上。对于写作、科研、数据分析、具身任务等缺乏天然版本控制语义的领域，该组织的可迁移性缺乏证据。
- **理论刻画缺失**：论文给出的是现象学叙事，未建立"agent 数量 → 协作收益"的模型，也未说明收益何时饱和、何时转为负（协调开销超过并行收益的临界点）。因此无法回答"给定任务该配多少 agent"这一实践中最关键的问题。
- **可复现性信息不完整**：未给出完整的超参（如 idle detector 阈值、事件退避参数、上下文条目投递策略的细节取舍）、未公开代码/配置链接（至少在正文中未见），加上无重复运行，独立复现与验证存在障碍。

## 9. 潜在影响与启示

- **研究范式层面**：论文把"组织规模"从工程实现细节提升为**可实验操纵的自变量**，为多智能体研究提供了一个新的、正交于"模型能力"和"提示词工程"的扩展轴。这一视角可能启发后续工作系统研究"组织形态（去中心 vs 中心）× 规模"的二维设计空间。
- **系统设计层面**：以提示词而非运行时实现协作循环、以 Git/Mattermost 等成熟工具承担共享状态与通信，提示了一种**"薄组织层 + 厚既有基础设施"**的低成本落地路径，对工业界构建大规模 agent 系统具有直接参考价值。
- **对"中心编排器"路线的反思**：论文的实验结果（规模越大越好，且不依赖专门训练的编排器）构成对 orchestrator–worker 范式的实证挑战，但并非否定——更可能的结论是两条路线在不同任务结构下各有适用边界。
- **组织行为学的类比**：8→32→128→1,024 的分层叙事（同伴协作 → 评审与集成管理 → 专业化与流程标准化 → 组织级角色分化）与人类组织随规模增长而演化的规律高度相似，可能成为"AI 组织行为"这一新兴交叉方向的经验起点。

## 10. 总体评价

Agensh 是一篇**问题意识清晰、工程完成度高、结论有冲击力但证据边界也较明显**的工作。其核心贡献在于：以极薄的接口设计实现了一个无中心编排器的自组织多智能体 harness，并在软件工程最难基准之一上证明了"智能体数量可作为独立扩展维度"，同时给出质量与延迟双重收益，以及从 8 到 1,024 agent 的协作形态演化观察。

其结论的说服力主要受限于：单一模型/单一 harness/单一基准、1,024 规模仅单任务验证、无重复运行与方差报告、无消融与成本分析。因此更稳妥的表述是——**论文有力地证明了"去中心化自组织在数百至上千 agent 规模上可行且带来收益"这一存在性命题，但尚未确立其相对中心编排器路线的普遍优越性，也未刻画收益的饱和边界与成本结构**。这些正是后续研究最值得切入的方向。
