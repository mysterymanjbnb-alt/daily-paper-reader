## 摘要
远程模型上下文协议（MCP）服务使大型语言模型代理能够调用外部工具，但仅靠OAuth授权并不能确保后续工具调用由依赖方意图信任的提供方工作负载执行。即使在执行转移到替代工作负载、依赖过时的评估状态、重用从其他发送方转移的权限或遍历未声明的下游组件之后，端点仍可能保持授权状态。我们将此问题称为授权后执行信任鸿沟。我们提出ACLE-MCP，一种调用范围的架构，结合了委托授权、工作负载评估和资源侧执行准入。对于受保护的调用，ACLE-MCP签发短生命周期、发送方受限的能力租约，该租约绑定预期工作负载、新鲜度要求、操作、对象和参数边界、下游约束以及回执义务。提供方侧的执行门在执行受保护工具逻辑之前立即消耗该租约。我们使用Keycloak/OIDC验证、MCP Python SDK服务器和可选的vTPM引用验证后端实现了可运行的原型。受控安全实验和代理工具使用扩展表明，较弱的授权或连接时证明模式会留下不同的授权后攻击，而完整的ACLE-MCP阻止了所有评估的攻击系列，同时保留了所有良性任务。在本地模拟的代理扩展中，完整设计相对于仅OAuth，将正常允许调用的请求级池化p95延迟增加了25.7%。这些结果表明，调用时绑定调用权限与当前工作负载状态是OAuth保护远程工具使用的实用补充。

## Abstract
Remote Model Context Protocol (MCP) services enable large language model agents to invoke external tools, but OAuth authorization alone does not ensure that a later tool call is executed by the provider-side workload that the relying party intended to trust. An endpoint may remain authorized even after execution shifts to a substituted workload, relies on stale appraisal state, reuses authority transferred from another sender, or traverses an undeclared downstream component. We call this problem the post-authorization execution trust gap. We present ACLE-MCP, an invocation-scoped architecture that couples delegated authorization, workload appraisal, and resource-side execution admission. For protected calls, ACLE-MCP issues a short-lived, sender-constrained capability lease that binds the expected workload, freshness requirement, operation, object and parameter bounds, downstream constraints, and receipt obligations. A provider-side Execution Gate consumes the lease immediately before protected tool logic begins. We implement a runnable prototype with Keycloak/OIDC validation, an MCP Python SDK server, and an optional vTPM quote-verification backend. Controlled security experiments and an agent tool-use extension show that weaker authorization or connect-time attestation modes leave distinct post-authorization attacks open, whereas full ACLE-MCP blocks all evaluated attack families while preserving all benign tasks. In the locally simulated agent extension, the complete design increases request-level pooled p95 latency on normal allowed calls by 25.7% relative to OAuth-only. These results indicate that invocation-time binding between call authority and current workload state is a practical complement to OAuth-protected remote tool use.

## 1. 论文的核心问题与整体含义

- **研究背景**：大语言模型（LLM）应用程序已从被动文本生成转向主动的代理式执行，频繁通过模型上下文协议（Model Context Protocol, MCP）调用外部工具、数据源和企业服务。在远程部署中，OAuth 可用于授权 MCP 客户端访问受保护 MCP 服务器。
- **核心问题**：论文提出并定义了一个此前未被充分认识的安全问题——**授权后执行信任缺口（Post-Authorization Execution Trust Gap）**。其含义是：OAuth 授权只回答了"客户端/用户是否有权访问某资源"，但**不能保证**后续调用实际由依赖方（Host）所意图信任的、提供方（Provider）侧的具体工作负载来执行。一个执行端点即使在 OAuth 授权通过之后，仍可能出现以下情况而不被察觉：
  - 执行被转移到替代/被替换的工作负载（如容器被回滚到有漏洞的镜像）；
  - 依赖的是注册或连接时获得的、此后已过期的陈旧评估（stale attestation）状态；
  - 权限被其他发送方复用或转移；
  - 请求被路由到未声明的下游代理或组件。
- **整体含义**：仅靠 OAuth、连接时证明或细粒度授权策略都无法弥合"授权决定作出时"与"权限实际被消费时"之间的工作负载信任鸿沟。论文主张，应在**调用时刻（invocation time）**将调用权限与提供方工作负载的当前状态进行绑定，并在工具逻辑执行的最终边界上强制执行。

## 2. 论文提出的方法论

- **核心思路**：ACLE-MCP 是一种调用级作用域（invocation-scoped）的参考监视器架构，将三类要素耦合为一个统一的执行准入决定：
  1. 委托授权（OAuth/OIDC 上下文）；
  2. 提供方工作负载的实时评估/证明（RATS 式工作负载评估）；
  3. 资源侧（工具执行前）的准入控制。

- **关键技术组件**：
  - **Verifier**：验证来自目标工作负载的远程证明证据（完整性、nonce/时间新鲜度、平台或 Provider 策略），并签发签名评估结果 `AR_t = Sign_V⟨wid, state, ts, exp, pid_P, verdict⟩`。
  - **Lease Issuer / 租约颁发者**：综合经过验证的 OAuth 上下文、评估结果 `AR_t` 和调用边界 `I_t`，签发短时、发送方受限的能力租约 `CL_t`。
  - **Execution Gate / 执行门**：部署在 Provider 侧、受保护工具处理器之前，作为不可绕过的最终准入点，对令牌、租约、发送方证明、工作负载绑定、新鲜性、调用边界等进行校验，只有全部通过才允许执行。
  - **发送方约束**：租约绑定发送方确认密钥，防止租约被复制后成为可移植的授权凭证。

- **形式化定义**：
  - 授权调用边界：`I_t = ⟨aud, tool, op, obj, Θ, D, B, ρ⟩`（预期受众、工具、操作类、对象范围、参数约束、批准的下游集合、副作用预算和最小工作负载保证策略）。
  - 提供方实际执行观测：`E_t = ⟨wid, aud′, tool′, op′, obj′, θ′, D′, s, τ⟩`（实际服务请求的工作负载、其评估后的状态和证明时间）。
  - 目标准入性质：`Allow(E_t) ⇒ OAuthOK ∧ FreshWorkload(wid, s, τ, ρ) ∧ WithinBounds(E_t, I_t)`。

- **执行门准入算法流程**（Algorithm 1），按强制顺序执行：
  1. 验证访问令牌（发行者、主题、受众、目标资源）；
  2. 验证租约（发行者、签名、受众、过期时间、策略版本）；
  3. 验证发送方证明（必须匹配租约中绑定的发送方密钥）；
  4. 验证评估结果（`AR.wid = L.wid` 且 AR 足够新鲜）；
  5. 拒绝任何违反租约重放或执行状态策略的权限复用；
  6. 验证请求满足租约中的工具、操作、对象、参数、副作用和下游约束；
  7. 若租约要求回执，则必须经过可生成回执的受保护路径执行，并验证回执绑定租约、请求、评估结果、结果摘要和下游汇总；否则直接执行；
  8. 必要时将单次使用权限标记为已消费。

- **风险分级策略**：低风险读取可走普通 OAuth 路径；中风险调用要求窄范围租约和受限复用窗口内的评估结果；高风险调用要求更严格的新鲜度、更短或单次租约、更紧的副作用边界及必要的执行回执。不确定性只能提升风险级别，绝不允许自动降级。

## 3. 实验设计

- **实验总体结构**：实验分三个层级，覆盖机制级安全验证、组件消融研究和代理工具使用扩展场景。所有实验采用 Python 实现的服务间 HTTP 通信，独立的 Verifier、租约颁发者、执行门、MCP 工具服务和对抗性工作负载分开部署。
- **基准（Benchmark）设置**：
  - **机制级安全实验**：24 个场景，覆盖重放、工作负载替换、陈旧评估复用、作用域误用、未声明代理、回执违约等攻击类型；10 个随机种子，单并发。
  - **代理工具使用扩展**：含 4 个良性任务家族（文件系统摘要、GitHub issue 评论、有界数据库报告、Kubernetes 状态检查）和 6 个执行误用攻击家族（错误工具执行、校验/执行顺序颠倒、工具链步骤注入、跨工具链步骤的权限重用、降级或重执行、流式语义突变）。
- **对比方法**：共 5 种模式
  1. **OAuth-only**：仅验证不记名访问令牌；
  2. **Attest-on-connect**：仅在连接时记录一次工作负载评估；
  3. **Stateful LP**：执行侧检查工具/操作/对象/参数/执行顺序/下游策略，但不含发送方证明和工作负载评估；
  4. **Capability-only**：带有受众和请求限制的短时能力，但不绑定新的工作负载评估；
  5. **ACLE-MCP（完整设计）**：启用全部强制链。
- **真实组件集成验证**：Keycloak/OIDC 令牌验证（含 JWKS）、MCP Python SDK 服务器、可选 vTPM 引用验证路径（`swtpm`/`tpm2-tools`，覆盖 PCR 0,1,2,3,4,7,11）。

## 6. 论文的主要结论与发现

- **安全有效性**：完整 ACLE-MCP 在机制级实验和代理扩展中**阻止了所有评估的攻击家族**（100% 阻断率），且保持所有良性任务成功率为 100%、零误报率、零假阴性率。较弱的模式留下的攻击面各不相同：OAuth-only 和 Attest-on-connect 无法阻断任何执行误用家族；Stateful LP 漏掉流式语义突变；Capability-only 漏掉工具链步骤注入和流式语义突变。
- **消融归因**：去除发送方证明会重新打开令牌重放和跨客户端租约转移；去除新鲜度检查重新打开 TOCTOU 和陈旧评估复用；去除下游约束重新打开未声明代理和 SSRF 元数据访问；去除回执验证接受缺失、伪造和摘要不匹配的回执；去除 Attested Step-Up 则使受损/替换/不匹配的工作负载重新可以访问。
- **新鲜度关键性**：50 ms 评估窗口可阻断全部 TOCTOU 案例；500 ms 时阻断率降至 60%；5000 ms 时降至 0%。这直接说明连接时证明对后期高风险调用是不够的。
- **性能开销**：在代理扩展中，相对于纯 OAuth，完整 ACLE-MCP 使正常允许调用的请求级池化 p95 延迟从 12.20 ms 增至 15.34 ms，**相对增加 25.7%**（约 3.14 ms）。关闭 AR 缓存会增加 Verifier 调用次数（27→210）和约 7.4% 的 p95 延迟，因此 AR 缓存是性能优化而非安全需求。
- **总体结论**：对于高风险远程工具调用，工作负载信任必须在委托授权实际被消费的执行边界处进行检查。调用时绑定调用权限与当前工作负载状态是 OAuth 保护远程工具使用的实用补充。

## 7. 优点

- **问题定义清晰且具原创性**：明确将"OAuth 授权后、实际执行前"的信任缺口单独抽象并形式化为一个独立安全研究问题，对现有研究边界（提示注入防御、计划验证、OAuth 授权、发送方约束令牌、远程证明）做了合理划分。
- **形式化程度高**：用 `I_t`、`E_t` 和准入性质做形式化定义，将"调用时工作负载信任"从口号变为可验证、可测试的规格。
- **完整落地原型**：不只做理论设计，还实现了 Keycloak/OIDC 验证、MCP Python SDK 服务端和可选 vTPM 引用验证路径，验证了组件可替换性。
- **实验设计层次分明、归因性强**：通过 5 种模式对比 + 组件消融 + 新鲜度敏感性扫描，准确归因每个机制的具体安全贡献，而非黑箱式整体比较；阻塞路径和正常路径的延迟分离度量，将 TOCTOU 阻断路径 356.13 ms 的延迟明确归因于实验配置的 350 ms pre-invocation delay 而非系统自身开销。
- **诚实限定结论**：论文反复申明该机制不是通用代理安全万能药——不处理提示注入、不保证任意工具语义、回执不能撤销副作用，只针对执行时工作负载信任这一点。

## 8. 不足与局限

- **信任假设较严格**：整个保障依赖一个**不可绕过的 Provider 侧执行门**（gate）；如果攻击者控制 gate 本身或所有路由路径，保障即失效。若 Provider 暴露了绕过 gate 的替代路径，则该路径不受 ACLE-MCP 保护。
- **排除的攻击面较多**：不处理提示注入、Host 侧规划错误、恶意本地 stdio 启动命令、Verifier/租约颁发者的失陷、以及既未声明也未中介的隐藏下游依赖。这些是代理系统中非常重要的现实风险。
- **评估范围相对有限**：良性任务仅 4 个家族，攻击场景为作者构造的 6 个家族，论文自己承认不足以支持一般性代理能力不受影响的广泛结论。
- **实验环境强度不足**：主要实验采用模拟的 OAuth、证据签名和发送方证明；vTPM 路径只验证了 quote 验证本身、未将每个工作负载声明绑定到硬件信任根；真实 Keycloak/MCP 路径未包含生产级远程证明、DPPoP 绑定发行和完整硬件信任链；并发设置不足以真正测试单飞（single-flight）合并效果。
- **延迟评估的外部效度有限**：25.7% 的 p95 开销来自本地 warm-cache 模拟的 Verifier 路径，未包含冷缓存、真实 JWKS 网络获取或硬件远程证明成本，生产环境开销可能显著不同。
- **回执机制的固有局限**：结构化回执只能提供可审计责任，无法撤销外部副作用，也不能证明任意程序语义的正确性；下游保障只覆盖可见且受强制管制的依赖。
