## 摘要
编程智能体使用系统级工具读取文件、执行命令和修改源代码。在智能体的沙箱中，这些工具通常带有环境权限：只要指明资源名称，即可对该资源执行操作。间接提示注入利用这种权限，将指令置于仓库文件或工具输出中，使智能体执行用户未请求的操作。我们提出CapScope，一种管控层授权机制，它无需模型识别恶意文本即可限制工具使用。在读取仓库内容或工具输出之前，CapScope会从可信输入推导出任务级权限上限，并为每个智能体分配一组独立的类型化能力，这些能力存储在模型上下文之外。每次工具调用都会根据发起调用的智能体所拥有的能力接受检查，因此分配给某个子智能体的权限不会自动对其他子智能体可用。注入可能使智能体请求某个操作，但除非该智能体已具备相应能力，否则该请求将被阻止。我们在Pi编程智能体上实现了CapScope，并在一个修复工作流中进行了评估，由编排器将子任务委派给不同的子智能体。评估涵盖5个Python任务、5个注入面、4种授权条件以及每单元3次试验（共300次运行）。在环境权限基线和全局策略基线条件下，注入效应在33-47/75次运行中执行，而CapScope下仅为3/75。CapScope完成了68/75次修复，基线完成了68-72/75次。

## Abstract
Coding agents use system-level tools to read files, execute commands, and modify source code. Within the agent's sandbox, these tools often carry ambient authority: naming a resource is sufficient to act on it. Indirect prompt injection exploits this authority by placing instructions in repository files or tool output that cause the agent to perform actions the user did not request. We propose CapScope, a harness-level authorization mechanism that restricts tool use without requiring the model to identify malicious text. Before repository contents or tool output are read, CapScope derives a task-wide authority ceiling from trusted input. It then assigns each agent a separate set of typed capabilities, stored outside the model's context. Every tool call is checked against the capabilities of the agent that issued it. Permissions assigned to one sub-agent are therefore not automatically available to another. An injection may cause an agent to request an action, but the request is blocked unless that agent already has the required capability. We implement CapScope on the Pi coding agent and evaluate it in a repair workflow where an orchestrator delegates subtasks to separate sub-agents. The evaluation covers five Python tasks, five injection surfaces, four authorization conditions, and three trials per cell (300 runs). The injected effect executes in 33-47/75 runs under the ambient-authority and global-policy baselines, compared with 3/75 under CapScope. CapScope completes 68/75 repairs, while the baselines complete 68-72/75.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- 编码智能体（coding agent）通过系统级工具读取文件、执行命令、修改代码。在沙箱内，这些工具往往携带**“环境权限”（ambient authority）**：只要能指定某个资源名称，就可以对该资源进行操作。
- **间接提示注入（indirect prompt injection）**利用这种权限模式：攻击者将恶意指令隐藏在仓库文件（README、AGENTS.md、skill 文件、源代码注释）或工具输出（如 pytest 输出）中，使智能体执行用户未请求的操作，如篡改源码、引入后门。
- 现有防御大多停留在**模型层**：训练模型对不可信指令保持怀疑，或使用分类器识别恶意文本。此类方法本质上仍是**概率性判断**，已被证明可以被绕过（即使配合指令层级提示，攻击成功率仍可高达 84%）。
- 此外，现有工具权限控制存在**粒度缺口**：全局策略（哪怕是任务定制生成的全局策略）无法表达"runner 能跑测试但不能改源码，patcher 才能改源码"这种按主体区分的权限差异，即"confused deputy"问题。
- **整体含义**：该论文主张将安全重心从"识别恶意文本"转移到**框架/宿主层强制的最小权限边界**——无论模型是否被注入误导，只要发起调用的智能体不具备对应能力，工具调用就被阻止，从而实现不依赖文本识别的抗注入机制。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

### 核心思想

- **CapScope**：一种宿主层授权机制。在读取任何不可信内容（仓库文件、工具输出）之前，先从**受信任输入**（用户请求 + 项目文件树）推导**任务级权威上限（authority ceiling）**，并为每个智能体分配独立的、类型化的能力集，能力存储于模型的上下文之外。
- 每次工具调用都被检查：只有当发起调用的智能体自身持有覆盖该调用的能力时，调用才被放行。注入可能让模型"提出"某个工具调用，但该调用会被阻止——除非该智能体恰好已有对应权限。
- 核心原则：权限不是字符串，而是**结构化、可衰减、按主体隔离的能力**。

### 关键技术细节

- **能力定义**：能力是 (效果类型, 作用域谓词) 的二元组，写作 Cap[𝑒, 𝜑]。效果类型分为 Read、Write、Exec 三类：
  - Read 作用域谓词：路径规范化（解析 `..` 与 symlink）后检查是否位于允许的前缀之内；
  - Write 同理；
  - Exec：解析命令字符串（拒绝替换、拆分复合命令、去除重定向），每个命令片段逐一检查其 argv 前缀是否在允许集合中；允许 `pytest` 不会连带允许 `pytest; curl ...`。
- **三条形式规则**：
  1. **Mint（铸造）**：唯一引入新权威的规则。由可信宿主策略 P 处理受信任预检输入，生成并冻结任务上限 𝐷𝑟。该步骤发生在任何不可信文本进入上下文之前。
  2. **Derive（派生/衰减）**：当编排器委托子任务给子智能体时，子智能体请求候选能力，宿主过滤该请求，仅保留结构上被授权上限所包含（收窄）的部分安装到子智能体的能力存储中。例如 `src/**` 可收窄为 `src/parser.py`，但反之不可。
  3. **Invoke（调用检查）**：工具只有在被某条已持有的能力覆盖时才会执行；否则返回拒绝消息给模型。检查是确定性的，不询问模型关于文本来源的判断。

### 算法/流程

1. 会话开始时，用**独立 LLM 预检调用**（仅输入受信任用户请求 + 项目文件树，不含文件内容）生成能力提案；
2. 宿主代码确定性验证并编译该提案，冻结为任务级权威上限；
3. 进入代理循环后，每次工具调度前，宿主根据"发起调用的智能体"的能力存储做拦截判断；
4. 编排器委托子任务时，子智能体获得独立的派生能力存储（通过 `createAgentSession` 或独立进程隔离）；
5. 若工具调用未覆盖，返回一个信息性拒绝消息，模型可以重试，但拒绝不会变为允许。

## 3. 实验设计：数据集 / 场景 / Benchmark / 对比方法

- **拓扑控制**：所有条件的 LLM、任务和四主体拓扑保持固定，仅变更授权模型，从而将差异隔离在授权机制上。

## 6. 论文的主要结论与发现

- **防御效果显著**：CapScope 下注入效应仅执行 **3/75** 次运行，而最强的全局策略基线（B2）为 33/75，静态全局策略（B1）与环境权限基线（B0）分别高达 46/75 和 47/75（表 2）。B1 相比 B0 几乎没有改进——因为恶意操作本身就是普通仓库操作，denylist 根本不认识它。
- **为什么全局任务策略仍然漏防**：B2 生成的策略虽然更窄，但因所有主体共享，只能取"任务所需权限的并集"。runner 为了读测试输出和跑测试得以保留，但它也继承了不该有的源码写入权。CapScope 按主语拆分能力，runner 只有读测试与运行 pytest 的能力，没有 Write 效果，注入想要做的源码写入被拒绝。
- **修复成功率几乎不受影响**：CapScope 完成 68/75 次修复，对照不设防的 B0（72/75）仅差 4 次；对比 B2（同为 68/75）则完全持平。
- **残余攻击分布**：CapScope 内仅有的 3 次执行攻击全部经过 AGENTS.md 注入面；其余四个注入面（README、skill、源码注释、工具输出）均为 0/15（表 3）。
- **失败模式分析**（档案日志分解）：7 次修复失败中，2 次由预检漏掉源写入能力造成，2 次由 runner 提出正确修复但工作流未转交有写权限的 patcher，3 次测试已通过但达到会话超时（900 秒）被记为失败。
- **延迟代价**：CapScope 平均 316 秒，明显高于 B1 的 140 秒和 B2 的 194 秒；诊断日志显示重复攻击尝试的次数增加（35 次攻击定向提案中的 27 次有重复尝试），即拒绝后模型继续重试导致额外的 LLM 轮次。

## 7. 优点：方法与实验设计的亮点

- **机制性设计而非概率检测**：CapScope 不要求模型识别恶意文本，由宿主层在每次工具调用前做确定性的能力查找。"注入可能控制模型提出的请求，但控制不了存储于上下文之外的能力表。"该安全属性与模型行为无关，属于结构性的 fail-closed 设计。
- **"能力上限 + 逐主体派生"的清晰抽象**：形式规则仅三条（Mint/Derive/Invoke），简洁而严谨；能力用结构化数据表达（路径前缀 + 解析后的 argv 前缀），支持编译期检查嵌套关系。
- **识别的授权粒度缺口具有说服力**：通过 B2 vs C 的对比干净地证明了单一全局策略无法处理"同一任务中 runner 不需要的写权限"——这直接指向 agent 安全中常被忽视的 confused-deputy 本质。
- **安全性的来源明确**：执行前预检铸造能力、冻结上限，之后任何不可信文本无法加宽权限；比 Progent 这类运行时动态扩充策略的设计更保守、更符合最小权限原则。
- **可与信息流控制、进程沙箱等互补**：作者明确认定能力查找不解决保密性（读取后允许的写入仍能搬运数据）、不覆盖允许命令的传递效应（如 pytest 导入项目模块），将边界划得清楚，不夸大。
- **实验协议干净**：将"攻击是否执行"和"任务是否修复"分开度量，二者可以同时成立；按注入面拆表分析，而不只是报聚合数字；控制基线条件静态化，使对比归因清晰。

## 8. 不足与局限

- **语料规模窄**：只有 5 个小型 Python bug 修复项目。修复工作流短、能力需求面窄，不能推广到大型软件工程、长时多仓库任务或需要动态发现新工具的场景。
- **单模型**：仅 qwen3.5-flash。不同模型的能力遵循提示的程度差别可能很大，缺少跨模型验证意味着不清楚 CapScope 在更强的模型（更可能抗注入）或更弱的模型（更多重试）下收益/代价如何变化。
- **重复试验数少**：3 次重复的统计功效不足，且 300 次运行中的单格结果波动——论文选择只看条件聚合序次，这个处理合理，但也降低了做分面结论的底气。
- **预检发生错误时会影响任务完成**：2/7 次失败源于预检遗漏了必要的写能力；预检 LLM 本身也是一个概率性组件——它恰好在受信任内容上运行，降低了注入面风险，但预测过窄或过宽的策略都会直接影响系统可用性或残余安全性。
- **残余攻击路径仍存在**：3 次经过 AGENTS.md 的注入成功，意味着当授予能力比子任务实际需要的宽（如目录级写入），或注入文本通过影响模型生成的子任务描述而"引导"宿主侧的 grant completion 选中攻击者想要的能力时，分发检查无法纠正。
