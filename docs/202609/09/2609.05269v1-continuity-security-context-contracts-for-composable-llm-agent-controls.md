## 摘要
LLM智能体系统日益将来源追踪、授权、策略执行、协议适配器和执行控制相结合。然而，单独正确的安全机制并不一定能组合成端到端的安全系统：当操作跨越组件边界时，安全关键上下文可能被丢弃、放宽、重新绑定或重新解释。我们识别出这种故障模式为安全上下文不连续性，并引入CONTINUITY，一个用于智能体安全控制可验证组合的框架。CONTINUITY使用假设-保证契约为每个组件建模，并通过签名根授权、来源承诺、角色绑定转换收据、有界类型发布、转换见证和效果受限执行许可来携带经过认证的安全上下文跨转换。我们形式化端到端结果完整性，要求每个实现的外部效果必须由有效且最新的授权见证支持，该见证将主体、任务、来源、委托、策略状态、规范操作和最终性边界联系起来。我们实现了一个参考验证器和确定性跨层故障注入套件，涵盖四个应用领域的32个故障类别。在跨越128个故障域类别的2,560个参数化攻击实例中，完整的CONTINUITY配置没有造成任何有害的外部效果，同时完成了所有700个良性任务并升级了所有200个模糊案例。这些结果表明，安全的智能体执行不仅需要可靠的个体控制，还需要显式契约来在完整的指令到效果路径上保持其保证。

## Abstract
LLM agent systems increasingly combine provenance tracking, authorization, policy enforcement, protocol adapters, and execution controls. However, individually correct security mechanisms do not necessarily compose into an end-to-end secure system: security-critical context may be dropped, widened, rebound, or reinterpreted as actions cross component boundaries. We identify this failure mode as security-context discontinuity and introduce CONTINUITY, a framework for verifiable composition of agent security controls.   CONTINUITY models each component with an assume-guarantee contract and carries authenticated security context across transitions using signed root grants, provenance commitments, role-bound transition receipts, bounded typed releases, transformation witnesses, and effect-bound execution permits. We formalize end-to-end consequence integrity, requiring every realized external effect to be backed by a valid and current authorization witness linking the principal, task, provenance, delegation, policy state, canonical action, and finality boundary.   We implement a reference verifier and deterministic cross-layer fault-injection suite covering 32 fault classes across four application domains. In 2,560 parameterized attack instances spanning 128 fault-domain classes, the full CONTINUITY configuration commits no harmful external effect, while completing all 700 benign tasks and escalating all 200 ambiguous cases. These results show that secure agent execution requires not only sound individual controls, but explicit contracts that preserve their guarantees across the complete instruction-to-effect path.

## 1. 论文的核心问题与整体含义

**研究动机与背景：**

- 大型语言模型（LLM）智能体系统日益复杂，在实际部署中通常串联多个安全控制组件，包括：来源（provenance）追踪、任务范围授权、策略网关、协议适配器、效果绑定执行等。
- 这些安全控制通常被**孤立地设计和测试**，但组合之后可能暴露漏洞：例如某个边界丢失了来源标签、接受了自声明的权威链根、不当扩大了委派范围、未经验证的转换就修改了已批准字段，或执行了过期/重放的许可。
- 论文将这类故障统称为 **安全上下文不连续性（security-context discontinuity）**——即安全关键事实在组件间传递时被丢失、削弱、错误解释或错误绑定。

**核心问题表述：**

> 在什么显式条件下，各个独立有用的智能体安全控制能够组合成一个端到端的后果边界？

**整体含义：**

- 论文不试图证明 LLM 能正确推理，也不声称解决"提示注入"这一语义层面的问题。
- 论文的目标是**结构性的安全声明**：即使规划器（planner）完全被攻破、恶意构造任何动作，若系统满足声明的可信计算基（TCB）与组合条件，该动作也无法在没有合法端到端见证的情况下直接越过最终边界并产生外部效果。


## 2. 论文提出的方法论

**（1）形式化目标：端到端后果完整性（ECI, End-to-End Consequence Integrity）**

- 每个外部实现的效果必须有一个可验证的见证（witness），将该效果连接到：
  - 认证过的链起源（authenticated chain origin）
  - 主体（principal）
  - 任务（task）
  - 字段级来源（field-level provenance）
  - 根授权（root grant）
  - 组件契约（component contracts）
  - 当前策略（current policy）
  - 最终性接收器（finality sink）
  - 一次性执行状态（single-use execution state）

**（2）组件契约模型：Assume–Guarantee Contract**

- 每个控制组件被表示为四元组：

  \[
  C_i = (A_i,\ G_i,\ P_i,\ M_i)
  \]

  - \(A_i\)：输入假设
  - \(G_i\)：输出保证
  - \(P_i\)：必须保持不变的字段
  - \(M_i\)：显式的变换关系

- 安全组合必须满足：上游保证能够满足下游假设；每个被修改的安全字段要么被保留，要么由一个独立验证的关系见证证明其变换是合法的。

**（3）七条充分组合条件（C1–C7）**

| 条件 | 含义 |
|---|---|
| C1 认证起源 | 根信封由受信任的入口签名；根授权由受信任的授权者签发 |
| C2 契约兼容 | 下游担保必须由根授权或上游合法保证建立 |
| C3 上下文连续性 | 每个安全关键路径变更要么被保留，要么由已声明、独立验证的关系见证证明 |
| C4 非放大 | 权限与委派只能经单独认证的授权增加；数据污染级别不得降低 |
| C5 规范动作绑定 | 许可与接收器绑定同一规范动作 |
| C6 新鲜最终性 | 接收器在效果提交前立即重检主体、策略、撤销、过期等 |
| C7 完全中介 | 所有效果等价类路径都必须穿过兼容的最终性接收器 |

**（4）关键技术机制**

- **签名根授权（signed root grants）**：防止"自声明权威根"攻击，链的起点必须由单独认证的受信任授权者签发；
- **角色绑定组件身份（role-bound component identities）**：密钥仅对其配置的角色有效，不能跨角色、跨阶段使用；
- **RFC 6901 风格叶子路径（leaf paths）**：安全字段按叶子粒度解析和追踪，而非笼统的对象级引用；
- **签名来源/上下文清单**：验证器重新解析每个声明的叶子值并比对摘要；
- **有界类型发布凭证（typed releases）**：将来源值、目标路径、精确值摘要、谓词、任务等绑定在一起，防止字段名白名单式的宽松授权；
- **变换见证（transformation witnesses）**：独立于适配器评估语义转换（如别名解析到真实地址）的合法性；
- **一次性效果许可（one-shot finality permits）**：在最终提交前重新验证主体、策略、撤销、重放和幂等状态。

**（5）论文通过四个定理和一个命题刻画安全保证**：

- **定理 1（端到端组合安全）**：若 C1–C7 对某任务成立，即使规划器和所有攻击者可控内容均对抗性，系统仍满足 ECI。
- **定理 2（上下文截断）**：若中间投影遗漏安全字段 f，下游组件无法区分在该字段上不同的两个状态，除非失败关闭或通过认证恢复 f。
- **定理 3（未绑定字段替换）**：若关键字段未被 admission 与 finality 共同绑定，对手可替换该字段而不破坏已检查的许可字段。
- **定理 4（权限不可洗白）**：有限次 LLM 生成、摘要、记忆整合或协议翻译无法凭空创造授权。
- **命题 1（不完全中介）**：一个效果等价类若存在任一绕过最终性接收器的可达路径，即使主路径正确，ECI 也不成立。

- **攻击实例规模**：每个故障-领域类 20 个参数化实例 → 32 × 4 × 20 = **2,560 个攻击实例**；
- **良性任务**：400 个直接良性任务 + 300 个使用签名类型发布的外部数据任务 = 700 个；

- **总场景数**：3,460 个；
- **系统-场景运行数**：7 种系统配置 × 3,460 = 24,220 次系统-场景运行。

**对比方法（7 种配置）：**

| 配置 | 说明 |
|---|---|
| Pass-through | 直接执行最终动作（无安全机制） |
| Tool allowlist | 只检查最终工具标识符 |
| Gateway policy | 仅在网关评估权限/范围/策略/污染，之后信任下游 |
| Provenance gateway | 额外在网关验证字段来源与发布，但不验证下游转换 |
| Effect-bound permit | 仅绑定 post-adapter 动作到最终性，不验证其上游理由 |
| Gateway + finality | 结合网关策略与动作绑定最终许可，但不认证网关到适配器的转换 |
| **CONTINUITY（完整配置）** | 论文提出的参考实现 |

**关键实验设计特点：**

- 每个攻击场景都假设规划器已沦陷，攻击候选直接被注入为理想形式——避免把安全边界归功于"LLM 恰好拒绝"。
- 所有正常场景都包含真实的安全相关适配器转换（别名 → 规范地址），因此 100% 良性完成率不是来自"禁止一切变更"的保守策略。
- 测试了 8 类消融实验（删除特定检查），以识别各不变量被省略后暴露的故障类。

## 6. 论文的主要结论与发现

1. **单个控制本身正确，不意味着组合安全。** 更强的不完整配置（Gateway+Finality）仍使 65.6% 攻击实例产生有害效果，证明"网关授权 + 精确动作绑定"若缺少对网关-适配器转换的认证，组合仍不安全。

2. **完整 CONTINUITY 系统在所有生成场景中实现了 0 有害效果**：
   - 在 2,560 个攻击实例中未造成任何有害外部效果；
   - 包含全部 128 个故障-领域类；
   - 自动完成全部 700 个良性任务；
   - 将全部 200 个含未经发布外部字段的歧义任务升级为 Escalate；
   - 生命周期正确性（含重放/重试语义、幂等性）达 100%。

3. **消融实验显示各检查的重要性**：
   - 字段级来源移除、契约一致性移除、不完全中介，各重新开放 24 个故障类；
   - 根认证移除重新开放 16 个类；
   - 发布验证移除重新开放 12 个类；
   - 变换见证与重放保护移除各重新开放 8 个类；
   - 组件角色绑定、身份绑定等各开放 4 个类；
   - 仅删除权限单调性一项未打开任何类别——因为冗余检查能兜住该类失败，这体现了纵深防御。

4. **性能可接受**：
   - 证明验证中位延迟 4.21 ms；
   - 端到端转换 + 最终性提交中位延迟 7.17 ms；
   - 证明大小随转换数近似线性增长。

5. **架构层面的启示**：规划可以保持概率性和对抗性，但外部后果应通过一个小型确定性的、携带证明的控制平面来中介，该控制平面的保证必须从指令上下文持续贯穿到实现的效果。

1. **兼容基准为合成性、规模较小并有刻意限制**：基准只包含 32 个故障类，划分为四个域，在参数化上基本确定。其故障模式是人工设计的，不需要覆盖所有现实世界攻击（例如隐蔽渠道或由于错误的提示解释造成的失败）。

2. **信任根与语义正确性均属于假设范畴**：最终安全倚赖受信任的授权者、来源验证器、发布与转换见证者决策的语义正确性，协议无法保证包含在信任根中的信息确实为真。

3. **未强制并入模型运行时**：context-manifest 的正确性仅作为一部分运行时假设检验；生产级实现仍需验证其完整性。

4. **原型概念验证范围有限**：已验证的转换语言与谓词注册表很小（如实现中仅验证券别），缺乏生产环境所需的版本化或通用化关系谓词。生产负载的规范编码器（即 RFC 8785 兼容）尚未集成。

5. **规范对象模型与真实云环境结合不足**：使用内存模拟世界的承诺在并发、持久性、故障模式、分布式环境中不一定成立，仍需适配到具体部署环境。

6. **隐私化与提供商能力有待加强**：未在组合意义上涵盖更广泛的现实风险——例如多智能体工具泄漏或面向用户的应用中的越权问题、隐蔽通道导致的残留风险。

7. **论文未提供证据表明 Python 代码已以正式结构化方式完全精化出数学模型**，通过更多回归测试并不能消除人工验证中潜在的抽取不匹配。
