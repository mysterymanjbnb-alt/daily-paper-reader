## 摘要
AI 编码代理正从孤立工具演变为协作队友，它们发现并相互调用各自的专业技能。但协调通道本身可能泄露技能的知识产权。像 MCP 和 A2A 这样的协议在服务端运行实现，但仍将每个技能的描述和类型化模式发布给每个对等方，无法隐藏技能的存在，且无法保证封装后的系统提示不会在网络传输中出现。应用层隐私过滤器有所帮助，但仅在模型决定输出敏感文本之后才起作用。我们采用一种互补的协议层路线：技能即 API（Skill-as-API）——一种协调协议，其对技能的公共视图仅限于名称、描述、类型化输入/输出模式和信任级别。技能主体通过闭包捕获于所有者进程中，永不经过网络传输。四个层级提供访问控制，并通过结构而非内容过滤来缩小提示注入攻击面。我们提供基于 XMTP 的开源 Python 实现，跨洲热重连延迟为 1.8-2.9 秒，并提供一个软件工程案例研究：三个代理在各自保留专有分析提示所有权的同时协调一次拉取请求审查。

## Abstract
AI coding agents are evolving from solitary tools into collaborative teammates that discover and invoke one another's specialized skills. But the coordination channel itself can leak a skill's intellectual property. Protocols such as MCP and A2A run implementations server-side, yet they still publish each skill's description and typed schemas to every peer, offer no way to hide a skill's existence, and cannot guarantee that a wrapped system prompt stays off the wire. Application-layer privacy filters help, but act only after the model has decided to emit sensitive text. We take a complementary, protocol-layer route: Skill-as-API, a coordination protocol whose public view of a skill is limited to its name, description, typed input/output schemas, and trust tier. The skill body is closure-captured in the owner's process and never crosses the wire. Four layers add access control and narrow the prompt-injection surface structurally rather than by filtering content. We provide an open-source Python implementation over XMTP with 1.8-2.9 s cross-continent hot-reconnect latency, and a software-engineering case study in which three agents coordinate a pull-request review while each retains ownership of its proprietary analysis prompts.

# 论文总结

## 1. 论文的核心问题与整体含义（研究动机和背景）

论文聚焦于智能体软件工程（Agentic Software Engineering，即 SE 3.0）中的一个核心安全挑战：**当多个 AI 编码代理跨越组织边界协作、并相互调用彼此的专有技能（skill）时，协调通道本身会泄露技能的知识产权（IP）**。

- **背景**：AI 编码代理（如 SWE-agent、OpenHands）正从单机工具演变为跨组织协作的“AI 队友”。一个团队可能希望调用另一个团队封装的专有安全扫描技能或代码审查方法论。
- **现有方案的不足**：
  - MCP 与 A2A 等协议虽然将技能实现放在服务端（不传输代码），但仍向每个对等方公开技能的**名称、描述和类型化 schema**，且**无法隐藏技能的存在**，更不能保证其封装在系统提示词中的方法论不发生泄露。
  - 应用层隐私过滤器（如 PrivacyChecker）只在模型已决定输出敏感内容**之后**才介入，存在约 7–8% 的残余泄露率。
- **核心论断**：需要一种**互补的协议层方案**，从结构上（而非事后过滤）缩小技能知识产权的暴露面。

## 2. 论文提出的方法论

### 2.1 核心思想

**Skill-as-API**：技能对外的公共视图仅包含 `(name, description, routing hint, version, input schema, output schema, minimum trust tier, schema hash)`；而技能主体 `B = (code c, prompt p)` 通过**闭包捕获（closure-capture）** 存在于所有者进程中，**永不跨网络传输**。

### 2.2 核心抽象与保密不变式

- 技能定义为一个元组：`S = (name, d, w, v, σ_in, σ_out, t_min, B)`。
- 调用方式为 `call(S, x) = c(filter(x, σ_in))`，即输入经过 schema 过滤后仅以关键字参数传入。
- 系统提示词 `p` 在**注册时**被代码 `c` 通过闭包引用，不成为函数参数，从输入路径上不可触达。
- 关键保密不变式：**`B ∉ view(S)`**——技能主体永远不会出现在公共视图（传输线缆）上。

### 2.3 四层防御机制

| 层级 | 名称 | 针对威胁 |
|------|------|----------|
| Layer 1 | **信任层 ACL** | T3（信任漂移） |
| Layer 2 | **自动降级** | T3（信任漂移） |
| Layer 3 | **技能隐藏** | T1（技能 IP 提取） |
| Layer 4 | **函数边界防御** | T2（提示词窃取） |

- **Layer 1（信任分层）**：对等方分为 `UNTRUSTED(0) / KNOWN(1) / INTERNAL(2) / PRIVILEGED(3)` 四个信任层。调用技能需满足 `t ≥ S.t_min`，入站消息类型按层门控（如 ping/trust_request 在 UNTRUSTED 即可；discover 需 KNOWN；collab_request 需 INTERNAL；未知类型默认按 PRIVILEGED 拒绝）。
- **Layer 2（自动降级——“一次性信任”）**：信任不因成功使用而累积，而是**衰减**。连续 3 次失败降一层；完成协作 OKR 后降一层（下限为 KNOWN 层）。防止一次性的协作关系演变为永久的开放通道。
- **Layer 3（技能隐藏）**：隐藏技能与不存在的技能返回**完全相同的错误字符串**（`"Unknown skill: X"`），所有者日志中可区分但差异永不跨网络，阻止调用方枚举技能命名空间。
- **Layer 4（函数边界防御）**：调用者输入**只作为具名、schema 过滤后的 kwargs** 绑定到用户轮次，绝不拼接进系统提示词 `p`。由此在结构上关闭了 system-role 拼接攻击向量，但残余的 user-role 注入风险（模型自主复述提示词）仍属内容层问题，不在协议层的声称范围内。

### 2.4 实现

- 开源的 Python 3.10+ 包，运行时零第三方 Python 依赖（标准库即可）。
- 传输层通过 Node.js sidecar 走 XMTP v3（MLS）协议；Python 核心与 bridge 经 localhost HTTP/SSE 通信。
- 16 字节 schema hash 用作快速重连的缓存键。
- 已知局限：信任衰减计数器仅存内存（重启即失），信任层持久化使用原子写入；版本匹配采用精确字符串匹配。

## 3. 实验设计

### 3.1 场景与基准

论文设计了一个**软件工程案例研究**作为端到端验证，而非大规模基准数据集评测：

- 三个代理通过真实 XMTP 通道协调一次**拉取请求（PR）审查**：一个编排代理 + 两个专家代理（代码质量代理、安全代理）。
- 每个专家代理注册专属技能，最低信任层为 KNOWN。

### 3.2 对比方法

## 6. 主要结论与发现

- Skill-as-API 在不依赖 TEE 硬件、不引入显著开销的情况下，**从协议层结构性防止技能主体（代码+系统提示词）跨网络泄露**。
- 函数边界（闭包捕获 + kwargs 绑定）能在该测试中吸收 8 类常见提示注入攻击，使系统提示词在返回字段中保持零出现。
- “一次性信任”（自动降级信任层）机制可有效阻止一次协作关系固化为永久访问通道。
- 基于 XMTP 的实现可达到 1.8–2.9 秒的跨洲热重连延迟，延迟可接受。
- 论文将 Skill-as-API 定位为**MCP/A2A 的补充层方案**（而非替代品），可与传输加密、IAM 及内容层过滤器正交组合。

## 7. 优点

1. **问题选得准、角度新颖**：识别出“协调通道本身即泄露面”这一关键漏洞，提出从 ABI/协议层（而非应用层）治理，对手研究领域有明确的实践意义。
2. **结构性方案优于事后过滤**：其保密不变式（`B ∉ view(S)`）是从协议设计上保证的，不依赖模型行为的不确定性，也不产生加密/MPC 方案的高额开销。
3. **设计目标与威胁模型映射清晰**：G1–G5 与 T1–T3 一一对应，方案与威胁间有清晰的可追溯链路。
4. **对比框架有价值**：将方案与 AgentCrypt、A2A、MCP、PrivacyChecker 等代表不同策略方向的工作进行结构化对比，呈现定位差异而非泛泛的优劣评判。
5. **实现细节透明且可复现**：开源实现 + 对自身局限（内存计数器、精确版本匹配、时序侧信道、跨步骤投毒）的坦率披露增强了可信度。
6. **借鉴了 capability 安全思想**（Capsicum），将“最小可达资源”理念引入代理 ABI。

## 8. 不足与局限

### 实验层面
- **样本量小**：注入测试只有 N=10，无统计学保证；案例仅有一个 PR 审查场景，未覆盖多场景、多负载的压力测试。
- **无对照实验**：未在相同任务条件下量化对比 MCP/A2A/PrivacyChecker 的泄露率与延迟差异。
- **G4 验证混淆了结构性属性与行为性属性**：作者承认“absorbed”既包含了闭包边界的结构性保证，也包含模型不自主复述提示词的行为特性，两者未被解耦测量；且缺少一个对照组（如朴素的字符串拼接技能）。

### 方案层面
- **跨步骤输入投毒（L1）**：编排代理将代码质量代理的输出未加消毒地转发给安全代理，恶意代理可在输出中嵌入恶意内容进行间接投毒。
- **残余提示泄露（L2）**：即使系统提示词不进 system-role 参数，模型仍可能在用户轮次下“自愿”泄露其内容，这是协议层无法直接覆盖的。
- **时序侧信道**：隐藏技能与执行技能的响应延迟差异可能暴露技能存在性。
- **信任管理粒度粗**：按对等方而非按技能控制；并发安全未验证；自动降级计数器仅存内存，重启即失效。
- **共谋与 schema 推断（L5）**：多个被调用方池化观测结果可部分重建 schema 级信息，输入空间探测可推断提示词结构，论文只是缓解而非消除这些残余风险。

### 应用层面
- 传输依赖 XMTP v3 的 MLS 组形成，冷启动延迟 30–60 秒偏长，可能不适合大规模动态编排。
- 作者也承认该方案无法保护调用方自身的 LLM 栈——如果调用方将技能返回结果再输入自己的 LLM，该栈仍面临普通注入风险。
