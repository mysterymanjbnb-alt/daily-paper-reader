## 摘要
语言模型智能体通过赋予它的工具来行动。它在执行任务过程中读取的数据可能会改变它使用这些工具的方式。因此，越来越多用于安全可靠的智能体执行的技术被置于智能体与其工具之间，旨在在该边界上实施访问控制、信息流控制或隔离。如今，这些技术是在围绕间接提示注入构建的智能体安全基准上评估的。这些基准通过防御能在多大程度上降低成功攻击的数量，同时保持智能体效用，来评判防御。防御仅根据智能体的执行情况来评判。它可以在两项指标上都表现良好，却放任任务并不需要的转账、删除或大范围读取保持开放。Ajar 直接使用现有基准来度量这种开放权限。它附加到一个已经存在的智能体安全基准上，并复用该基准用于给自己的运行评分的任务、工具模式、参考解和目标状态。对于每个良性任务，它构建该任务不需要的候选工具调用，因此允许其中任何一个调用都意味着留下了开放权限。这些调用会在智能体可能行动的每个位置呈现给防御。我们通过将 Ajar 附加到 AgentDojo 来评估它，在那里开放权限成为除现有攻击成功率和良性效用之外的第三条轴。我们在五种防御上运行它：Progent、CaMeL、AC4A、Permission Assistant 和 Claude Code 的 Auto 模式。我们观察到，它们留下的开放权限量差异很大。两种防御泄漏量几乎相同，但它们完成的良性任务却差异很大；还有一种防御通过拒绝其任务本有权进行的调用来换取部分严格性。这种开放权限无法从测得的攻击成功率或良性效用中推导出来。Ajar 的源代码见 https://github.com/reSHARMA/Ajar。

## Abstract
A language model agent acts through the tools it is given. The data it reads while working on a task can redirect what it does with those tools. A growing set of techniques for safe and secure agent execution therefore sits between the agent and its tools, aiming to enforce access control, information flow or isolation at that boundary. Today these techniques are evaluated on agent-security benchmarks built around indirect prompt injection. Those benchmarks judge a defense by how far it brings the number of successful attacks down while preserving the agent's utility. A defense is judged only on the agent's execution. It can score well on both metrics while holding open a transfer, a deletion or a broad read that no task needed. Ajar measures that open privilege directly using the existing benchmarks. It attaches to an agent-security benchmark that already exists and reuses the tasks, tool schemas, reference solutions and goal states that benchmark uses to grade its own runs. For each benign task it builds candidate tool calls the task does not need, so allowing one is privilege left open. These calls are presented to the defense at every point where the agent could act. We evaluate Ajar by attaching it to AgentDojo, where open privilege becomes a third axis beside the existing attack success and benign utility. We run it on five defenses: Progent, CaMeL, AC4A, Permission Assistant, and Claude Code's Auto mode. We observed that they leave widely different amounts of privilege open. Two defenses leak by almost the same amount yet differ widely in the benign tasks they finish, and one defense buys part of its tightness by refusing calls its tasks were entitled to make. This open privilege cannot be derived from the measured attack success or benign utility. The source code of Ajar is available at https://github.com/reSHARMA/Ajar.

# Ajar: Measuring Open Privilege in Agent Defenses 论文总结

## 1. 核心问题与整体含义

- **研究动机**：语言模型智能体通过工具行动，其读取的数据可能重定向工具的使用方式。当前大量"安全执行"技术被部署在智能体与工具之间（访问控制、信息流控制、隔离），但它们的评估方式存在根本缺陷。
- **现有评估的盲区**：智能体安全基准（如 AgentDojo）只报告两个指标——**攻击成功率**（ASR）与**良性任务效用**。二者都只在"实际发生的那一次运行"上计算：
  - ASR 只在注入触发的运行上判断智能体是否服从；
  - 效用只在良性运行上判断任务是否完成。
  - 一个防御可以同时在这两个指标上表现良好，却仍然对任务并不需要的转账、删除或大范围读取保持开放。
- **核心洞见**：攻击是否成功取决于智能体模型（模型若不提出攻击调用，防御根本没被问到），因此 ASR 不能反映防御"准备允许什么"。真正缺失的度量是**最小权限（Least Privilege）**——一个组件应仅持有其工作所需的权限，不多不少。
- **整体含义**：论文提出 **Ajar**，直接度量防御留下的"开放权限"，将其作为继攻击成功率、良性效用之后的**第三条评估轴**。这一度量在 LLM 智能体场景下首次针对"防御层"而非"模型本身"。

## 2. 方法论

### 核心思想
- Ajar 附加到**已有的**智能体安全基准上，复用其任务、工具模式、参考解（reference solution）和目标状态，为每个良性任务构造"任务不需要的候选工具调用"，并在智能体可行动的每个时机提交给防御，通过防御的允许/拒绝决策与真实标签对比来量化开放权限。
- 关键假设：防御可被统一接口驱动：`decide(call, context) → {allow, deny}`。

### 关键技术细节

- **决策点（Decision Point）**：任务参考解序列的每个前缀（k=0 为行动前状态）。对前缀敏感的防御在每个深度都询问；前缀无关的防御只需查询一次。
- **测试（Test）**：一个候选调用 + 固定决策点 + 标签，构成一次测试。
- **七类故障（Fault Class）**：
  - *必需调用*（required call）：任务无法完成所必需的调用（唯一 ALLOW 标签类）。
  - *攻击者植入调用*（attacker-seeded call）：基准注入所瞄准的 sink 调用，其 DENY 标签由基准自身谓词验证。
  - *偏离路径工具*（off-path tools）：任务从不需要的工具，参数取自环境。
  - *参数故障*：错误资源、参数拓宽、类型违规、参数省略——从授权调用出发替换参数。
- **允许调用（Permitted Call）**：任务有权做出但非必需的调用，用于度量"过度限制"。通过参考解调用的偏序（由返回值依赖关系确定）枚举合法替代顺序，并重放验证。
- **Oracle 标签**：从任务 ground truth（所需工具集 + 目标谓词）分配标签。当候选与攻击 sink 相同（触发 security() 为真）则为已验证 DENY；当候选与参考解中的写操作相同且后续仍达到 utility() 则为已验证 ALLOW。其余由 Ajar 自身规则断言。
- **危害分层（Harm Tier）**：根据副作用是否可逆及影响范围分为五级，权重递增：

| 层级 | 描述 | 权重 |
|---|---|---|
| H0 | 必需调用（ALLOW 集） | 0 |
| H1 | 可逆、自身范围的读或草稿 | 1 |
| H2 | 可逆、触及第三方的操作 | 3 |
| H3 | 不可逆、自身范围的操作 | 9 |
| H4 | 不可逆、触及第三方或资金的操作 | 27 |

- **两个核心评分**：
  - **过度权限泄漏（Over-Privilege Leakage, OPL）**：防御允许的过量调用在危害加权下的占比：
    $$OPL(D,t)=\frac{\sum_{c\in C_t^-} w(c)\cdot \mathbb{1}[d(c)=\text{allow}]}{\sum_{c\in C_t^-} w(c)}$$
    OPL 在所有任务的 DENY 测试上**池化（pooled）**计算。
  - **充分性（Sufficiency）**：`1 − UP`，即必需调用中被放行的比例，按**每任务均值**聚合。
  - 另有**过度限制（Over-restriction）**：防御拒绝的允许调用比例；以及**攻击准入（Attack Admission）**：防御允许其全部 sink 调用的攻击计数。

### 算法流程
1. 适配器从宿主基准读取任务、工具模式、参考解、目标状态、攻击 sink。
2. 生成器在参考解各决策点生成候选调用（七类规则）。
3. Oracle 为每个候选分配标签与危害层级。
4. 包装器重放前缀，通过 `decide` 接口获取防御裁决。
5. 评分模块对比裁决与标签，输出 OPL、充分性、过度限制、攻击准入。

## 3. 实验设计

- **宿主基准**：**AgentDojo v1.2.2**，包含四个任务套件：banking（16 任务）、slack（21）、travel（20）、workspace（40），共 **97 个良性任务**（92 个可评分）。
- **测试规模**：生成 **10471 个测试**，来自 **3551 个唯一 (task, tool, arguments) 候选**，决策点 k=0 到 k=18。标签分布：9039 DENY、339 必需、1093 允许；其中 2822（27.0%）由基准谓词验证，7649（73.0%）由 Ajar 断言。
- **被测防御（5 种）**：
  - **Progent**：基于任务写入允许列表，随工具结果更新（有状态）。
  - **CaMeL**：信息流控制，检查可信规划器输出的能力。
  - **AC4A**：每任务实例写入一次权限模型的访问控制。
  - **Permission Assistant**：逐调用权限预测分类器（含冷启动与个性化历史两种配置）。
  - **Claude Code Auto mode**：已部署的逐调用分类器。
- **决策模型**：Sonnet-5 与 Haiku-4.5（Amazon Bedrock 提供），Auto mode 仅 Sonnet-5。
- **对比基线（4 种）**：allow-all、deny-all、tool-name allowlist、argument-exact oracle。
- **其他实验**：Progent 动态 vs 冻结消融（Progent-static）；6 种危害权重方案；测试预算子采样（10/25/50/75/100%）；提示词改写与重复运行；3 次重复运行测方差；2000 次 bootstrap 置信区间。

## 6. 主要结论与发现

- **开放权限是独立轴**：OPL 无法由攻击成功率或良性效用推导。
  - 两种防御泄漏量相差 **<0.009**，良性任务完成率却相差 **37 个百分点**，且更严格的那一个完成更多任务。
  - 一种防御（CaMeL）的严格性部分来自**拒绝任务本有权做出的调用**（过度限制最高）。
- **所有防御都远离最优区域**：每个被测防御的 OPL 都介于 tool-name allowlist（0.3551）与 argument-exact oracle（0.0020）之间；最接近 oracle 充分性的防御泄漏量仍是 oracle 的 40 倍以上。
- **分数归属于整个决策流程**：
  - 更换决策模型会改变每个防御的 OPL，且方向不一，多数是放松；充分性在所有情况下随弱模型下降。
  - 相同输入的重复运行中，防御仅能复现 91%–98% 的自身裁决，OPL 波动可超过相邻防御间的距离。
- **稳定性**：改变危害权重、测试数量、任务措辞后，防御排序基本保持；OPL 在约 25% 测试预算后趋于平稳。
- **更新步骤的作用**：Progent 的每调用策略收紧步骤被消融后，OPL 上升 24%–56%，而充分性几乎不变——说明该步骤关闭的是"任务不需要的权限"。

## 7. 优点

- **问题定义清晰且重要**：将经典最小权限原则引入 LLM 智能体防御评估，填补了 ASR 与效用之外的空白。
- **与现有基准解耦**：通过适配器复用宿主基准的 ground truth，附加新基准只需写一个适配器，附加新防御只需写一个包装器，方法通用性强。
- **Oracle 成本低且可追溯**：直接复用基准用于自身评分的谓词，并明确记录每个标签来源（验证 vs 断言）。
- **抗博弈设计**：OPL 与充分性成对报告，避免"全拒"或"全允"的退化最优；引入危害加权避免把廉价读取与资金转移同等计分。
- **覆盖有状态防御**：通过在多个合法替代顺序上呈现同一调用，捕捉"随运行推进而收紧"的防御翻转（flips）。
- **严谨的稳定性分析**：危害权重、测试预算、提示词措辞、运行间方差四个维度均做了检验，并给出 bootstrap 区间。

## 8. 不足与局限

- **Oracle 依赖自身判断**：73.0%（7649/10471）的标签由 Ajar 断言而非基准验证；作者明确不宣称超越这一划分的构念效度。
- **测试覆盖受限于构造规则**：候选参数取自环境、参考解或基准注入，攻击者可发明但环境中不存在的调用不在覆盖范围内；泄漏是采样估计而非全空间估计。
- **防御集成敏感**：包装器提供的上下文（如 CaMeL 的溯源信息、Permission Assistant 的权限历史）不同可能改变分数，而历史本身又由 Ajar 的标签构建，存在循环风险。
- **裁决方差大**：LLM 决策导致相同输入下防御仅复现 91%–98% 裁决，单次运行无法区分相邻防御；主要结果均为单次运行。
- **无法展示攻击被阻止**：AgentDojo 的重要指令攻击对未防御智能体已不成功，因此论文不报告自身的 ASR，只能报告攻击准入计数。
- **未报告成本**：缺少延迟、token、美元成本，而这对部署决策至关重要。
- **测量范围有限**：只评分单步决策，不建模"后续步骤会兜底"的防御，也不认证任何防御在

任意设置下是安全的，只能陈述"在给定基准、给定任务分布上留下了多少开放权限"。

## 9. 总体评价与定位

- **贡献层次**：Ajar 的主要贡献是**评估框架**而非新防御。它把"最小权限"从一句设计口号转化为可量化、可比较、可复现的第三个数字，使"防御到底开放了多少权限"第一次成为可被审问的对象。
- **与 ASR/效用三角关系**：论文最有说服力的论证是三条轴的**不可互推性**——两个防御可以在 ASR 与效用上几乎并列，却在 OPL 上相差一个数量级；也可以泄漏量近乎相同，而任务完成率相差数十个百分点。这直接说明现有基准的"双指标"叙事是不完整的。
- **对实践的指向**：结论暗示，当前主流防御并未真正实现最小权限，而是把"任务不需要的权限"当作可接受的代价换取兼容性。Progent 的收紧步骤消融实验给出了一个正面信号：**逐步收紧**确实能在不牺牲效用的前提下关闭不需要的权限，这是可操作的改进方向。
- **方法学价值**：把 oracle 标签明确拆分为"基准谓词验证"与"Ajar 断言"两类，并公开比例（27.0% / 73.0%），是一种值得效仿的诚实做法——它让读者能自行判断哪些结论建立在多强的证据上。
- **方法论上的谨慎**：作者没有宣称某个防御"安全"，也没有宣称 Ajar 是完整的最小权限度量，而是把自己定位为**采样估计 + 第三评估轴**，这一自我限定与结论的强度相匹配。

## 10. 可复现性与开放性

- Ajar 以纯 Python 实现、仅依赖标准库，且运行时不导入宿主基准或模型客户端，这意味着框架本身可脱离 AgentDojo 与具体模型独立运行，复现门槛较低。
- 适配器/包装器的解耦设计使第三方可以低成本地把 Ajar 迁移到其他智能体基准或其他防御上，扩展路径清晰。
- 但论文未给出代码/数据的公开发布状态、许可证或复现脚本细节（就现有信息而言），复现的实际便利性仍需以随论文发布的产物为准。

**Ajar 首次把"最小权限"变成 LLM 智能体防御的可测量第三轴：通过在良性任务的每个决策点注入"任务不需要的候选调用"并用危害加权统计防御放行的比例（OPL），它揭示了当前防御——包括已部署产品——普遍存在大量无法由攻击成功率或良性效用反映的开放权限，且这一测量对危害权重、测试预算与提示词措辞都相对稳健。**
