## 摘要
智能体系统越来越多地通过针对文件、服务和外部资源的多步工具工作流来满足用户请求。在这些工作流中，孤立的逐调用检查可能会漏掉一种工作流级故障：每次调用可能在局部是可允许的，但整个序列可能超出为会话建立的授权边界。我们将这种故障模式称为“授权漂移”。为了解决这一问题，我们提出运行时授权一致性检查（RAC），一种位于控制器侧工具调用边界的轻量级防护机制。RAC 将授权视为由已接受工作流步骤携带的运行时状态。对于每个待处理动作，它从控制器观测到的元数据中重建可信授权事件，并且仅当该调用仍然不比通过已接受谱系继承的授权依据更宽松时，才允许该调用。被拒绝的步骤会从谱系中排除，因此后续延续只能从已接受的工作流历史中获得支持。我们的评估表明，RAC 在受控工作流和规划器生成的工作流中都减少了漏检的授权漂移。在包含 1,248 个工作流的 TraceBench 套件上，RAC 没有漏拦案例，而最强的 Static+History 基线在 1,008 个 oracle-BLOCK 工作流中漏掉了 509 个。在盲式 LLM 生成计划的高置信度可观测子集上，RAC 达到 92.8% 的拦截召回率，而最强基线为 68.8%。在真实 MCP 文件系统规划器回放中，RAC 在服务器执行前阻止了九个不安全的后续操作，且 p99 检查延迟为亚毫秒级。

## Abstract
Agentic systems increasingly fulfill user requests through multi-step tool workflows over files, services, and external resources. In these workflows, isolated per-call checks can miss a workflow-level failure: each call may be locally admissible, but the sequence can exceed the authorization boundary established for the session. We identify this failure mode "authorization drift." To address this problem, we present Runtime Authorization Consistency Checking (RAC), a lightweight guard at the controller-side tool-call boundary. RAC treats authorization as runtime state carried by accepted workflow steps. For each pending action, it reconstructs a trusted authorization event from controller-observed metadata and admits the call only when it remains no more permissive than the basis inherited through accepted lineage. Rejected steps are excluded from lineage, so later continuations can draw support only from accepted workflow history. Our evaluation shows that RAC reduces missed authorization drift across both controlled and planner-generated workflows. On the 1,248-workflow TraceBench suite, RAC has no missed-block cases, while the strongest Static+History baseline misses 509 of 1,008 oracle-BLOCK workflows. On a high-confidence observable subset of blind LLM-generated plans, RAC reaches 92.8% block recall, compared with 68.8% for the strongest baseline. In the real MCP filesystem planner replay, RAC stops nine unsafe continuations before server execution, with sub-millisecond p99 checking latency.

# 论文总结：Runtime Authorization Consistency Checking for MCP-based Agentic Workflows

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：基于大语言模型的智能体越来越多地作为规划器，将用户请求分解为多步工具调用，并通过 MCP（Model Context Protocol）等协议访问外部工具。用户级任务由此被展开为运行时动态扩展的工作流，甚至可进一步委派给其他智能体或专用组件。
- **核心问题**：现有的逐调用（per-call）访问控制只检查单个动作是否在本地可执行，但忽略了一种工作流级故障——**授权漂移（authorization drift）**。即：每一次工具调用在局部都合法，但整个调用序列逐步累积后，超出了会话初始任务所授予的授权边界。
- **典型场景**（论文图 1）：企业助手拥有日历、邮件、内部消息工具的常备权限，但用户仅授权“查看日历以寻找可用会议时段”。智能体先读日历（允许），随后搜索相关邮件、起草并发送改期邮件——这些后续调用在本地工具权限下仍可执行，却已超出原始任务范围，构成资源漂移、动作漂移与外部联系漂移。
- **问题本质**：授权不是一次性入口决策，而是需要随工作流演化持续保持的一致性属性。近期多机构网络安全指南也警告了智能体广泛/无限制访问、权限提升与范围蔓延的风险。
- **研究意义**：论文将授权漂移形式化为一个工作流级安全失效模式，并主张在控制器侧的工具调用边界上进行运行时一致性检查，而非依赖孤立的逐调用授权。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想

- 提出 **RAC（Runtime Authorization Consistency Checking）**，一个位于工作流控制器（或工具网关）侧、工具调用提交前的**轻量级预提交防护（pre-commit guard）**。
- 将授权建模为**由已接受工作流步骤携带的运行时状态**（authorization basis）：每个待执行调用只有在“不比从已接受谱系继承的授权依据更宽松”时才被放行。
- 被拒绝的步骤**不进入谱系**、不产生后继状态，因此后续延续只能从已接受的执行历史中获得授权支持。
- RAC 不修改 MCP 协议与服务器端工具实现，部署在控制器侧调用边界。

### 2.2 形式化模型

- 工作流建模为授权相关事件序列 \(W = \langle e_1, e_2, \dots, e_n \rangle\)，每个事件在控制器中介的预提交边界被观测。
- 每个会话始于已认证主体和初始授权包络（grant envelope）\(G\)，定义初始授权边界。
- **运行时授权一致性谓词**（公式 1）：
  \[
  Consistent(e_i) \equiv LocalAllow(e_i) \wedge ValidOrigin(e_i) \wedge [\text{根情形} \vee \text{延续情形}] \wedge NoMorePermissive(e_i, B^-_i)
  \]
  其中包含：本地访问控制结果、资源来源有效性、根事件（从 \(G\) 初始化，前驱为 \(\perp\)）或延续事件（谱系有效）、以及工作流级的“不比继承依据更宽松”检查（覆盖动作、资源、目的、委派、条件五个维度）。
- 整个工作流一致当且仅当每个已提交的授权相关事件在其预提交边界满足该谓词。

### 2.3 关键技术组件（RAC 四步流程）

1. **可信授权事件构建（Event Construction）**：
   - 将规划器提议（工具选择、参数、解释）视为**非权威的提案数据**；由事件适配器从控制器观测到的运行时证据（会话授权、清单类型化参数、注册资源、已验证锚点）重建授权相关视图。
   - **来源纪律**（表 I）：主体来自已认证会话；工具来自控制器边界；动作来自工具清单；资源来自类型化参数与注册资源 ID；目的归一化为受控令牌；委派来自授权包络；条件来自授权约束与运行时元数据；输入锚点必须由控制器验证；前驱来自谱系存储。自由文本、工具自述、智能体声明的动作标签/前驱提示仅作诊断元数据，不能单独作为授权证据。
   - 若必需字段无法落地，事件构建失败，步骤被拒绝（fail-closed）。

2. **锚点与资源来源验证（Anchor & Resource-Origin Verification）**：
   - 锚点验证（公式 2）：声称的锚点只有在其生产者匹配、内容哈希与控制器观测输出一致、声称资源集是观测资源子集、模式被工具清单接纳时，才成为已验证锚点。
   - 资源来源验证（公式 3）：每个被引用资源必须属于授权范围，或由已验证输入锚点携带；仅注册表存在性不等于授权来源。

3. **控制器解析的因果谱系（Controller-Resolved Causal Lineage）**：
   - 维护仅追加的谱系存储，记录绑定会话、顺序、前驱、已验证输入/输出锚点、操作、依据指针的哈希链记录（公式 4、5）。
   - 前驱从已验证输入锚点和谱系记录解析；原型要求所有已验证输入锚点解析到**同一会话中的同一已接受前驱**，否则（缺失、跨会话、歧义、哈希不匹配）判为谱系违规并阻断。

4. **授权依据传播与收紧（Basis Propagation & Tightening）**：
   - 根事件依据由 \(G\) 初始化；延续事件加载前驱依据 \(B^-_i = LoadBasis(pred_i)\)（公式 6）。
   - 放行后生成收紧的后继依据 \(B_i = Tighten(B^-_i, Obs(e_i))\)（公式 7）：动作、资源、目的、条件各维度取交集，无更窄配置则保留继承依据；任一维度为空或不兼容则阻断（公式 8）。
   - 动作覆盖关系 \(\preceq_{act}\) 由部署清单定义、保持无环、对缺失标签 fail-closed。

5. **预提交一致性检查与决策（Pre-commit Checking & Decision）**：
   - 规则族（表 II）：LineageOK、OriginOK、SubjectOK、ActionOK、ResourceOK、PurposeOK、DelegationOK、ConditionOK。
   - 决策映射（公式 10）：违反集非空则 BLOCK，否则 ALLOW。BLOCK 不写谱系与后继依据；ALLOW 则写入谱系与收紧依据。

### 2.4 安全论证

- 通过 5 条引理（事件字段可靠性、来源可靠性、谱系可靠性、依据单调性、被阻断事件的状态排除）证明定理 1：在信任假设下，每个被 RAC 放行并提交的事件都满足一致性谓词；被阻断事件不能成为后续延续的授权证据。

## 5. 实验数量与充分性

- **实验规模**：围绕四个研究问题（RQ1–RQ4）展开，覆盖受控规格工作负载、盲式 LLM 计划回放、真实 MCP 文件系统强制、组件级延迟测量四类实验；基线对比包括 5 种方法。

  - 优点：规格工作负载 + 盲式 LLM 生成 + 真实 MCP 边界 + 延迟测量四层验证，覆盖较全面；oracle 标签与实现输出分离，评测在同一证据与 oracle 决策下进行，较为客观。

## 6. 主要结论与发现

- **授权漂移是一种真实且被现有防御遗漏的工作流级失效模式**：工具白名单与资源历史检查只能覆盖可见的动作/资源扩张，对目的保持、运行时条件、委派约束、输出锚点与谱系有效性等维度无能为力。
- **RAC 在受控工作负载上无漏拦**：在 TraceBench 的 1,008 个 oracle-BLOCK 工作流上零漏拦，而最强基线漏拦 509 个。
- **RAC 在盲式 LLM 生成计划上保持较高拦截能力**：高置信度可观测子集上阻断召回率 92.8%，显著优于最强基线 68.8%；剩余漏拦集中在证据可见性受限的谱系/来源案例。
- **RAC 能在真实 MCP 边界阻止不安全副作用**：在服务器执行前阻断调用，防止了 No RAC 会产生的 5 个不安全文件系统副作用。
- **开销极低**：步骤级 p99 检查延迟 0.377 ms，亚毫秒级，适合在线运行。
- **总体结论**：RAC 以极低开销在控制器侧拦截工作流级授权漂移，将“继承的授权支持”在每次延续处显式化，与本地授权和智能体安全防御互补。

## 7. 优点

- **问题识别新颖且切中要害**：清晰定义“授权漂移”这一被逐调用检查忽略的工作流级失效模式，并给出形式化谓词与威胁模型。
- **信任边界设计严谨**：将规划器文本、工具自述、智能体声明的前驱/委派/条件均视为非权威诊断信息，安全关键字段只从控制器观测证据落地，符合“模型面向文本不应单独决定安全决策”的经验。
- **机制轻量、非侵入**：不修改 MCP 协议与服务器端工具，仅部署在控制器侧调用边界；原型基于内存存储，易于替换为持久化存储而不改变语义。
- **形式化安全论证**：通过 5 条引理与定理 1 的归纳证明，给出被提交事件的一致性保证，且被阻断事件不进入谱系。
- **多维度规则族**：覆盖谱系、来源、主体、动作、资源、目的、委派、条件八个维度，防止仅靠工具可用性或资源历史导致的漏检。
- **实验设计层次分明**：规格工作负载 + 盲式 LLM 计划回放 + 真实 MCP 文件系统 + 延迟测量，且 oracle 标签与实现输出分离，评测公平性较好。
- **明确的失败关闭策略**：证据缺失、歧义前驱、缺失标签等均 fail-closed，避免不安全放行。

## 8. 不足与局限

- **算力信息缺失**：论文未报告 GPU 型号、数量、训练时长等资源信息（RAC 本身无需训练，但 LLM 生成计划的具体模型与资源未披露）。
- **真实世界漂移频率未验证**：作者明确表示评估验证的是语义强制，而非真实部署中的漂移发生率；TraceBench 为合成工作负载。
- **单一前驱限制**：当前原型采用保守的单前驱模型，无法支持良性的多源合并（如汇总多份独立授权报告）；歧义或多前驱延续默认被阻断，可能造成过度阻断，需要显式合并策略。
- **证据可见性依赖**：RAC 依赖足够的结构化运行时证据构建类型化事件与解析谱系；RQ2 的剩余漏拦即源于生成计划引用了信任状态证据不完整的先前笔记或派生锚点。
- **边界依赖**：RAC 仅覆盖通过控制器中介边界的授权相关动作；绕过边界的动作或隐藏副作用不在其保证范围内，需要沙箱、受监控工具包装或出口控制补充。
- **配置依赖**：动作覆盖关系与清单映射需由部署定义且必须可审计；错误映射会削弱强制效果，缺失标签 fail-closed。
- **不评估授权包络本身的最小权限性**：RAC 保持与所提供的授权包络一致，但不证明该授权包络是最小权限的；意图语义完整性与授权修复由外围组件负责。
- **评测规模有限**：RQ2 仅报告高置信度子集（排除歧义自然语言锚点），RQ3 回放语料规模较小（14 个计划），泛化性与真实场景覆盖仍待扩展。
