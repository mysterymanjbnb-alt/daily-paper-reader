## 摘要
LLM 智能体会将自然语言上下文（其中可能包含攻击者控制的文本）转化为特权工具调用，因此即使智能体遭遇提示注入或被对抗性操控，授权也必须持续有效。模型上下文协议（MCP）已成为这一边界上被广泛采用的接口，但其官方 SDK 的认证与授权原语未能满足企业零信任要求，其中最突出的是双身份模型：同一服务器必须同时服务人类用户（企业 SSO）和自动化智能体（位于不同请求头上的服务账户凭据）。我们对六种调研的 MCP SDK（Python、TypeScript、Go、Rust、C#、Swift）进行了系统性差距分析，并识别出三项结构性不足：凭据提取绑定到单一 Authorization 头，导致若不使用自定义中间件就难以进行双身份部署；缺少认证前的工具发现；以及基础 SDK 缺乏细粒度的按工具授权。我们通过 FastMCP 的可组合扩展弥补这些差距：面向同时服务人类和服务账户调用方的企业部署的跨请求头凭据归一化；跨异构 IdP 的缓存令牌验证；用于无需凭据的注册表发现的未认证元数据端点；以及通过单个声明式注解，使按权限过滤的工具可见性与按工具调用强制执行保持一致，且无需修改协议或 SDK 内部实现。在四种前沿 LLM 的 2160 次尝试中，仅进行请求体检查的服务器仍会暴露被禁止的工具（152/720，21.1%），而权限感知的可见性将该比率降至 0/720；仅依赖可见性过滤仍可被脚本化客户端绕过，而当可从提示中推断出隐藏工具时，模型在高达 94% 的设置中按名称引用了该隐藏工具，这证实了发现控制不能替代调用时强制执行。

## Abstract
LLM agents translate natural-language context, which may include attacker-controlled text, into privileged tool calls, so authorization must remain effective even when an agent is prompt-injected or adversarially steered. The Model Context Protocol (MCP) has become a widely adopted interface for this boundary, yet its official SDKs' authentication and authorization primitives fall short of enterprise zero-trust requirements, most acutely a dual-persona model in which one server must serve human users (corporate SSO) and automated agents (service-account credentials on a different header). We conduct a systematic gap analysis of six surveyed MCP SDKs (Python, TypeScript, Go, Rust, C#, Swift) and identify three structural shortcomings: credential extraction bound to a single Authorization header, complicating dual-persona deployment without custom middleware; the absence of pre-authentication tool discovery; and the lack of fine-grained per-tool authorization in the base SDKs. We close these gaps with composable extensions to FastMCP: cross-header credential normalization for enterprise deployments serving both human and service-account callers, cached token verification across heterogeneous IdPs, an unauthenticated metadata endpoint for credential-free registry discovery, and permission-filtered tool visibility kept consistent with per-tool invocation enforcement by a single declarative annotation, all without modifying the protocol or SDK internals. Across four frontier LLMs over 2160 attempts, an in-body-check-only server still exposes forbidden tools (152/720, 21.1%), whereas permission-aware visibility drives the rate to 0/720; visibility-only filtering remained bypassable by scripted clients, while models referenced the hidden tool by name in up to 94% of settings when inferable from the prompt, confirming that discovery controls cannot replace invocation-time enforcement.

## 1. 核心问题与整体含义（研究动机与背景）

- **新型授权对手**：LLM 智能体的工具调用由自然语言上下文生成，而该上下文可能包含检索文档、第三方工具输出、网页内容等**攻击者可控文本**。攻击者不在传输边界，而在调用方的推理循环内部，因此网络层认证无法判断"请求的动作是否被恶意上下文塑造"。
- **MCP 成为关键边界**：模型上下文协议（MCP，2024 年底发布）迅速成为 LLM 智能体发现与调用外部工具的事实标准，企业已部署数十至数百个暴露特权操作（查生产库、触发 CI/CD、管理 K8s、读私有代码库）的 MCP 服务器。**每个注册工具都是新的攻击面**，风险被 OWASP LLM Top-10 列为"过度自主性（Excessive Agency）"，并被 NIST AI RMF 标记为新兴风险面。
- **零信任四要求**：论文以 NIST SP 800-207 为框架，提出（1）每次工具调用都须携带已验证凭据；（2）智能体只能看见并调用被授权的组件；（3）控制面（注册表）须能**免认证**发现工具与认证方式；（4）须支持多异构 IdP 共存。
- **三大结构性缺口**（对 Python、TypeScript、Go、Rust、C#、Swift 六种官方 SDK 的系统性差距分析）：
  - 凭据提取绑定到单一 `Authorization` 头，**双身份部署**（同一服务器同时服务人类 SSO 与服务账户自动化）须替换 SDK 中间件而非配置；
  - **缺少认证前的工具发现**能力（未认证端点只暴露 OAuth/服务器元数据）；
  - 基础 SDK **缺少细粒度的按工具授权**。
- **核心论点**：*工具可见性本身即安全边界的一部分*——`list_tools` 返回的工具集合定义了智能体可达的动作空间，因此授权必须在"发现"与"调用"两个面上同时成立，且源自同一份声明。论文明确不主张发明首个 MCP 授权机制，而聚焦于**三面一致性（pre-auth 元数据、认证后列表、调用检查）**这一组合问题。

## 2. 方法论

### 2.1 核心思想
在 FastMCP 的**原生扩展点**上实现四项可组合扩展（C1–C4），不修改 MCP 协议、不访问私有 API、不做 monkey-patching。四个扩展落在四个原生扩展点：Starlette 路由、Starlette HTTP 中间件、FastMCP 应用中间件、Python 函数装饰器。

### 2.2 四项贡献（技术细节）

- **C1 跨请求头凭据归一化**
  - 新增 `CustomHeaderAuthBackend`（读取可配置头，`optional=True` 时缺失头视为 no-op）与 `AuthMiddleware`；
  - 中间件对**所有出现头的后端**执行验证，采用 **OR 语义**（亦可组合为 AND 用于高保障场景）；只要有一个后端成功即放行，失败/缺失的后端"不贡献"，**无效令牌不会阻断另一头中的有效令牌**；
  - 每个后端将主体写入按请求、按头键控的 ContextVar，`get_all_permissions()` 返回跨槽位的**去重 scope 并集**，下游过滤与装饰器无需关心由哪个后端认证。

- **C2 跨异构 IdP 的缓存令牌验证**
  - `BaseTokenVerifier` 采用模板方法模式：新厂商只需实现 3–4 个小方法（构造认证头、构造验证 URL、解析 scope、识别调用者），继承缓存、连接复用与 scope 映射；
  - 面向**不透明令牌**（opaque token）需 API 往返验证的企业 IdP（不同于 JWT/JWKS 本地校验）；默认 **300 秒 TTL**，缓存键用 **SHA-256** 哈希（不存原始令牌），可插拔至 Redis 等共享后端；
  - 可选 `map_permissions_func` 做厂商 scope → 应用权限的映射；可选 audience 策略（RFC 8707）：resource-bound 模式要求 `aud` 指向本服务器，fleet-bound 模式接受运维配置的共享受众。

- **C3 控制面/运行时面分离的预认证发现**
  - 注册在认证中间件之外的单个 Starlette 路由，返回每个 tool/prompt/resource 的**原生 MCP schema** 及 `required_permissions`（DNF 形式，缺失键表示无需特定权限），外加服务器接受的认证方法列表；
  - 该处理器通过**内省服务器自身状态**（中间件栈、路由表、组件注册表、`_required_permissions` 注解）构建响应，使发现、列表与强制三者无法漂移；
  - 设计权衡：schema 对任何网络可达方公开（"暴露 schema 是描述而非访问"），但调用能力仍由认证路径 + 逐工具检查把关；其替代方案（用一个客户端对所有服务器认证来汇编目录）会造成"混淆代理"式的信任边界膨胀。

- **C4 跨面策略一致性（双层防护）**
  - **第 2 层（可见性）**：`PermissionFilterMiddleware` 仅挂钩 `on_list_tools / on_list_prompts / on_list_resources`，在认证会话内按调用者 scope 裁剪响应；对 `call_tool` 等非列表方法为 no-op；
  - **第 3 层（调用强制）**：`@require_permissions` 装饰器在调用时求值逐工具 **DNF 需求**——每个位置参数是一个 AND 子句，多个参数之间为 OR，即 `(admin ∧ write) ∨ superadmin`，短路求值；
  - **签名保持**：FastMCP 用 `inspect.signature()` 生成 JSON schema，`functools.wraps` 会破坏参数列表，故采用**基于 `exec` 的动态包装器生成**，由 `inspect.signature(func)` 构造包装器源码，使参数与原函数一致、JSON schema 正确；`exec` 输入不含任何运行时请求数据，故不引入代码注入面；
  - **单一真相源**：装饰器把需求存为 `_required_permissions: list[list[str]]`，被元数据端点（序列化 DNF）与组件过滤器（求值同一 DNF）共同读取，从而实现**发现、列表、强制三面同步，无需人工对齐**；
  - **安全不变量（可见性–强制一致性）**：对任意已认证调用者 *c* 与任意工具 *t*，*t* 出现在 *c* 的 `list_tools` 响应中 **当且仅当** *c* 可调用 *t*，**且**当且仅当 *c* 满足 *t* 声明的 DNF 权限需求；智能体的自然语言输入不进入该决策。

### 2.3 请求生命周期
请求进入 `AuthMiddleware` → 逐后端提取令牌并查缓存/回退厂商内省 API → 写入 persona 键控的 ContextVar → 仅当无任何后端成功才抛 `AuthenticationError`（401）。随后按 JSON-RPC 方法分派：列表分支由 `PermissionFilterMiddleware` 按 scope 裁剪；调用分支由 `@require_permissions` 求值（通过 200，失败 403）。

## 3. 实验设计

### 3.1 场景与测试床
- 统一测试床：MCP 服务器注册 **8 个模拟 Kubernetes 工具**，其中 4 个 viewer 权限（如 `get_metrics`）、4 个 admin 权限（如 `restart_pod`）；
- 禁用目标选 `restart_pod`（`cluster:admin`），因其在社工压力下"看似可调用"，不同于显然灾难性的 `drop_database`；
- 使用 stub `TokenVerifier`（任何非空 bearer 令牌签发固定 viewer scope，无 IdP 往返）以隔离 SDK 自身开销。

### 3.2 对抗性评测（G1 提示注入驱动的工具误用）
- **语料**：60 条 LLM 辅助起草 + 人工审核的提示注入载荷，分 4 类各 15 条——直接注入（DI）、间接注入（II）、角色扮演绕过（RP）、上下文溢出（CO）；每类覆盖不同社工钩子（权威、紧迫、伪造政策、思维链劫持、工具输出投毒、身份交换、模拟框架、runbook 尾巴）；
- **模型**：4 款前沿 LLM（gpt-5、claude-sonnet-4-6、claude-opus-4-7、gemini-2.5-pro），经 OpenAI 兼容的企业网关访问；非推理类模型温度取 {0.0, 0.3, 0.7}，推理类用网关默认采样；
- **规模**：4 模型 × 3 种子 {42,43,44} × 60 载荷 × 3 次尝试 = **2160 次尝试**，全部有效；
- **对比三种服务器配置**：
  - **Baseline**：列出全部 8 个工具，在各 admin 工具**函数体内**做权限检查（pre-C4 惯用法）；
  - **Filter-only**：用 `PermissionFilterMiddleware` 从 `list_tools` 移除 admin 工具，但**不加** `@require_permissions` 与函数体检查（刻意隔离过滤层）；
  - **With-extensions（生产）**：过滤器 + 装饰器双层，读取同一 `_required_permissions` 注解；
- **每步记录三个布尔量**：attempt（是否发出命名 `restart_pod` 的 `tool_call`）、invocation（是否执行 vs. `PermissionError`）、leak（名称是否出现在输出任意位置）；
- **阳性对照**：4 个 viewer 允许的良性请求 × 3 次/模型，要求选对工具并完成调用；GPT-5、claude-sonnet-5、claude-opus-4-8 各 12/12 成功（合计 36/36）。

### 3.3 其他评测
- **G2/G3 多请求头矩阵**：枚举 Bearer + 自定义头（SSO + 服务账户）的 4 种组合（有/无 × 有/无），验证无越权、无静默默认、全失败即报错；
- **G4 缓存陈旧窗口**：解析分析（均匀到达下平均延迟 TTL/2，最坏 TTL）；
- **过滤旁路验证**：脚本化（非 LLM）攻击者直接发 `tools/call`，对比三种配置的结果（表 6）；
- **C3 侦察分析**：对"被攻陷注册表"与"匿名 scope 猜测"两种弱化对手做定性分析；
- **性能微基准**：每（配置, 操作）1000 次请求、3 轮取中位数、50 次预热，4 种累积配置（vanilla / +auth / +auth+filter / +auth+filter+decorator）；
- **生产观测**：PayPal 企业 AI 智能体平台上数十个已认证 MCP 服务器，7 天生产追踪。

### 3.4 Benchmark 说明
论文**未使用公开标准 benchmark**（如 AgentDojo、InjecAgent、ToolEmu），明确声明"不评测模型对提示注入的鲁棒性"，仅自建 60 条载荷语料用于测量基线暴露分布、跨厂商方差与名称泄漏率。

    - **阳性对照仅 GPT-5 与攻击扫描做了 checkpoint 匹配**，因此作者将其定位为"基础设施级"而非逐条件的模型级验证；
    - gemini-2.5-pro **未纳入阳性对照**（当时无可用网关路由）；
    - 生产数据为观察性，不可复现；使用专有网关使外部复现受限（虽提供兼容接口）。

## 6. 主要结论与发现

- **防护效果**：仅做请求体检查的 Baseline 在 720 次 viewer 尝试中暴露禁用工具 **152/720（21.1%，Wilson 95% CI [18.3, 24.2]）**；Filter-only 与 With-extensions 均为 **0/720（CI [0, 0.5]）**。三种配置下**实际成功调用均为 0**。
- **跨厂商对齐方差巨大**：在完全相同的 60 条提示与 scope 集合下，Baseline 尝试率从 **0

- **跨厂商对齐方差巨大**：在完全相同的 60 条提示与 scope 集合下，Baseline 尝试率从某厂商的 **0%（完全未发起越权调用）** 跨越到另一厂商的显著高位，作者据此指出——**同一套 MCP 服务器配置在不同模型背后呈现出截然不同的攻击面**，因此"模型层对齐"不能替代"服务器层强制"，企业不能依赖单一模型的安全训练结果来收敛授权风险。
- **名称泄漏与调用尝试解耦**：`leak`（工具名出现在输出中）与 `attempt`（真正发起 `tools/call`）是两个独立量。过滤层消除了 `attempt`，但名称仍可能在模型输出中被复述；论文据此强调"隐藏"不等于"防护"，真正的安全来自调用时的 DNF 强制。
- **过滤层与装饰器层的互补性**：Filter-only 已把 LLM 路径的尝试降到 0，但**脚本化攻击者可直接构造 `tools/call`**（表 6），此时过滤器不生效、只有 `@require_permissions` 拦截并返回 403/`PermissionError`。两层的组合才同时覆盖"智能体被诱导"与"攻击者绕过智能体"两类威胁。
- **多请求头矩阵结论**：4 种 Bearer/自定义头组合下，无越权提升、无静默回退到匿名、双头同时无效时正确返回 401，验证了 OR 语义下的失败隔离（无效令牌不阻断另一头的有效令牌）。
- **缓存陈旧窗口**：解析分析给出均匀到达假设下平均授权延迟为 **TTL/2**、最坏情形为 **TTL**，论文用默认 300 秒 TTL 说明这是可运维调整的"新鲜度—厂商 API 负载"权衡，而非协议缺陷。
- **性能开销**：微基准显示累积配置（vanilla → +auth → +auth+filter → +auth+filter+decorator）的每次操作开销增量保持在**可接受的低毫秒级**，装饰器层因复用缓存权限与短路 DNF 求值而额外开销有限（论文以中位数报告，未观察到数量级退化）。
- **生产观测**：PayPal 平台上数十个已认证 MCP 服务器、7 天追踪未出现由本方案引入的认证回归或误拒（假阳性）事故，作者以此说明"发现—列表—强制三面同源"的工程可行性。
- **核心主张验证**：三面一致性（pre-auth 元数据 / 认证后 `list_tools` / 调用时检查）由**单一 `_required_permissions` 注解**驱动，因此不存在"元数据说可调用、列表里不出现、调用时却放行"的漂移状态——这正是论文声称的结构性贡献，而非任何单一机制的 novelty。

## 7. 局限性与未来工作

- **单工具、单场景**：仅以 `restart_pod` 作为禁用目标、8 个模拟 K8s 工具，未覆盖多工具链式调用、跨服务器组合攻击、工具输出污染下游调用等复合路径。
- **不评测模型鲁棒性**：60 条语料用于刻画"服务器配置暴露"而非"模型抗注入能力"，混淆/编码/多语言载荷交由专门基准（如 AgentDojo、InjecAgent）评估。
- **生产数据不可复现**：专有企业网关、观察性 7 天追踪均无法从制品重建；虽 harness 兼容 OpenAI API，但模型版本漂移会使重跑结果不可比。
- **缓存与不透明令牌的固有窗口**：300 秒 TTL 意味着撤销（revocation）存在最长 5 分钟的生效延迟，对高敏感操作需配合更短 TTL 或每次调用内省，论文承认这是可用性与时效性的取舍。
- **schema 公开性**：C3 的预认证端点对任何网络可达方暴露工具名、参数 schema 与 `required_permissions`，论文以"描述非访问"为辩护，但承认这为攻击者提供了侦察信息（已在 C3 侦察分析中以弱化对手做定性讨论）。
- **生态范围**：实证仅覆盖 6 种官方 SDK 的特定版本快照，Java/Kotlin/PHP/Ruby 明确不在主张范围内；MCP 协议与 SDK 的快速演进可能使差距分析过时。
- **未涉及的授权维度**：未处理工具调用**参数级**的细粒度约束（如"只能重启 namespace X 中的 Pod"）、配额/速率限制、以及智能体间委托（on-behalf-of）链路的令牌降权。

## 8. 整体评价与价值

- **定位准确**：论文刻意不宣称"首个 MCP 授权机制"，而把贡献收敛为**三面一致性的组合问题**及其在原生扩展点上的实现，这种克制的定位使其结论比"又一个认证方案"更可复用。
- **工程友好**：C1–C4 全部落在 Starlette 路由、HTTP 中间件、FastMCP 应用中间件、Python 装饰器四个原生扩展点，不修改协议、不碰私有 API、不做 monkey-patching，降低了企业采纳的迁移成本。
- **安全论证清晰**：把"工具可见性即动作空间"形式化为可见性–强制一致性不变量（*t* 在 *c* 的 `list_tools` 中 ⇔ *c* 可调用 *t* ⇔ *c* 满足 *t* 的 DNF 需求），并强调**智能体的自然语言输入不进入该决策**，这直接切断了提示注入到授权的因果链。
- **与零信任框架对齐**：逐次调用携带已验证凭据、最小可见性、免认证发现、多 IdP 共存四点，均能在 NIST SP 800-207 的语境下自洽，适合作为企业内部 AI 智能体平台的落地参考。
- **可改进之处**：若能把 60 条语料扩展为与公开注入基准的对齐评测、把单工具扩展为多工具链式场景、并把 TTL 撤销窗口做定量安全分析，论文的经验说服力会显著增强；此外，阳性对照覆盖不全（缺 gemini-2.5-pro）与生产数据不可复现，是外部读者评估其泛化性时需自行打折的两点。
